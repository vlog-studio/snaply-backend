# Consuming the backend API contract

This document records how the mobile workspace consumes the Snaply API workspace in the same monorepo. The contract — every endpoint's path, method, query, body, and per-status response — is a set of Zod schemas in `packages/shared-types/src/contract/`, published as `@vlog-studio/shared-types`. The backend validates requests and serializes responses with those same schemas and generates its OpenAPI document from them, so the package *is* the wire contract, not a description of it. `src/shared/api` owns the mobile transport (`apiRequest`), `_app/providers` owns the `QueryClient`, and the entity/feature slices consume them (see [`state-and-data.md`](../frameworks/state-and-data.md)).

For where each piece of state and data code lives, read [`state-and-data.md`](../frameworks/state-and-data.md). For import direction and Public API rules, read [`module-boundaries.md`](../conventions/module-boundaries.md). The monorepo-level decision, its rejected alternatives, and the mismatches it surfaced are in [`docs/decisions/api-contract-schema-first.md`](../../../../docs/decisions/api-contract-schema-first.md).

## Decision

Use **the shared contract package for types plus a hand-written client, query, and mapping layer**:

- Derive request and response **types** from the contract's route registry (`apiContract`) — imported as a type only, so the package is not part of the app bundle.
- Perform transport with the hand-written `apiRequest` in `src/shared/api/client.ts` — a thin `fetch` wrapper that owns the base URL, Supabase JWT injection, the backend's response envelope, and `ApiError` normalization.
- Write Zod validation, domain mapping, `queryOptions` factories, and mutations **by hand**, placed in the owning FSD slice.

Slice code (entity queries, domain mapping, feature mutations) stays hand-managed so it keeps obeying FSD rules. When the contract changes, the backend change edits the package; the app's next `npm run typecheck` reports every call site the change affects.

### Why not a generated client

Tools such as `orval` or `@hey-api/openapi-ts` generate a client, TanStack Query hooks, and Zod schemas in one pass, but they fight this project's architecture:

- Output is a **flat generated folder** that ignores FSD slices (`entities` / `features` / `pages`).
- They **expose DTOs as app-wide types**, which [`state-and-data.md`](../frameworks/state-and-data.md) forbids ("Do not expose DTOs as if they were application-wide domain types").
- They generate their own query keys, **bypassing the `queryOptions` factory** convention.
- They group mutations mechanically with read queries instead of by user action.

`openapi-fetch` was evaluated twice (2026-08-07) and deferred both times: every response is wrapped in the `{ success, data }` envelope and the app's error model is throw-based (`ApiError`), while `openapi-fetch` returns result-shaped `{ data, error }`. Wrapping it inside `apiRequest` would erase the per-call inference that is its main value. With the contract package the question is moot — `apiRequest` derives the same typing from the Zod schemas directly.

### History

Until 2026-09-05 the types came from `openapi-typescript` over a committed copy of the backend's OpenAPI document (`docs/api/openapi.json`, refreshed by curling a running server's `/docs/json`). That pipeline — `api:pull`, `api:gen`, `api:check`, and the generated `src/shared/api/schema.d.ts` — is gone. The OpenAPI document still exists as `apps/api/openapi.json`, generated by the backend from the same contract and guarded by its snapshot test; it serves Swagger UI, Postman, and any consumer outside this monorepo.

## Tooling

| Concern | Tool | Location |
| --- | --- | --- |
| Endpoint paths, methods, query, body, response types | `@vlog-studio/shared-types` (`apiContract`, type-only import) | `packages/shared-types/src/contract/` |
| Typed endpoint paths | `ApiPath` / `apiPath()` over the registry's `path` literals | `src/shared/api/paths.ts` |
| Transport | hand-written `apiRequest` (`fetch` + envelope + `ApiError`) | `src/shared/api/client.ts` |
| DTO validation + domain mapping | Zod (hand-written) | `entities/<entity>/api`, `features/<action>/api` |
| Queries and mutations | TanStack Query `queryOptions` factories | `entities/<entity>/api`, `features/<action>` |
| QueryClient and provider | hand-written | `src/_app/providers` |

The contract package is consumed from its build output (`packages/shared-types/dist`, `exports` → `dist/index.d.ts`). `npm run verify` builds it first (`contract:build`), and the root `npm run dev:mobile` does the same before starting Metro. A bare `npm run typecheck` after pulling a contract change may need `npm run contract:build` once.

## Contract source of truth

The contract is the Zod schemas in `packages/shared-types/src/contract/`, one file per API area (`videos.ts`, `edit-jobs.ts`, …) plus `common.ts` (the success/error envelopes), `vocab.ts` (the closed value sets), and `define-route.ts`. Each endpoint is a `defineRoute({ method, path, schema })` and the registry `apiContract` lists them all. The backend registers its Fastify routes from the same objects and the package is a shared surface under [`docs/team.md`](../../../../docs/team.md) §2 — a contract change is a backend change first, made together with the route and, when user-visible behavior moves, the spec under `docs/specs/`.

To understand a contract — the fields, the enums, the error codes — read the route's file in the contract package. Grepping for the path (`'/edit-jobs/{id}'`) finds its `defineRoute`. The generated `apps/api/openapi.json` shows the same thing in OpenAPI form.

The edit-progress WebSocket (`/edit-jobs/:id/progress`) is not representable in OpenAPI; its message contract is `editProgressEventSchema` in `contract/edit-jobs.ts`, described for readers in the [root API document](../../../../docs/api-spec.md).

## How `apiRequest` uses the contract

`apiRequest(path, { method, query, body, schema })` selects the route by path — or the template a `ResolvedApiPath<P>` was built from, which the brand carries — plus method, and from its schema derives:

- the allowed `query` keys and value types (`z.input` of the route's `querystring`),
- the JSON `body` shape (`z.input` of the route's `body`; forbidden where the route has none),
- whether `method` may be omitted (only where the contract defines a GET for that path),
- the success envelope's `data`, which the call's Zod `schema` must be **assignable from** — a schema may narrow the contract to the consumed fields, or widen an enum to `string`, but cannot invent a field or contradict a type.

A typo'd endpoint, query key, or body field is therefore a compile error at the call site. The compile-time cases live in `src/shared/api/client.test.ts` as `@ts-expect-error` contract tests.

## Layered data flow

```text
apiRequest (typed by the contract)  →  entities/<e>/api: Zod parse + map  →  domain model
       [shared/api]                            [entities]                    [ui / model]
```

- **`shared/api`** encapsulates transport: base URL, the `Authorization` header, the response envelope, HTTP status handling, and transport-error normalization into `ApiError`. It exposes `apiRequest`/`apiPath`, not DTOs.
- **`entities/<entity>/api`** calls the client, validates the response with Zod where validation is warranted, and maps the DTO to the domain model. Keep query keys and query functions together in a `queryOptions` factory (`<entity>.queries.ts`) as shown in [`state-and-data.md`](../frameworks/state-and-data.md).
- **`features/<action>`** owns mutations, including cache invalidation and optimistic updates. Place a mutation by the user action, not next to the read queries.
- **`pages/<page>/api`** holds a composite endpoint or a mutation meaningful to only one screen.

Contract types are referenced **only** inside `shared/api` and at the input boundary of each slice's `api` segment. Do not let a contract type escape into `ui` or `model` — those see domain models only.

## QueryClient and provider

`src/_app/providers` owns the first `QueryClient`, the `QueryClientProvider`, and global retry/cache policy. Do not create a `QueryClient` singleton inside a feature or page.

## Authentication and error ownership

- Token injection (the Supabase JWT `Authorization` header) and HTTP/transport error normalization live in `shared/api/client.ts`.
- The **meaning** of a session token — which keys are stored and when they are cleared — belongs to the session domain, not to `shared`. Persist tokens through the `shared/lib/secure-storage` adapter, orchestrated by `entities/session` and a sign-in feature, per [`state-and-data.md`](../frameworks/state-and-data.md).

## Zod validation policy

Contract types are compile-time only. Zod at the slice `api` boundary remains the **runtime** response contract: every `apiRequest` call requires a schema for the envelope's `data`. Keep schemas focused on the fields the app actually consumes; do not blanket-validate every field of every response (see the error-placement table in [`state-and-data.md`](../frameworks/state-and-data.md)). Where a response's enum may grow on the server (edit-job status, template style), keep the boundary schema **wider** than the contract (`z.string()`) and narrow in the mapper — a value this build has not heard of must not fail the whole call.

Reusing the contract's Zod schemas at runtime (`videoSchema.pick(...)`) would make the package part of the app bundle; that step is tracked in the root backlog (B-5) and is not done — until then the boundary schemas stay hand-written, checked against the contract by `apiRequest`'s assignability rule.
