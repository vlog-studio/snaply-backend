# Application shell and navigation

## User-visible behavior

Snaply opens into a four-tab application — 스튜디오 (`/`), 스냅 (`/snaps`), 무비 (`/movies`), and 나 (`/me`) — laid out as **five slots**: the four tabs sit two to either side of a reserved middle lane that holds an ember capture button. The tab bar shows icons only (no text labels); each screen keeps its label for accessibility and route-name fallback. Capture is an action rather than a tab: the center button opens `/capture` from any tab, which the root stack presents as a full-screen modal over the tab navigator. `/capture` is the viewfinder itself (the clip length is chosen inline, not on a separate setup screen).

| Capability | Status | Notes |
| --- | --- | --- |
| Root stack and route composition | `Functional` | Route files are thin Expo Router adapters. |
| Tab navigation | `Functional` | All platforms share one implementation using the stable `Tabs` navigator from `expo-router` (React Navigation bottom tabs) with four screens. The bar is icon-only (`tabBarShowLabel: false`) with `@expo/vector-icons` Ionicons; each screen keeps a `tabBarAccessibilityLabel`. |
| Animated tab switch | `Functional` | Switching tabs cross-fades with a slight lateral shift (`animation: 'shift'`) on both platforms — the JS tab navigator animates nothing by default, which read as a hard cut, most visibly on Android. Reduced motion (`useReducedMotion`) drops it back to `'none'`, per the app-wide 저감 모션 rule. The navigator also mounts all four scenes at launch (`lazy: false`): a lazily-mounted scene's first frame is its empty background, and the cross-fade stretched that blank frame into a visible blink on a tab's first visit. Visited tabs stayed mounted anyway (see scroll retention below), so this only moves render cost to startup, behind the splash overlay. |
| Center capture button | `Functional` | A 52pt ember circular button (`CaptureButton`) is rendered as an overlay inside `app-tabs.tsx`, outside `<Tabs>`, seated in the bar's reserved middle lane and lifted 10pt clear of its top edge. Its `pointerEvents="box-none"` container lets tab touches pass through; only the visible circle is tappable, and it `router.push('/capture')` with a light impact haptic on iOS. It is an overlay rather than a tab because `/capture` is a root-stack modal, not a tab route. |
| Reserved capture lane | `Functional` | The bar's four items are `flex: 1`, so an overlay centered on the bar would land on top of the inner two rather than between them — with four tabs the clearance to the 스냅 and 무비 icons was ~6pt and the button ate ~31pt of each of their touch areas, so aiming at a tab could open the camera. The two inner items now each give up half of `CaptureLane` (`CaptureSize + CaptureGutter * 2` = 80pt) as a `marginEnd`/`marginStart`, which makes the bar lay out as five slots and leaves the lane exactly screen-centered. Clearance to the neighbouring icons is ~41pt on a 393pt-wide device, and no tab item's touch area is taken. The lane is derived from `CaptureSize` so the two cannot drift apart. |
| Translucent blurred tab bar | `Functional` | The bar is absolutely positioned with a transparent background and an `expo-blur` `BlurView` (`tabBarBackground`) so scene content shows through it — native blur on iOS, `dimezisBlurViewSdk31Plus` on Android (semi-transparent fallback below SDK 31); tint follows the resolved scheme. On Android the blur needs an explicit sample source: each tab scene is wrapped (via the navigator's `screenLayout`) in a `BlurTargetView` and the focused scene registers itself as the bar's `blurTarget` — without it the native side silently falls back to the tint-only background. A hairline top border remains. Scrollable screens offset content by `useTabBarHeight` (`shared/ui/theme`) so nothing sits permanently behind the bar. |
| Headerless pushed screens | `Functional` | `/movie/[id]`, `/movie/[id]/add-snaps`, and `/template/[id]` run with `headerShown: false` and draw a bare back arrow of their own (`shared/ui/back-bar`; the picker passes it the `스냅 더 넣기` title), pinned above the scroll view so it stays reachable on iOS, where there is no system back button. A titled navigation bar over these screens could only ever name the *kind* of screen — `무비`, `템플릿` — one line above the movie's or template's actual name, and on Android it cost a second status-bar height as well: both pages padded their content with `useTopContentInset`, which is for headerless screens, so the bar and the inset stacked into ~55dp of empty ground between the two titles. Removing the bar removed both, and the four tab screens' large-title-with-no-bar layout now runs through the whole app. Header titles remain on the auth screens, which have no large title of their own. |
| Modal capture entry | `Functional` | The center button opens `/capture` as a root-stack full-screen modal (`presentation: 'fullScreenModal'`, header hidden); a close button on the screen returns to the Studio. |
| Native animated splash transition | `Functional` | The system splash is hidden after the overlay lays out, then the overlay — the Snaply moment-ring mark (`assets/images/brand-glyph-ember.png`, 150dp) on the ground background — fades out. The native splash has light and dark variants (`expo-splash-screen` `dark` config) that follow the **OS** appearance, so the overlay mirrors `useColorScheme()` rather than the in-app theme mode; its resting frame matches the native config exactly, so the handoff is seamless. |
| Web splash transition | `Functional` | The overlay intentionally renders nothing on web. |
| App-wide Pretendard GOV | `Functional` | Every piece of app text is Pretendard GOV — prose, headings, controls, inputs, and the native stack header titles. The four faces the type roles use (400/500/700/800) are **embedded natively** by the `expo-font` config plugin, so the family is there on the first frame: no `useFonts` gate in the root layout and no flash of a system face. One family name (`Pretendard GOV`) carries all four weights on both platforms, so styles pair `fontFamily` with `fontWeight` and never name a single face. The system monospace stays in place for the two mono roles (`edge`, `code`), which Pretendard has no face for — but only for the Latin and digits it can actually draw: it ships no Hangul, so Korean micro-labels take the sans `note` role instead of falling back to a third, unasked-for CJK family. See [App branding and native config](../workflows/app-branding-and-native-config.md#app-font). |
| Theme modes (system / light / dark) | `Functional` | The app ships one warm-neutral design in two schemes: the original dark palette and a warm-paper light palette that shares the ember accent and the near-black `media` video ground. A persisted theme-mode preference (`shared/ui/theme`'s `theme-mode` store, SecureStore key `snaply.theme-mode`, default `system`) is set from the 나 tab; `useResolvedColorScheme` resolves a `ThemeScope` pin first, then the stored mode, then the OS appearance (unknown OS scheme falls back to dark). The viewfinder (`/capture`) is pinned dark via `ThemeScope` because its ground is the camera feed. |
| Unified Android system navigation bar | `Functional` | The OS contrast scrim behind the Android 3-button navigation bar is disabled (`expo-navigation-bar` config plugin, `enforceContrast: false`), so the system buttons float directly over the tab bar's blur instead of sitting on a separate opaque strip. `AppProviders` renders `NavigationBar` with the resolved scheme's style — light buttons over the dark shell, dark buttons over the light shell. `NavigationBar`'s `style` names the **button** color, exactly like `expo-status-bar`, so it must track the `StatusBar` style rather than invert it; the package's own `NavigationBarStyle` doc comment claims the opposite ("`dark` a dark navigation bar with light content"), but its native module reads the value as content color (`hasLightBackground = style == "dark"` -> dark glyphs), and the app shipped the inverted pairing until it was caught on device. The OS is the only owner of the button color beyond that light/dark bit: Android 15+ enforces edge-to-edge and offers no API to tint the system glyphs. Since the system side cannot move, the **dark** scheme moves the app side instead: unselected tab glyphs take a dedicated `tabInactive` palette role (`#969696`) rather than the warm `textSecondary`, dropping the hue while keeping that color's exact relative luminance, so the two rows read as one family and no contrast ratio changes. The light scheme keeps `tabInactive` equal to `textSecondary` — the OS draws dark glyphs over the paper shell there, so nothing clashed, and going neutral only chilled the tab bar against the warm headings beside it. Both schemes were compared on device before deciding. Gesture navigation and iOS are unaffected. |
| Scheme-driven status bar and navigation theme | `Functional` | `AppProviders` recolors the matching Expo Router base theme (`DarkTheme`/`DefaultTheme`) with the resolved scheme's palette and flips the `expo-status-bar` style with it; `/capture` mounts its own light status bar for the viewfinder. |
| Film-grain overlay | Removed | A faint grain texture used to be laid over the whole app. It was the film metaphor's defining texture, which the redesign drops; `shared/ui/film-grain` was deleted with it. |
| Daily-roll gate | Removed | A headless provider used to create "today's roll" on app entry. There is no daily roll any more, so the provider and its entity are gone. |
| Screens without narration | `Functional` | **App-wide copy rule.** No screen explains itself in a sentence when the screen already shows the thing. Standing instruction lines under controls, empty-state paragraphs that describe the flow, per-row `note` captions restating a button's label, and scope disclaimers on sheets were removed everywhere they existed: the viewfinder's five-branch helper line, the tray's empty paragraph, the style sheet's `스타일은 전환·색보정·음악에만 적용돼요` tail, `EditExitSheet`'s three option notes, the progress panel's `앱을 나가도 계속돼요`, the recording library's empty description and storage note, the failure footer's `타임라인의 +로…` retry instruction, the picker's `…에 넣을 스냅을 고르세요` subtitle, the sign-up subtitle, and the second sentence of every empty state (스냅 · 무비 · 스튜디오 · 스냅 더 넣기). What stays: **state** (what the app is doing or refusing, and why — errors, refusals, disabled-row reasons, the drift notices, destructive-action consequences), **read-outs** (a value the UI cannot otherwise show, written as a label rather than a sentence — 세부's 순서 고정 reads `지금 순서` / `찍은 시각 순`), and **accessibility hints**, which are copy for a screen reader and are not on screen. An empty state is a heading plus its action button, nothing else. |
| Scroll position kept per tab, reset on re-tap | `Functional` | Switching tabs keeps each tab's scroll position: the tab screens stay mounted, so a trip to another tab and back returns the user where they were — the shell is a workbench the user resumes rather than four screens that restart. Resetting is bound to the gesture that means it on a native tab bar: tapping the tab that is **already** open scrolls it back to the top, animated. All four tab pages own a ref on their `ScrollView` and call `useScrollToTop` from `expo-router` (which re-exports React Navigation's hook, so no `@react-navigation/*` import is needed). The hook reads focus **synchronously** when `tabPress` fires — before the navigator's `jumpTo` commits — and only defers the scroll itself a frame, which is what keeps a tap on an *inactive* tab from resetting the tab it reveals. The Snap tab's selection mode hides the tab bar, so there is no tab to re-tap while picks are in progress. |
| Screen-owned bottom chrome takeover | `Functional` | A screen can claim the bottom of the shell for an action bar of its own through the `shared/ui/tab-bar-chrome` store: it flips the switch, and the navigator hides both the tab bar (`display: 'none'`) and the capture button. The one caller today is the Snap tab's selection mode ([Snap library](snaps.md)). The mechanism was briefly removed when the then-selection grid moved to a route that had no tab bar to hide, and restored when selection came back inside a tab — a screen cannot simply draw over the bar, because the navigator paints it above every scene. Whoever hides it owns restoring it; tying the flip to an effect's cleanup, conditioned on focus as well as on the screen's own state, is what keeps a stray navigation from stranding the app with no bottom chrome at all. |

`src/app` parses string search parameters where needed and passes them to page components as explicit props (`snaps.tsx` turns `?select=1` into `startSelecting`). The `src/_app/routes` module owns stack and tab policies; page slices own screen content.

**A pushed tab route is not a pushed screen.** Navigating from a root-stack screen to a route inside `(tabs)` diverges at the root stack, so Expo Router pushes a *second* `(tabs)` entry: a whole new tab navigator mounts over the screen the user came from, with the target tab focused and the first tab in its history. `router.back()` is then delivered to that tab navigator — the deepest focused one — which handles it by switching back to its first tab instead of letting the root stack pop. This is what a movie's 스냅 더 넣기 used to do (`/snaps?select=1&for=<movieId>`), landing the user on the 스튜디오 screen after they added a cut. A flow that starts on a pushed screen and must return to it belongs on the root stack (`/movie/[id]/add-snaps`), even when it looks like a tab.

`/movie/[id]` and `/template/[id]` are pushed stack screens rather than tabs: each is a task with a beginning and an end, and each needs its own back affordance — which is a back arrow the page draws itself (`shared/ui/back-bar`) rather than a navigation bar. The bar is bare where the screen can name itself in its content (`/template/[id]`, a scroll with a large title); a screen with no row to spare passes it a `title` and one `action` instead, which is how `/movie/[id]` shows the movie's name and its ✎ without taking height from the stage. There is deliberately **one** movie route — watching a finished movie and fixing it are the same visit, so a second one would have meant two places that can edit one cut list. A movie tile or studio row therefore has nothing to branch on: every movie, at every status, opens on `/movie/[id]` ([The movie screen](movie.md)).

## Composition and ownership

- `src/app/_layout.tsx` exposes `RootLayout` from the `_app` Public API.
- `src/_app/providers/app-providers.tsx` derives the Expo Router navigation theme, status-bar style, and Android navigation-bar button style from the resolved color scheme. It also mounts eight headless nodes, none of which owns any UI. Two run signed out as well as signed in: `LibraryScopeGate`, which binds the snap, sync, and movie stores to the signed-in account's own files and drops the query cache when the account changes (see [Authentication](authentication.md), [Snap library](snaps.md#file-model-and-storage-boundary)), and `DeletedLibraryPurgeGate`, which collects what a deleted account left on the device once its 30-day restore window has passed. The remaining six serve the authenticated session: `PushTokenGate` (which wraps `register-push-token`'s `PushTokenRegistrar`) and `GeofenceGate` (see [Location alerts and push notifications](location-and-push-notifications.md)); `MovieGenerationBridge`, which hands the 무비 완성 알림 preference to `compose-movie`'s `MovieGenerationGate`; `SnapDurationBackfill`, the one-per-start duration repair; `TrayDraftMigration`, the one-per-start promotion of an older build's leftover `snaply.tray` into a draft movie (see [Studio and movies](studio.md)); and `SnapUploadGate`, the background snap upload worker (see [Snap library](snaps.md#backend-upload-sync)). `MovieGenerationBridge` carries a movie's generation job to its render from here rather than from the movie screen, so a job keeps running once the user leaves it and is picked back up on the next app start (see [The movie screen](movie.md)). `PushTokenGate`, `GeofenceGate`, and `MovieGenerationBridge` are the same shape despite the different names — each is an app-layer component that reads a preference from `features/notification-settings` and hands it to the feature that acts on it, because features must not import each other. It wraps its children in `GestureHandlerRootView`, the ancestor `react-native-gesture-handler` gestures require, which expo-router's native stack does not provide.
- `src/_app/routes/root-layout.tsx` composes providers, splash behavior, and stack presentations, and imports `register-background-tasks` for its side effect so the background geofence task is defined at startup (including on a headless OS relaunch).
- `src/_app/routes/app-tabs.tsx` is the single cross-platform tab navigator (`Tabs` from `expo-router`) with the four screens plus the `CaptureButton` overlay; there is no platform-specific tab variant.
- `src/shared/ui/theme` owns the two palettes (`Colors.light`/`Colors.dark`, sharing every token key including `amber`, `lumen`, `ai`, and `media`), the persisted theme-mode store (`useThemeMode`/`useSetThemeMode`), the `ThemeScope` scheme pin, the resolution hooks (`useTheme`/`useResolvedColorScheme`), the two font families (`Fonts.sans` — Pretendard GOV — and `Fonts.mono`) and the type scale, spacing, radii, content width, the Android top content inset helper, the tab bar height helper (`useTabBarHeight`) used to offset scrollable screens beneath the translucent bar, and the `useReducedMotion` accessibility helper that lets animated screens present their final state immediately. `TabBarContentHeight` (52pt, the bar above the safe-area inset) is sized to seat the capture button rather than be towered over by it; every scrollable screen follows it through `useTabBarHeight`.
- `src/shared/ui/tab-bar-chrome` owns the bottom-chrome switch shared by the tab navigator and any screen that replaces the bottom chrome with its own bar. It is business-agnostic: it knows something owns the bottom of the screen, not what or why.
- `src/shared/ui/back-bar` owns the pushed screens' back affordance. It takes an `onPress` and knows nothing about routing — the page decides what "back" means, including the fallback to the studio when a deep link left no history behind it.
- `src/shared/ui/fade-in-view` owns the mount fade-in used instead of Reanimated `entering` presets, which never start on iOS in Expo Go and left content invisible.

## Known limitations

- The tab bar is a JS-drawn React Navigation bar, not a platform-native tab bar; it has no haptics or scroll-to-minimize. Re-tap-to-top is implemented in JS (see the capability table) but deliberately fires no haptic: the press cannot tell whether the screen was already at the top, so a haptic would fire for a scroll that never happened. Its background blur is native on iOS and uses the `expo-blur` Dimezis implementation on Android (semi-transparent fallback below SDK 31).
- The Android blur samples only the focused tab scene's subtree (the `BlurTargetView` wrapper), because Dimezis BlurView v3 forbids the `BlurView` from living inside its own target — wrapping the whole navigator (which contains the tab bar) is not possible. Content rendered outside the scene, such as a root-stack modal sliding over the tabs, is not reflected in the bar's blur on Android.
- The splash animation is native-only.
- The near-black `media` token and the white glyphs/scrims drawn over video are the same in both schemes by design: video surfaces never lighten. The ember accent is also shared, which leaves it at ~3:1 against the light ground — acceptable for fills and large glyphs, so it should not be used for small light-theme body text.
- Pretendard GOV is embedded for native builds only, by design: the app ships to iOS and Android, so no webfont is served and `npm run web` falls back to the next family in the `--font-body` stack in `_app/styles/global.css` (`Noto Sans KR`, then a system sans). Text the OS draws rather than the app — permission dialogs, `Alert`, notifications, the share sheet — also stays on the system font.
- Expo Router's generated route types (`.expo/types/router.d.ts`) are a gitignored build artifact that regenerates on `expo start`; after the route set changes, typed-route checking is only as fresh as the last regeneration.
