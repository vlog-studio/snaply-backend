# Me tab

## User goal

The 나 tab (`/me`) shows who you are and what you have recorded, and is the doorway to every preference: reminder timing, notification frequency, movie-completion alerts, location alerts, quiet hours, interests, social connections, and account management.

The record is the hero and the settings are one push away (owner decision, from the "기록이 주인공" prototype). The tab root shows the week ring, the identity, the three counts, and five summary rows — 크레딧, 알림, 화면 테마, 관심사, 소셜 연결 — whose one-line read-outs are the current settings; the controls themselves live on `/settings/*` root-stack screens. **Do not expand the controls back onto the root.** Fully expanded, they ran three viewports deep at one visual weight; state stays visible at the root and only the controls are deferred.

This document owns these controls and their persistence. The push/geofence mechanism the location-alert, quiet-hours, and interests preferences drive is owned by [Location alerts and push notifications](location-and-push-notifications.md).

## Ownership and state

`src/pages/me` owns the tab root and all six `/settings/*` screens — one page slice, because they are one screen group: the root shows the state the settings screens change. The route files under `src/app/settings` are thin re-exports, and the routes are registered on the root stack in `src/_app/routes/root-layout.tsx` with the stack's own titled headers (크레딧 / 알림 / 화면 테마 / 관심사 / 소셜 연결 / 계정 삭제) — unlike the movie screen, the title here is not one line above the same words. The hero reads the current user through `src/entities/session` (`useCurrentUser`) and computes the week ring from the snap store's `capturedAt`s via `pages/me/model/week-record` (pure, unit-tested; Monday-start calendar week in device-local time). The account section signs out through the same entity (`useClearSession`); the delete-account action (backend soft delete, then sign-out) is owned by `src/features/delete-account` (`useDeleteAccount`), and the confirmation screen only renders its pending/error state. The two stat pills read `entities/snap` and `entities/movie` directly. The row/section/pill primitives the five screens share live in `pages/me/ui/rows.tsx`; the reminder-window labels both the summary row and the 알림 screen render come from `pages/me/model/reminder-windows.ts` so they cannot drift apart. There is no settings entity, form schema, notification scheduler, or social-auth adapter connected to these screens.

The row order on the tab root is deliberate: 크레딧 first (the balance is account state the movie flow spends, not a preference), then 알림 (the group of preferences most likely to be touched), then 화면 테마, 관심사, 소셜 연결, then 계정. Grouping every notification preference — capture reminders, movie completion, location, quiet hours — onto one 알림 screen replaced the old adjacency arrangement in which 관심사 sat under 위치 알림 to imply that it personalizes the location push; that relationship is now server-side documentation ([Location alerts and push notifications](location-and-push-notifications.md)) rather than a placement.

The 화면 테마 control is owned by `shared/ui/theme`'s theme-mode store (`useThemeMode`/`useSetThemeMode`); the page only renders the radio. Resolution order and the light/dark palettes are documented in [Application shell and navigation](app-shell-and-navigation.md).

The location-alert, quiet-hours, interests, movie-completion, and capture-reminder controls are owned by `src/features/notification-settings`. The page renders the controls and consumes the feature's hooks (`useLocationAlerts`, `useQuietStart`/`useQuietEnd`/`useSetQuietStart`/`useSetQuietEnd`, `useInterests`/`useToggleInterest`, `useMovieReadyAlerts`, `useReminderWindows`/`useSetReminderWindow`, `useReminderFrequency`/`useSetReminderFrequency`, plus `INTEREST_OPTIONS`). `useLocationAlerts` mirrors `useMovieReadyAlerts`' contract: turning the switch on first requests foreground then background location permission through `shared/lib/location`, and a refusal leaves the stored preference off with a visible blocked read-out instead of a switch that claims a capability the OS denied. The page adds the two-stage ask on top: the switch opens `pages/me/ui/location-alerts-sheet.tsx`, and only its yes calls `setEnabled(true)` — the OS "always allow" prompt is one-shot, so the in-app question (which can be re-asked freely) absorbs the exploratory taps. The feature persists a Zustand store through the SecureStore adapter (`snaply.notification-settings`; persist v1 — a v0 `enabled: true`, which was a default rather than an opt-in, migrates to off). The first three map to the backend user fields (`notification_enabled`, `quiet_start`, `quiet_end`, `interests`) but are local-only: `GET|PATCH /auth/me` are in the API spec, but no client code binds them yet. How the location-alert switch (`notification_enabled`) drives OS geofencing — the headless `GeofenceGate`, permissions, and arrival reporting — is documented in [Location alerts and push notifications](location-and-push-notifications.md); quiet hours and interests are not consumed on the client and are enforced server-side when the arrival push is decided.

The movie-completion preference (`movieReady`) has no backend field: the run is remote, but the announcement is local — the app raises the notification when it learns the run ended, so the preference never needs to reach the server. `useMovieReadyAlerts` owns the rule that turning it on must first obtain the OS notification grant (`shared/lib/notifications`' `requestLocalNotificationPermission`) — a preference the device will never honor is not worth storing, and the request belongs to a control the user just touched rather than to a background timer. `src/_app/providers/movie-generation-bridge.tsx` reads the stored preference and passes it to `MovieGenerationGate`, the same app-layer composition `GeofenceGate` uses, because the two features must not import each other.

The reminder copy still speaks of suggesting good moments to shoot, which the redesign keeps: the capture reminder is the app's only nudge to shoot now that automatic collection is gone (concept §7).

## Known limitations and implementation requirements

- The morning/lunch/evening windows and the daily-frequency choice persist (notification-settings store), but nothing schedules a reminder from them yet — the section is a placeholder whose choices become effective only when a scheduler exists.
- The location-alert permission *request* runs only when the user flips the switch on; the app-start gate checks the grants without prompting, so a permission revoked later in OS settings means geofencing silently does not start (the switch still shows on) until the switch is toggled again.
- The movie-completion notification is a **local** notification raised by the app when it learns the run ended, not a push from the server. The run itself survives a force-quit (it belongs to the backend), but the announcement does not: nothing is announced until the app is next opened, when the catch-up pass announces immediately; a job the user only backgrounded is announced when the app is next foregrounded, not while it is suspended. Tapping the notification opens the app but does not route to the movie — nothing subscribes to notification responses yet, though the movie id is carried in the payload for when something does.
- The location-alert switch starts/stops geofence monitoring, but none of these preferences are synced to the backend (`PATCH /auth/me` is in the spec, not yet called); quiet hours and interests are enforced server-side when the arrival push is decided.
- Turning the location-alert switch on requires foreground + background ("항상 허용") location permission; if the user declines, monitoring cannot start. The geofence and push mechanism, its platform/permission caveats (including Android 13+ `POST_NOTIFICATIONS` and Expo Go's missing Firebase modules), and foreground-notification presentation are documented in [Location alerts and push notifications](location-and-push-notifications.md).
- Social connections do not use authentication or external APIs.
- Account deletion routes to the in-code mock until an API origin is configured (`USE_MOCK_API`), so against the mock it only signs the user out; the 30-day grace period, the purge, and the restore path are backend behavior. The confirmation screen states the grace period as "30일" statically — the authoritative `purgeAfter` arrives only after the decision is made, so the exact date is shown on the restore screen rather than here (see [Authentication](authentication.md)).

When a control becomes functional, document its persistence owner, permission behavior, external service, loading and error states, and platform support here.
