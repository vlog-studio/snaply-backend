# Me tab

## User goal

The 나 tab (`/me`) shows who you are and what you have recorded, and is the doorway to every preference: movie-completion alerts, location alerts, quiet hours, the theme, the consent to snap analysis, the automatic album copy, and account management — plus the credit balance, and the 준비 중 rows for capture reminders, interests, and social connections.

The record is the hero and the settings are one push away (owner decision, from the "기록이 주인공" prototype). The tab root shows the week ring, the identity, the two counts, and seven summary rows — 크레딧, 알림, 화면 테마, 스냅 분석, 앨범 저장, 관심사, 소셜 연결 — whose one-line read-outs are the current settings; the controls themselves live on `/settings/*` root-stack screens, except 관심사 and 소셜 연결, whose rows read 준비 중 and open nothing. **Do not expand the controls back onto the root.** Fully expanded, they ran three viewports deep at one visual weight; state stays visible at the root and only the controls are deferred.

This document owns these controls and their persistence. The push/geofence mechanism the location-alert and quiet-hours preferences drive is owned by [Location alerts and push notifications](location-and-push-notifications.md).

## Ownership and state

`src/pages/me` owns the tab root and all six `/settings/*` screens — one page slice, because they are one screen group: the root shows the state the settings screens change. The route files under `src/app/settings` are thin re-exports, and the routes are registered on the root stack in `src/_app/routes/root-layout.tsx` with the stack's own titled headers (크레딧 / 알림 / 스냅 분석 / 앨범 저장 / 화면 테마 / 계정 삭제) — unlike the movie screen, the title here is not one line above the same words. The hero reads the current user through `src/entities/session` (`useCurrentUser`) and computes the week ring from the snap store's `capturedAt`s via `pages/me/model/week-record` (pure, unit-tested; Monday-start calendar week in device-local time). The account section signs out through the same entity (`useClearSession`); the delete-account action (backend soft delete, then sign-out) is owned by `src/features/delete-account` (`useDeleteAccount`), and the confirmation screen only renders its pending/error state. The two stat pills read `entities/snap` and `entities/movie` directly. The row/section/pill primitives the root and the settings screens share live in `pages/me/ui/rows.tsx`. There is no settings entity, form schema, notification scheduler, or social-auth adapter connected to these screens.

The row order on the tab root is deliberate: 크레딧 first (the balance is account state the movie flow spends, not a preference), then 알림 (the group of preferences most likely to be touched), then 화면 테마, 스냅 분석, 앨범 저장, 관심사, 소셜 연결, then 계정. 스냅 분석 and 앨범 저장 sit with the live preferences, above the 준비 중 placeholders, because each is a real choice with a real effect; they are next to each other because both are about the user's snaps. Every notification preference — capture reminders, movie completion, location, quiet hours — sits on the one 알림 screen, and 관심사 is not placed next to 위치 알림: adjacency would imply that it personalizes the location push, which it does not — nothing reads interests (see the 관심사 row above).

The 스냅 분석 consent is owned by `src/features/analysis-consent`: the read (`useAnalysisConsent`, one query writing nothing locally), the give/withdraw actions (`useAnalysisConsentActions`, which write the server's answer straight into that query so every screen reading it moves at once), and the consent sheet (`AnalysisConsentSheet`) both this screen and the template screen open. The page renders the switch and the read-out only.

The 앨범 저장 switch is owned by `src/features/save-snap-to-album` (`useAlbumAutoSave` — the permission-gated switch; `useAlbumAutoSaveEnabled` for the tab root's read-out); the page renders the switch, the read-out, and the settings row only.

The 화면 테마 control is owned by `shared/ui/theme`'s theme-mode store (`useThemeMode`/`useSetThemeMode`); the page only renders the radio. Resolution order and the light/dark palettes are documented in [Application shell and navigation](app-shell-and-navigation.md).

The location-alert, quiet-hours, movie-completion, capture-reminder, and interest preferences are owned by `src/features/notification-settings`. The alerts and the quiet hours are the **account's**, held by the server ([notification preferences decision](../../../../docs/decisions/notification-preferences.md) — "서버가 원천, 기본은 꺼짐"): `useNotificationPreferences` reads them (`GET /auth/me`, the query `notificationPreferencesQueries.current()`, `undefined` until the server answers), and `useUpdateNotificationPreferences` writes a change (`PATCH /auth/me`) — shown at once, replaced by the server's answer, put back with an error line on a refusal, and only the newest write's answer committed. The page consumes `useLocationAlerts`, `useMovieReadyAlerts`, and `useQuietHours`; the tab root's 알림 read-out reads `useNotificationPreferences`. `notificationEnabled`, the server's all-off switch, is neither read nor written. The feature still exports `useReminderWindows`/`useSetReminderWindow`, `useReminderFrequency`/`useSetReminderFrequency`, and `useInterests`/`useToggleInterest`/`INTEREST_OPTIONS`, but no screen consumes them while reminders and interests are 준비 중 — those stay in the device-only Zustand store (`snaply.notification-settings` through the SecureStore adapter). `useLocationAlerts` mirrors `useMovieReadyAlerts`' contract: turning the switch on first requests foreground then background location permission through `shared/lib/location`, and a refusal writes nothing and shows a blocked read-out instead of a switch that claims a capability the OS denied; both hooks also read the device's grant check-only (`useDeviceGrant`, on mount and on every return to the foreground) to say when the account's switch is on but this device cannot honor it. The page adds the two-stage ask on top: the switch opens `pages/me/ui/location-alerts-sheet.tsx`, and only its yes calls `setEnabled(true)` — the OS "always allow" prompt is one-shot, so the in-app question (which can be re-asked freely) absorbs the exploratory taps. **Moving from the device copies (persist v2):** builds before 2026-10-07 kept the switches and quiet hours in the store. The v2 migration turns the ones the user had changed from that build's defaults (a switch turned on, an hour moved) into `legacyChoices`, and `LegacyChoicesUploadGate` (mounted in `_app/providers`) writes them to the signed-in account once its preferences have loaded, clearing them only when the server took them; untouched defaults are not sent, so they cannot overwrite what another device set. A v0 `enabled: true` was a default rather than an opt-in and is not sent. How the location-alert switch drives OS geofencing — the headless `GeofenceGate`, permissions, and arrival reporting — is documented in [Location alerts and push notifications](location-and-push-notifications.md).

The movie-completion preference (`movieReady`) is the server's `movieNotificationEnabled`: the server's completion push follows it, and on the device it gates the failure notice the app raises itself. `useMovieReadyAlerts` owns the rule that turning it on must first obtain the OS notification grant (`shared/lib/notifications`' `requestLocalNotificationPermission`) — a preference the device will never honor is not worth storing, and the request belongs to a control the user just touched rather than to a background timer. `src/_app/providers/movie-generation-bridge.tsx` reads the account's preference and passes it to `MovieGenerationGate` (nothing is announced until it has loaded), the same app-layer composition `GeofenceGate` uses, because the two features must not import each other.

The capture reminder stays on the screen as a 준비 중 placeholder rather than being removed because, once a scheduler exists, it is the app's one unprompted nudge to shoot — nothing collects snaps automatically ([product concept](../../../../docs/decisions/product-concept.md) §3).

## Known limitations and implementation requirements

- Capture reminders are 준비 중 placeholders with no control. The notification-settings store still persists reminder-window and frequency values from earlier builds, but nothing schedules a reminder from them; bringing the controls back needs a scheduler first.
- The location-alert permission *request* runs only when the user flips the switch on; the app-start gate checks the grants without prompting, so a permission revoked later in OS settings means geofencing does not start — the switch stays on with the blocked read-out — and a grant given back in OS settings starts it only on the next app start or when the switch is toggled again.
- A **failed** run is announced by a local notification the app raises when it learns the run ended, so that announcement waits for the app: nothing is announced while it is force-quit or suspended, and the next start's or foreground return's catch-up pass announces it. A completed run is announced by the server's push instead, which does not depend on the app running. Tapping either opens the movie ([Location alerts and push notifications](location-and-push-notifications.md)); neither the push's arrival nor the tap has been checked on a device yet.
- The alert switches and quiet hours need the server to be read: offline at start, the controls stay disabled and the geofence gate leaves monitoring as it was. The account has one value for every device, while the OS grants are per device — and the server pushes to the one device that registered its token last (root backlog B-2). A grant given in the OS settings re-registers the push token only on the next app start, or when the movie switch flips. Interests are read by nothing and shown as 준비 중 (backlog A-9).
- Turning the location-alert switch on requires foreground + background ("항상 허용") location permission; if the user declines, monitoring cannot start. The geofence and push mechanism, its platform/permission caveats (including Android 13+ `POST_NOTIFICATIONS` and Expo Go's missing Firebase modules), and foreground-notification presentation are documented in [Location alerts and push notifications](location-and-push-notifications.md).
- Social connections do not use authentication or external APIs.
- Account deletion routes to the in-code mock until an API origin is configured (`USE_MOCK_API`), so against the mock it only signs the user out; the 30-day grace period, the purge, and the restore path are backend behavior. The confirmation screen states the grace period as "30일" statically — the authoritative `purgeAfter` arrives only after the decision is made, so the exact date is shown on the restore screen rather than here (see [Authentication](authentication.md)).

When a control becomes functional, document its persistence owner, permission behavior, external service, loading and error states, and platform support here.
