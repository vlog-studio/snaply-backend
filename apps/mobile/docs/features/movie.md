# The movie screen

## User goal

Users run a movie, watch it, fix what came back, and run it again. All of that happens on one screen, because it is one object at four points of its life.

```text
/  (스튜디오)  이 스냅으로 새 무비        →  /movie/[id]
/  (스튜디오)  무비 board row            →  /movie/[id]
/movies       any tile                  →  /movie/[id]
/template/[id]  이대로 만들기            →  /movie/[id]   (an editable draft)

The one route has two faces. A `ready` movie opens in **watch
mode** — a player and nothing else, with every act behind the back bar's ⋯
sheet — and the **studio** below is what a `draft`/`failed` movie opens on,
what a `generating` movie shows as a read-out, and what "무비 편집하기" in the
⋯ sheet switches a finished movie back to. Watch mode:

/movie/[id]  (무비, ready) — watch mode
├── back bar             ← · the movie's title · ⋯ (the actions sheet)
├── stage                the player, on the render's own composition
│                         (`render.snapRefs`), paused on the first frame;
│                         tapping the stage plays and pauses
├── facts line           {완성 시각} 완성 · 길이 · 스타일 — read-outs, not chips
├── footer               공유 (disabled until a render produces a file, with the
│                         reason written under it); while the cut list has
│                         drifted from the render, a standing notice above it —
│                         편집한 컷 구성이 있어요 — with 구성 확인하고 다시
│                         만들기 opening the studio
└── ⋯ sheet              무비 편집하기 · 이름 바꾸기 · 공유하기 → and, grouped
                          apart in danger color, 무비 삭제하기 (a confirm step
                          inside the same sheet)

/movie/[id]  (무비) — the studio: a timeline studio, not a scroll: every zone is always on screen
├── back bar             ← · the movie's title · ✎ (rename sheet) — the title rides
│                         the bar, so naming the movie costs the stage no height
├── stage                the player on an editable movie, corner-tagged 미리보기;
│                         the progress ring under a job
│                         an edit shows up in it the moment it lands
├── transport            under the stage: 재생/일시정지 on the left, 되돌리기 ↺ / 복원 ↻
│                         on the right (hidden under a job)

│                         scale under a ruler of second marks, running under a playhead
│                         fixed at the middle of the screen; tap = select + the stage
│                         jumps there; playback and scrubbing move the playhead only —
│                         nothing but a tap takes a cut; the selected clip
│                         grows a trim handle outside each edge while stopped (‹ › where
│                         footage remains, a bar where the file ends)
│                         + tile = 스냅 더 넣기 → /movie/[id]/add-snaps

                          no selection — 생성: AI로 생성 시작 / 다시 시도 /
                            이 구성으로 다시 만들기 · 공유 (ready)
```

**Editing happens outside a run, never under one.** Generation becomes slow remote work once a real backend runs it (the LLM integration), so a `draft` is where the user settles the cut order, the cut lengths, and the style **before** paying for a run — and fixing a result afterwards is the same controls on the same screen. Only a `generating` movie is frozen, because an edit under a job would make the result describe a cut list that no longer exists. Two other shapes were tried and dropped, and neither should come back: a three-step wizard *before* generation (조립 → 스타일 → 생성), which split one object across three screens, and its opposite — editing allowed only *after* a run — which made the user pay for a composition they had not settled yet.

There is no separate playback route. Watching a finished movie and fixing it are the same visit, and two routes would have meant two places that can edit one cut list. Watch mode is a face of this screen, not a route: one local flag (`editing`, cleared whenever a run starts so the next result opens as a result), no navigation, and the same undo history rules — switching to the studio and back within a visit keeps the visit's history.

**Leaving the studio mirrors entering it.** 무비 편집하기 switches faces in place, so on a `ready` movie the studio's ← (and Android's hardware back) switches back to watch mode instead of popping the route; only watch mode's ← leaves the screen. When edits made since the studio was entered drifted the cut list from the render's composition (`editedSinceRender`, with the undo depth grown past what it was at entry), the ← asks one question on the way out (`EditExitSheet`): `이 구성으로 다시 만들기` (run now — a refused start stays in the studio with the refusal in the footer), `나중에 만들기` (keep the edits stored and watch the finished movie), or, grouped apart in danger color because the visit's undo history dies with the visit, `편집 취소` (`restoreRenderCuts`). Drift already answered for — an earlier studio entry's within the visit, or an earlier visit's — does not reopen the question; watch mode carries a standing notice for it instead (편집한 컷 구성이 있어요, with 구성 확인하고 다시 만들기 opening the studio), because without one the edits kept for later would be invisible on the face that plays the render. Nothing here is a save prompt: edits commit as they land either way.

**The layout is a timeline studio, not a scroll.** The stage, the strip, and the inspector are fixed zones that never scroll apart: the stage always shows the cut list being edited, the strip and the stage point at the same cut in both directions, and the settings (스타일, 세부, 순서 고정) are sheets opened from chips rather than sections in a column. A long scroll was tried and dropped, because checking an edit meant scrolling back to the top to look at the player.

**The screen carries no explanatory prose.** No status line under the title, no summary under the generate button: every zone the user is looking at already says what those sentences said, and the text cost about 110dp of the one zone that has to stretch, the stage. The title and its ✎ ride the back bar's own 44dp row (`BackBar`'s optional `title`/`action`) instead, which costs nothing. Two consequences worth stating as rules, because both look like omissions:

- **The screen never promises that leaving is safe.** Leaving *is* safe, and the app says so by surviving it rather than by writing it down.
- **The screen does not disclose the mock-mode limitation.** In mock mode nothing is composited (see [Known limitations](#known-limitations)); that is a fact about the build, not something a user acts on, so it stays out of the UI.

| `generating` | The progress ring and the backend's current stage fill the stage — verified on a device (2026-08-10): the ring follows the pipeline's own milestones (0/10/35/60/85/95/100) and the stage line reads the server's wording, with nothing on the screen ticking between them; the strip stays visible as a read-out (no add tile, no inspector), and the sheets open read-only. ### Before a run starts

`startGeneration` is asynchronous and can be refused four ways. Two are the movie's own state — `frozen` (a job already owns it) and `empty` (nothing to generate from). The other two are the backend's:

| Refusal | When | What the user is told |
| --- | --- | --- |
| `uploading` | A cut has not reached the backend yet — still uploading, a failed upload, or never started. The run is made from the *server's* copies of the snaps. Verified on a device (2026-08-10). | 스냅을 서버에 올리는 중이에요. 잠시 뒤에 다시 시도해주세요. |
| `rejected` | The backend refused the run (`403`): a video that is not the caller's, is not `ready`, or is itself a generated result. | **The backend's own message.** One status, one code (`FORBIDDEN`), and only the message says which of those it was — so it is carried through rather than reworded. Verified on a device (2026-08-10) against the quota refusal the backend served at the time (see [How many runs a user gets](#how-many-runs-a-user-gets)): the server's sentence reached the footer unedited, which is the part of this path the app owns. |
| `no-credit` | The backend refused to reserve the run's 100 credits (`402 INSUFFICIENT_CREDITS`). Its own refusal rather than one more `rejected`, because it is the one the screen can point somewhere about. | 크레딧이 부족해요 · {balance}/{required}. 나 탭의 크레딧에서 채울 수 있어요. — the numbers are the 402's own (`error.required`/`error.balance`, read by `readCreditShortfall`) and the line drops them when the backend stops sending them. See [Credits and rewarded ads](credits-and-rewarded-ads.md). |
| `unreachable` | The request itself failed. Nothing was queued and the movie is untouched. | 서버에 연결하지 못했어요. 연결을 확인하고 다시 시도해주세요. |

`uploading` is answered here rather than discovered as a `403`, because `POST /edit-jobs` refuses a batch whole when one source is missing — the user would otherwise press the button and be told something opaque. Refusals surface in the footer, under the button that refused; the movie tab's retry has nowhere to show one, so a retry that cannot start there simply leaves the movie failed with the reason it already carries.

### How many runs a user gets

**Today: as many as the rate limit allows.** The backend enforces no per-plan quota on generation — the free plan's monthly cap of three was withdrawn, and it is explicitly not to be restored mechanically. What still guards the pipeline is technical rather than commercial, and none of it is a product rule this screen states: ten cuts per request, five requests per minute per user (`429`), and a ten-minute worker timeout.

**A run costs 100 credits.** `POST /edit-jobs` reserves 100 credits in the same transaction that creates the job — a run that does not fit the balance is never created — and the reservation is refunded automatically when a run fails or is cancelled (idempotently: re-cancelling refunds once). The insufficient-balance answer is the `no-credit` refusal above, and where credits come from is owned by [Credits and rewarded ads](credits-and-rewarded-ads.md).

**What the app still owes.** A run's cost has to be readable *before* the button is pressed — a cost discovered by being refused is the failure `Value Before Cost` names, and this screen is still committing it: the refusal exists, but no balance or per-run read-out sits beside the generate button yet. That read-out is owed when the paid flow goes live for real (the cost is currently only enforced by a backend the app runs against in mock mode).

### Canceling a run

A `generating` movie's footer holds 만들기 취소; without it the worker's ten-minute timeout would be the only way a mis-started run ends. The control confirms in place (the confirm states what a stop costs: the progress, not the cuts) rather than in a sheet, and while the request is out it reads 취소하는 중….

The rules, owned by `useComposeMovie.cancelGeneration`:

- The server is asked first (`DELETE /edit-jobs/{id}`) and the movie leaves `generating` **only on its word** — flipped first, a run that kept going would finish into a state no longer expecting it.
- **A canceled movie returns to `draft`**, not to `failed`: the stop was asked for, so there is no reason to recover from. The cuts and settings stay exactly as they were; the previous render was already dropped when the job began, so a canceled *regeneration* lands on a draft, not back on the finished movie it was replacing. The backend mirrors this: the job's terminal state is `canceled` and its result video row is deleted.
- A `409` means the run ended while the request was in flight (`done`/`failed`) — nothing is changed and nothing is said, because the result is already arriving through the runner. A `404` (a job the backend never heard of) goes to `draft` all the same: nothing is running, which is what the user asked for. A transport failure changes nothing and says so under the confirm; the run is untouched and pressing again is the recovery.
- The runner recognizes a cancellation it did not perform — the socket's `{"status":"canceled"}` frame, or a `canceled` status on the poll/catch-up pass (another session, or account deletion) — and returns the movie to `draft` without announcing anything. An unknown status must never read as "still running": that would leave a canceled movie polling forever.
- **The confirm does not mention credits.** The rules are settled: the run's 100-credit reservation is released server-side when the job is canceled, idempotently, so a stop costs the progress and nothing else — see [Credits and rewarded ads](credits-and-rewarded-ads.md). The confirm still states only the progress. Saying the refund out loud belongs with the balance read-out this screen already owes (see [How many runs a user gets](#how-many-runs-a-user-gets)), not before it.

### How a job fails

Two things can end a run in `failed`:

- **The backend says so.** A pipeline error, or a render that ran past its timeout. **The stored reason is worded by the app from the failure's classification code**: `GET /edit-jobs/{id}` and the progress socket carry an `errorCode` — `TIMEOUT | SOURCE_UNAVAILABLE | QUEUE_FAILED | INTERNAL`, append-only, an unknown code reads as `INTERNAL` — and the code→copy table lives in `features/compose-movie`'s `lib/edit-failure-copy.ts`, one table because the reason is stored (`Movie.error`) and every failure surface reads the stored string. The server's `errorMessage` is, by its own contract, a diagnostic rather than user copy: it is kept on the movie as `Movie.errorDetail` and shown only as a demoted secondary line under the worded reason in the movie screen's footer (the grid tile shows the worded reason alone). This closes the "messages are not user-facing quality yet" caveat this document carried — the app no longer shows them as the reason. Verification status (2026-08-13): the code→copy mapping and both transports (poll and socket) are unit-tested; the footer's rendering of the worded reason with the demoted diagnostic under it is verified on a device by briefly forcing the failed branch (a real pipeline failure cannot be provoked against a healthy backend, and the worker timeout is ten minutes); a real `errorCode` arriving end-to-end has not been observed on a device yet.
- **The material went.** The user deletes the last original a running job was built from. Deleting a snap strips it from every movie that references it ([Snap library](snaps.md#deleting-an-original)), and a job with no cuts left can only produce nothing — so the app fails it locally rather than waiting for a render of an empty list. Verified on a device (2026-08-10): deleting the last original mid-run failed the movie locally, without waiting for the backend.

`useGenerationRunner` checks the material on every pass rather than only at the end — waiting out a remote render to be told the material is gone is a pointless wait — and refuses to judge it at all before the snap store has rehydrated, when every cut would look deleted. A retry is offered only when the movie still has cuts; with none, the copy sends the user to the cut list instead of to a retry that would fail again immediately.

A third case ends a run that was never really there: a job the backend has never heard of (`404`). That is how a movie left `generating` by a build older than 2026-08-07 gets out — its job id was a local string and no run ever existed for it — and it fails with 이 무비의 편집 작업을 서버에서 찾을 수 없어요. A transport failure is **not** treated this way: the movie stays `generating` and the next poll asks again, because a flaky network must not be able to throw away a run that is still going.

## Watching it

**A finished movie plays the file its run produced**: when `render.uri` holds one, watch mode plays that single video — the backend's actual edit, with its cuts, music, and subtitles — through `RenderPlayer`. A finished movie *without* a file (mock mode, renders from before the backend composited anything) still plays its cuts back to back, each inside its trim window; and the cut player is also what previews a `draft`, so a trim can be judged before the run is started.

**The stage plays the stored cut list — which is always current, because edits commit as they land** — there is no staged copy and no save button. The point of keeping the stage on screen is that a reorder, a trim, or a removal is *seen*: the stage holds its place in the edited list and pauses on the new frame the moment the edit lands. What the stage shows is exactly what a generation is built from.

**Watch mode plays what was made, not what is being edited.** A `ready` movie's live list can lawfully drift after the run, but what the user came to watch is the finished movie. With a file, that is the rendered file as one video (`RenderPlayer`): the address is resolved **fresh on every visit** — the backend's links are time-limited signed URLs to a private bucket, so `useRenderSource` (`features/compose-movie`) re-asks `GET /videos/{id}` by the render's stored result id (`render.videoId`) and plays the answer, falling back to the stored `render.uri` only when the ask fails or an old render kept no id. The player itself is a single `expo-video` player that opens paused on the first frame, toggles on the stage tap, offers a replay at the end, shows 불러오는 중 while the stream opens, and states its error face when the remote file cannot be played — a URL can rot and the network can be gone, which local cuts never had to say. Because the file outlives the snaps it was made from, it keeps playing even when every original is deleted. **Verified on a real device against a real server (2026-08-10):** the backend now presigns the GET URL at `GET /videos/{id}` response time, the fresh-address ask fires on watch-mode entry, and the rendered file plays — in 9:16 portrait (1080×1920), confirming the `outputProfile` the app sends. Without a file, watch mode resolves `render.snapRefs` rather than the working list (`model/watch-cuts.ts`), so an edited finished movie still *watches* as what was made; a render stored before the snapshot field existed falls back to the live list, as does a snapshot emptied by snap deletions (`removeSnapsEverywhere` strips the snapshot too). That fallback runs the same `CutPlayer` as the studio, inheriting sequential trim-aware playback, the per-cut progress segments, and the stage-tap play/pause. Either way watch mode drops everything around the player — the transport, the strip, the chips, and the footer's generate slot.

## Composing and fixing it

Available whenever no job owns the movie — the same controls settle a `draft` before its first run and fix a `ready` or `failed` result after one. Only a `generating` movie shows them as a read-out.

### The three styles are the backend's presets

The app follows the backend rather than naming looks of its own. An earlier four-look catalog (`calm`, `upbeat`, `plain`, `emotional`) was invented before the editing backend was known; the backend implements **three** presets named for occasions, two of the four had no counterpart at all, and no mapping could have described what a run would produce. The presets:

| `MovieStyle` | Card | What the pipeline does | Sent as |
| --- | --- | --- | --- |
| `daily` (default) | 일상 · 원본 색감 · 컷 편집 | no color filter, hard cuts | `일상` |
| `emotional` | 감성 · 차분한 색감 · 부드러운 전환 | desaturates, crossfades between cuts | `감성` |
| `travel` | 여행 · 밝은 색감 · 빠른 컷 전환 | brightens, short hard cuts | `여행` |

The identifiers stay English while the backend's preset names are Korean, and the translation is the API boundary's job — a preset renamed on the server moves one mapping instead of every identifier, key, and test in the app. `daily` is the default because it is also the preset the backend falls back to for a name it does not recognize, so the two agree.

Movies stored by an older build still name a retired look, and the local store has no migration step, so every reader goes through `movieStyleOrDefault`: `emotional` keeps its movies and the other three read as `daily`. Nothing guesses at a closer match — the old looks and the new presets classify by different things, and a guess would silently restyle a movie the user had already settled. Sending an unmapped name would be a `400` from `POST /edit-jobs`.

## 순서 고정 — who arranges the cuts

`Movie.arranger` records who owns the cut order, and it is the one thing generation is allowed to change.

| Value | What it means | How a movie gets it |
| --- | --- | --- |
| `user` | The stored order is final. Generation must not touch it. | Every movie started from snap picks. Also any AI-arranged movie the moment the user reorders it. |
| `ai` | Generation may re-arrange the cuts before it runs. | A movie made from a template ([Movie templates](movie-templates.md)). |

The switch is offered rather than required: **rearranging a cut by hand already turns the lock on**, because that is what moving it meant. The user never has to find the switch first, and a later re-arrangement cannot undo what they just did. Trimming a cut is not rearranging one and costs nothing. The switch exists so the order can be handed back.

`arranger` is optional on the stored movie — movies written before the field existed have none, and the local store has no migration step — so every reader goes through `isAiArranged`, which reads a missing value as `user`. Getting that backwards would let generation rewrite a cut list someone arranged by hand.

| Capability | Status | Actual behavior |
| --- | --- | --- |
| Lock on manual reorder | `Functional` | `saveCuts` compares the committed snap sequence with the stored one and writes `arranger: 'user'` when they differ. |
| AI arrangement at generation | `Partial` | For an `ai` movie, `startGeneration` re-sorts the cut list by the snaps' capture times and stores it before starting the job. **That is the whole of "AI arranges" today** — chronological is a real arrangement and the one template matching produces, but no model looks at the pictures. It is visible when a snap is appended to an AI-arranged movie: the new cut drops into its place in the day instead of sitting at the end. Because a draft is reviewed before the run, the 순서 고정 row states that an `ai` order will be re-arranged at run time — and rearranging by hand locks it. A cut whose original is gone stops the re-sort entirely rather than being dropped. |
| Hand it back | `Functional` | Turning the switch off writes `arranger: 'ai'` again, on any movie no job owns. |

## Rules and where they live

`features/compose-movie` owns every rule about a movie's cuts, settings, arrangement, and generation, so none of them depends on a screen remembering a `disabled` prop:

| Rule | Refusal |
| --- | --- |
| No cut or style edits while a job owns the movie (`generating`) | `saveCuts` → `frozen`, `saveStyle` → `false` |
| At least one cut | `saveCuts` → `empty` |
| At most ten cuts (`MovieSnapLimit`) | `saveCuts` / `appendSnaps` → `full` |
| No second job while one is running | `startGeneration` → `frozen` |
| Nothing to generate from | `startGeneration` → `empty` |
| Every cut must be on the backend before a run | `startGeneration` → `uploading` |
| The backend may refuse the run (ownership, `ready`, plan cap) | `startGeneration` → `rejected`, carrying the server's message |
| The request may not get there at all | `startGeneration` → `unreachable` |
| A run leaves `generating` only on the server's word | `cancelGeneration` → `settled` (already ended) / `unreachable` (still going) |

`canEditMovie` is exported so the screen asks the same question the commit answers, rather than deciding for itself which statuses are editable. A refused edit changes nothing — the stored list stays as it was and the reason is shown. `appendSnaps` refuses a batch whole rather than adding as many as fit; snaps the movie already holds are skipped rather than duplicated.

The rules about what a *trim* may be belong to the entity, not the feature: `withTrim` snaps the window, holds it inside the snap, keeps it above `MinCutSec`, and drops a full-width window. Every screen that prints a length uses the same `cutDurationSec` / `cutsDurationSec`, so no two surfaces can disagree about how long a movie is.

- `src/features/compose-movie` owns starting a movie from picked snaps or a template, committing cut lists and style settings, the arrangement rules, starting generation, and `MovieGenerationGate` — the app-wide runner that follows a run to its result or to a failure (`model/use-generation-runner.ts`) and, when asked, announces the end (`lib/announce-job-end.ts`). Its `api/` segment is the whole of the backend contract for generation: `create-edit-job.ts` (which also owns the style→preset translation, the seconds→milliseconds conversion of each cut's trim window, and the output profile the app asks for), `get-edit-job.ts`, `cancel-edit-job.ts` (stopping a run), `get-edited-video.ts` (with its query factory `edited-video.queries.ts`), `download-render-thumbnail.ts` (the render's cover, brought local), and `subscribe-edit-progress.ts`. `lib/edit-failure-copy.ts` is the one table that words a failure from its classification code — in the feature rather than on a screen, because the reason is stored and read by surfaces in layers that may not import each other. It also owns `model/use-render-source.ts` — the watch-time resolution of a render to a *fresh* file address, because the backend's links expire and the stored `render.uri` is only a fallback.
- `src/shared/api/socket.ts` is the WebSocket transport — origin, JWT handshake header, JSON decoding — alongside `client.ts`'s `apiRequest`, with `auth-header.ts` shared between them. It is a plain string path rather than a typed one because **WebSocket endpoints are not in the route registry**; the message contract is `editProgressEventSchema` in the shared contract package (described for readers in the monorepo's [root API document](../../../../docs/api-spec.md)), which is why the frames are validated with Zod at the feature boundary.
- `src/_app/providers/movie-generation-bridge.tsx` mounts the gate with the user's 무비 완성 알림 preference. The preference belongs to `features/notification-settings` and features must not import each other, so the app layer composes them — the same shape as `GeofenceGate`.
- `src/features/rename-movie` owns the rename form (`RenameMovieForm`), the sheet that wraps it (`RenameMovieSheet`), and its schema. This screen is its only consumer: the movie tab's selection mode deliberately does not offer rename, because an appearing-and-vanishing single-selection action read as inconsistent. It stays a feature rather than page-local code because the movie screen's rename is slated to grow.
- `src/features/share-movie` owns the export decision (`useShareMovie`) — what may be handed to the share sheet, why a movie is blocked, and the download-to-cache step that makes a remote render shareable (`api/download-render-file.ts`). A feature because this screen's footer and the movie tab's selection bar offer the same act. It does not resolve the render's address itself: the page passes the same `RenderSource` the stage plays, so the share and the playback can never point at different files.
- `src/entities/movie` owns the store and its write actions (including `useSetMovieArranger`, the five job actions — begin, advance, finish, fail, cancel — and `useSetRenderThumbnail`), the default-title rule, the style and BGM catalogs, the generation step table and its progress rule, the trim rules, the arrangement predicates (`lib/movie-arrangement.ts`), and the render-source predicates — the same-composition comparison and the drift question the screen asks (`lib/movie-render.ts`).
- `src/widgets/movie-shelf` supplies the row and tile that open the screen, and the summaries behind them.
- `src/pages/add-snaps` owns the picker screen behind the strip's `+` tile (`/movie/[id]/add-snaps`): it draws `widgets/snap-grid`, refuses what the movie has no room for, appends through `compose-movie`, and returns to the movie. It states its own "무비를 찾을 수 없어요 / 지금은 컷을 더 넣을 수 없어요" when the movie disappears or a job takes it while the picker is open.
- `src/widgets/snap-grid` supplies the day-grouped grid, the pick-order and cap rules, and the selection bar the picker shares with the Snap tab ([Snap library](snaps.md#ownership)).
- `src/shared/lib/sharing` is the `expo-sharing` adapter (`canShareFiles`, `shareFile`) with a `.web.ts` stub — transport only, no product decisions.
- `src/app/movie/[id]/index.tsx` and `src/app/movie/[id]/add-snaps.tsx` are the route adapters; both screens are registered in `src/_app/routes/root-layout.tsx`.

## Known limitations

- **Renders from before 2026-08-10 cannot be re-resolved.** `render.videoId` is what `useRenderSource` re-asks the backend by, and renders stored before the field existed have none — those movies fall back to their stored `render.uri`, which is a link that has since stopped working (the backend now presigns, so old unsigned links answer AccessDenied). There is no backfill: the result id is not recoverable from the stored URL (its path carries the *job* id). Regenerating the movie once is the recovery.
- **The studio's preview is the raw cuts, not the coming render.** Watch mode plays the finished file now, but the studio stage still previews the editable cut list — by design (it is what a change is judged against) — and that preview carries none of what the run will add: no music, no subtitles, no style grading, no `fitMode` background. The stage says *what it is* — a 미리보기 tag in its corner, opposite the player's own 컷 n/N — but not what it is missing: naming the four absent things would be the screen explaining itself, and the list would go stale as the pipeline grows. The tag is the honest floor, not the full disclosure this owes before reaching anyone outside the team.
- **The music cannot be chosen, and the title does not travel.** The pipeline picks a track from the style preset and takes no track id, so the app offers no track picker at all; the movie's name never reaches the renderer either. `Movie.bgm` is stored and unread until `GET /bgms` and a track field on `POST /edit-jobs` exist.
- No movie has any versions and a rerun replaces the previous file. The backend keeps every result row it has ever produced; the app points at the newest and never asks about the rest.
- Regeneration keeps no history. The previous render is dropped when the new job starts, so there is no way back to the version the user just replaced. The one thing that survives a run is the *current* render's source cut list (`render.snapRefs`), which is what 완성 당시 구성으로 되돌리기 restores — the composition, not the render.
- Deletion from this screen exists only in watch mode's ⋯ sheet: a `draft` or `failed` movie recognized as wrong while it is open still has to be removed from the movie tab's grid (selection mode — see [Studio and movies](studio.md)).
- A dropped socket is covered by a 20-second poll, not by reconnection: the socket is opened once per run and, if it dies, progress stops moving until a poll or a foreground return catches up. The run itself is unaffected.
- AI arrangement is capture-time order, not a model's judgement.
- Reordering is button-based, not drag-based, and trim is set on a tenth-second grid.
- The undo/redo history lives in the screen: it is dropped on leaving, and when the cut list changes from outside (a snap deleted, snaps appended). Undoing a reorder restores the order but not `arranger` — a hand that moved a cut keeps the lock (순서 고정) even after stepping the move back. The render-source restore is the only edit recovery that outlives the visit, and it only reaches back to the last render.
- Scrubbing seeks on release, not live: the stage holds its frame while the finger drags the strip and seeks only when the scroll rests, so there is no frame-by-frame preview during the drag itself.
- Each cut plays its own recorded sound and no track is mixed.
- A very short snap gets a very narrow clip, because the strip is honest about time and a hold can be released after a quarter second. Nothing widens it to a comfortable tap target, since a minimum width would put the ruler off the cuts.
- 무비 공유 is disabled on a movie without a rendered file (mock mode, or a render made before the backend composited anything): there is nothing to export but the user's own originals.
- The movie itself is still local. Only the *run* is remote: the cut list, order, trim, style, title, and render pointer live in the on-device store, and `POST /edit-jobs` is a fire-and-read job queue, not a place a movie is stored. So a movie does not follow the user to another device, and reinstalling loses every one of them while their rendered files sit on the server unreferenced (concept §9 keeps `PATCH /movies/:id` as the contract for that).
