## 1. 왜 다시 기획했나

이전 기획은 "필름을 찍고 → 하루가 끝나면 현상한다"는 은유 위에 서 있었습니다. 은유가 제품 규칙까지 지배하면서 다음 제약이 생겼습니다.

- **하루 1롤 강제** — 여러 날에 걸친 영상, 주제별 영상을 만들 수 없다.
- **미현상 블러** — 사용자가 자기가 방금 찍은 영상을 못 본다. 은유를 위해 기능을 뺐다.
- **지연 현상** — 만들고 싶을 때 못 만든다. 하루가 끝나야 한다.
- **AI가 안 보인다** — "현상"이라는 의식 뒤에 숨어서, 이게 AI 제품인지 필름 감성 아카이브 앱인지 구분되지 않는다.

원래 의도는 **AI 기반 숏폼 브이로그 제작 앱**이었고, 은유가 그 의도를 덮었습니다. 은유를 걷어냅니다.

### 버리는 것

`하루 1롤` · `현상(develop) 의식` · `미현상 블러(negative frame)` · `필름 그레인·퍼포레이션·edge print` · `12컷 목표` · `보관함(archive)이라는 탭 이름` · `지오펜스 기반 자동 수집`

### 남기는 것

3–5초 짧은 촬영 · 원본은 불변이고 조합은 별도(N:M) · 다크 팔레트 · 촬영 리마인더 · 푸시/위치 알림 인프라 · 인증/설정 전반

> 다크 팔레트는 남깁니다. 영상 앱에 어두운 배경은 은유가 아니라 기능입니다. 다만 앰버 safelight·필름 질감처럼 "필름임을 주장하는" 장식은 뺍니다.

## 3. 선택한 방향 — 스튜디오(작업대형)

홈은 **내 작업대**입니다. 담아둔 재료와 진행 중인 무비가 항상 여기 놓여 있고, 앱을 다시 열면 하던 작업을 이어서 합니다.

**전제:** 사용자는 결과물을 자기 손으로 통제하고 싶어 한다. AI는 주인공이 아니라 마지막에 붙는 강력한 도구다.

### 결정 기록

2026-07-28에 홈의 성격만 달리한 세 방향을 프로토타입으로 만들어 비교했습니다 — `오늘(AI 제안형)` / `스튜디오(작업대형)` / `레시피(의도 우선형)`. 비교 문서의 원래 추천은 레시피였고, **채택된 것은 스튜디오입니다.**

추천을 뒤집은 근거는 비교 문서 자신이 단 단서였습니다: 레시피 방향은 **레시피 카탈로그를 상시 운영해야** 성립하고, 그걸 감당할 사람이 없다면 스튜디오로 시작하는 편이 정직합니다. 스튜디오는 운영 비용이 0에 가깝고, 백엔드도 합성 잡 하나면 출발할 수 있습니다.

나머지 두 방향은 폐기가 아니라 **뒤 단계로 밀어둔 것**입니다(§10 참조). 세 방향은 배타적이지 않고 단계로 놓을 수 있습니다.

### 감수하는 것

- 첫 무비까지 탭 6–8회. 제안형(2회)·레시피형(3–4회)보다 길고, 이탈 지점이 많습니다.
- AI가 "도구"로 밀려나 제품 차별점이 흐려질 수 있습니다. 차별화는 **재료 관리 경험**이 집니다.

## 5. 정보 구조

```text
탭바:  [스튜디오] [스냅] (●촬영) [무비] [나]

스튜디오  새 무비 진입 + 템플릿 + 무비 보드. 앱을 다시 열면 여기서 이어서 한다.
스냅      내가 찍은 3–5초 원본. 날짜별 그리드. 즉시 재생 가능(블러 없음).
          우상단 [선택] → 다중 선택(최대 10) → [이 스냅으로 새 무비].
무비      완성작 + 초안. 2열 그리드. 열면 재생 / 컷 수정 / 스타일 변경 / 재생성 / 공유.
          모든 상태가 같은 화면(`/movie/[id]`)으로 열린다 — 재생과 수정이 같은 방문이다.
나        프로필 · 통계 · 리마인더 · 알림 · 연결된 계정 · 계정 관리 (기존 설정 그대로).
```

### 재료를 모으는 그릇 — 초안 무비 (구 담기 트레이)

원래는 별도의 "담기 트레이"(장바구니)가 §5의 핵심 발명이었으나, **2026-08-12에 제거하고 초안(draft) 무비가 그 역할을 이어받았습니다.** 스냅 탭에서 고른 스냅은 확정 즉시 초안 무비가 되고, 그 무비 화면이 열립니다. 트레이가 하던 일은 초안이 전부 합니다:

- 여러 날에 걸쳐 재료를 모을 수 있습니다 — 초안은 앱을 껐다 켜도 유지되고, 무비 화면의 `스냅 더 넣기`로 언제든 채울 수 있습니다. "하루 1롤"이 풀리는 지점은 그대로입니다.
- 상한은 **10개**이며, 이것이 제품의 유일한 하드 제약입니다(무비 1편 = 스냅 ≤10).
- 초안은 여러 개일 수 있습니다 — 두 무비 분량을 동시에 모으는 일이 트레이 시절에는 불가능했고, 지금은 자연스럽습니다.

트레이를 제거한 이유: 같은 "바구니" 결정에 트레이와 초안이라는 두 메커니즘이 공존했고, 트레이 경유는 `담기 → 스튜디오 → 이 스냅으로 새 무비`라는 화면 전환 2회·결정 1회를 추가로 요구했습니다.

### 무비를 만드는 경로

경로는 **두 갈래**입니다. 둘은 서로를 소모하지 않습니다.

1. **손으로 모으기** — 스냅 탭에서 다중 선택(≤10) → `이 스냅으로 새 무비` → 초안 무비 화면 (필요하면 나중에 `스냅 더 넣기`로 이어서 수집)
2. **템플릿으로 시작** — 스튜디오의 템플릿 카드 → 앱이 같은 외출로 보이는 스냅을 슬롯에 배치 → 빈 슬롯은 `지금 찍기` → `이대로 만들기` (바로 생성 시작)

### 슬롯 템플릿 (2026-08-03 추가)

레시피 방향(§3에서 미룬 것)에서 **운영 비용이 0인 부분만** 가져왔습니다. 템플릿 4종이 빌드에 상수로 들어 있고, 서버도 시즌 콘텐츠도 없습니다.

- 슬롯 이름(`출발` `골목` `가게` `한 컷` `풍경` `돌아오는 길`)은 **사람에게 주는 촬영 지시**입니다. 앱은 사진을 보지 못합니다.
- 자동 매칭이 보는 것은 **촬영 시각과 좌표뿐**입니다. 3시간·2km 안에서 이어지는 스냅을 한 번의 외출로 묶고, 시간 순서대로 슬롯에 깝니다.
- 슬롯마다 표시되는 `같은 외출 확신 NN%`는 "이 슬롯과 일치하는 정도"가 아니라 **"같은 외출에 속할 확률"**입니다. 근거가 시간·거리뿐이므로 그 이상은 주장하지 않습니다.
- 빈 슬롯의 `지금 찍기`가 이 방향의 진짜 무기입니다 — 라이브러리가 촬영을 만들어냅니다.

## 6. 무비 화면 — 만들고, 보고, 고친다

**살아 있는 결정: 무비는 상태가 무엇이든 한 화면(`/movie/[id]`)에서 열린다.** 재생 화면을 따로 두지 않는 이유는 간단합니다 — 완성본을 보는 것과 고치는 것은 같은 방문이고, 라우트를 둘로 쪼개면 같은 컷 리스트를 고칠 수 있는 곳이 둘이 됩니다.

**폐기된 결정: 3단계 위저드(① 조립 → ② 스타일 → ③ 생성), 그리고 그 반작용으로 나온 "수정은 생성 이후에만".** 위저드는 2026-08-03에, 생성-이후-수정 규칙은 2026-08-05에 각각 폐기됐습니다. 지금은 초안이 편집 가능하고, 생성이 실제 유료 원격 작업이 된 뒤로는 **구성을 먼저 확정하고 실행하는 것**이 규칙입니다.

상태별로 화면에 무엇이 있는지는 이 문서가 아니라 [`docs/features/movie.md`](../../features/movie.md)가 소유합니다. 이 자리에 있던 표는 2026-08-03 시점의 안이라 `draft`·`generating` 행이 지금과 다릅니다.

### 순서 고정 (2026-08-03 추가)

컷 순서의 주인을 무비가 기억합니다(`Movie.arranger`).

- 스냅 선택으로 만든 무비는 항상 `user`입니다. 생성이 순서를 건드리지 않습니다.
- 템플릿 매칭으로 만든 무비는 `ai`입니다. 다시 만들 때 촬영 시각 순으로 재배치될 수 있습니다.
- **사용자가 손으로 순서를 바꾸면 그 순간 `user`로 바뀝니다.** 스위치를 먼저 찾아 켤 필요가 없습니다 — 옮겼다는 것이 곧 고정하겠다는 뜻이기 때문입니다. 스위치는 순서를 다시 AI에게 넘겨주기 위해 존재합니다.
- 트림은 재배치가 아니므로 고정을 유발하지 않습니다.

지금 "AI가 배치한다"의 실체는 **촬영 시각 순 정렬**입니다. 진짜 배치는 백엔드가 맡습니다(§9).

무비 상태는 `draft`(초안) → `generating`(생성 중) → `ready`(완성)이며, 실패 시 `failed`입니다. 스튜디오 보드는 `ready`가 아닌 무비를 진행률과 함께 보여줍니다.

## 7. 콜드 스타트

스냅이 0개여도 홈이 비지 않습니다. 첫 블록의 `새 무비 · 스냅 고르기` 줄이 스냅 선택 모드로 바로 데려가고, 무비가 없으면 보드 블록 자체가 그려지지 않습니다.

콜드 스타트를 **설명문으로** 채우던 초기 방침은 2026-08-10에 접었습니다. "스냅 탭에서 쓸 만한 장면을 골라 담기를 누르면 여기 모여요" 같은 문장은 바로 아래 버튼이 이미 하는 말이었고, 앱 전체에 같은 패턴이 반복되면서 화면이 사용자가 아니라 개발자에게 설명하는 톤이 됐습니다. 빈 화면은 이제 제목 한 줄과 다음 행동 버튼으로만 이루어집니다(규칙: `docs/features/app-shell-and-navigation.md`).

촬영 유도는 이 방향의 약점입니다(§3). 촬영 리마인더(기존 `나` 탭 설정)가 당분간 그 역할을 대신합니다.

## 9. 백엔드에 필요한 계약 (초안)

```text
POST  /snaps                  스냅 업로드 (video + 메타: 촬영시각, 길이, 위치, 해상도)
GET   /snaps?cursor=          내 스냅 목록

POST  /movies                 { snapIds[] (≤10), order[], trims[], style, bgm, ratio }
                              → { movieId, jobId, status: "generating" }
GET   /movies/:id             → { status: draft|generating|ready|failed, renderedUrl?, error? }
PATCH /movies/:id             초안 저장 (순서/트림/스타일) — 재생성 없이
POST  /movies/:id/regenerate  같은 스냅 세트로 다시 합성 (seed/style 변경)
GET   /styles, GET /bgms      스타일·BGM 카탈로그
```

```text
GET   /templates              슬롯 템플릿 카탈로그 (지금은 클라이언트 상수)
POST  /templates/:id/match    슬롯별 후보 스냅 + confidence + 근거 문구
```

두 가지가 반드시 필요합니다.

1. **순서·트림 보존 모드.** 합성 잡은 `arranger`를 그대로 지켜야 합니다 — `user`면 사용자가 정한 순서와 트림을 절대 건드리지 않고, `ai`일 때만 재배치가 허용됩니다. 이 플래그가 무시되면 편집 기능 자체가 무의미해집니다.
2. **초안의 서버 저장.** `PATCH /movies/:id`로 순서·트림·스타일·`arranger`를 서버에 유지해야 기기를 바꿔도 작업이 이어집니다. **2026-08-03 기준 이 항목은 계약만 확정하고 구현은 보류했습니다** — 스냅/무비 백엔드가 아직 없고, 원본 영상이 로컬에만 있어 초안만 올려도 기기 이전이 성립하지 않기 때문입니다.

알림도 하나 필요합니다: **무비 완성 푸시.** 합성이 40초씩 걸리면 사용자는 앱을 나갑니다. 기존 FCM 인프라를 그대로 씁니다.

## 11. 아직 안 정한 것

- **공유/소셜을 넣을 것인가.** 지금은 "내보내기 + 외부 앱 공유"만 가정했습니다. 앱 안에 피드가 생기면 탭 구조가 다시 바뀝니다.
- **재생성 버전 보관.** 다시 만들면 이전 완성본이 사라집니다. "버전은 없다"가 현재 규칙(`docs/features/movie.md`)이지만, 되돌릴 수 있어야 하는지는 여전히 미정입니다.
- **무비 길이 상한.** 스냅 10개 × 5초 = 최대 50초. 숏폼 기준으로는 적당하지만, 트림으로 줄일지 목표 길이를 먼저 정할지 미정.
- **무비의 서버 보관.** 스냅 원본은 2026-08-07부터 백그라운드로 업로드됩니다(결정 완료). 남은 질문은 무비 자체 — 컷 리스트·설정·렌더 포인터가 아직 기기에만 있어 재설치하면 사라집니다.
