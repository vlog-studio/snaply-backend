# 문서 컨벤션 — 위치·이름·형식

**작성일**: 2026-09-03 (AGENTS.md §문서 컨벤션에서 분리)
**상태**: 현행 — 문서의 위치·이름·형식 규칙의 원천
**관련 문서**: [constitution.md](constitution.md) 제7조 · [AGENTS.md](../AGENTS.md) §문서 갱신 의무 · [README.md](../README.md) §어디를 봐야 하는가

문서를 **새로 만들거나 옮기기 전에** 이 문서를 읽는다.

## 어디에 두는가 — 문서의 수명으로 결정한다

| 위치 | 담는 것 | 수명 |
|---|---|---|
| 저장소 루트 | 진입점 4개(`README` · `ONBOARDING` · `AGENTS` · `CLAUDE`)만. **늘리지 않는다** | 상시 |
| `docs/` 직하 | 계속 갱신되는 현행 문서 (계약·상태·규칙·절차). 최상위 원칙은 [`constitution.md`](constitution.md) | 상시 |
| `docs/specs/` | 제품 요구사항(무엇을·왜) — 요구 ID + 구현 상태 라벨. 동작 계약을 바꾸는 작업은 해당 spec 갱신이 먼저다 | 상시 |
| `docs/decisions/` | 한 시점에 내린 정책·설계 결정. 배경·기각한 대안 포함. 결정 전의 **결정 요청**(선택지·결과·권장)도 상태 `미결`로 여기에 두고, 결정되면 같은 파일을 갱신한다. 어느 문서가 미결인지는 [decisions/README.md](decisions/README.md) | 결정 시점 고정 |
| `docs/plans/` | 착수 전 구현 계획. **제안이며 현행 사실이 아니다.** 목록과 어디까지 구현됐는지는 [plans/README.md](plans/README.md) | 구현 시작까지 |
| `docs/meetings/` | 회의 안건과 결과 | 회의 단위 |
| `docs/archive/` | 수명이 끝난 문서 | 보관 |

`apps/mobile/docs/`는 모바일 에이전트 문서 체계이므로 위 `docs/` 배치 규칙의 예외다. 사용자 동작과
구현 상태는 `apps/mobile/docs/features/`, 모바일 아키텍처·규칙·절차는 해당 하위 디렉터리에 둔다.

판단 기준: **"이 문서를 계속 고칠 것인가?"** 계속 고친다면 `docs/` 직하,
한 시점의 기록으로 굳는다면 `decisions/`·`plans/`·`meetings/`.
어느 것도 아니게 되면 `archive/`로 옮기면서 상단에 상태 배너를 붙인다(배너 외의 본문은 고치지
않는다 — 단, 이동으로 깨지는 상대 링크 경로의 보정은 허용하고 배너에 그 사실을 적는다).

## 이름

- **kebab-case 소문자 + `.md`** — `api-spec.md`, `commit-guidelines.md`, `snap-source-of-truth.md`.
  저장소 코드 컨벤션(파일명 kebab-case)과 같은 규칙이다.
- 예외는 루트 진입점 4개, 각 워크스페이스 루트의 진입점(`apps/mobile/AGENTS.md`·`CLAUDE.md`·`README.md` 등),
  디렉터리 인덱스 `README.md`뿐. 그 밖에 대문자·`UPPER_SNAKE`를 쓰지 않는다.
- 이름은 **주제**로 짓는다. `notes.md`·`temp.md`·`new-doc.md`처럼 내용을 알 수 없는 이름을 쓰지 않는다.
- `docs/meetings/`는 **날짜 접두사**를 쓴다: `YYYY-MM-DD-<주제>.md` (예: `2026-08-14-backend-review.md`).
  아직 날짜가 안 잡힌 예정 회의는 `next-agenda.md`로 두고, 날짜가 정해지면 위 형식으로 rename한다.
- 디렉터리 안내가 필요하면 그 디렉터리의 `README.md`에 쓴다(예: [`archive/README.md`](archive/README.md)).

## 새 문서를 만들기 전에

기존 문서에 절이 하나 늘어나는 것으로 끝나는 내용이면 **새 파일을 만들지 않는다.**
새 문서에는 아래 [헤더](#헤더)를 붙인다.

## 헤더

`docs/` 아래 문서는 제목 바로 아래에 볼드 라벨 줄을 이 순서로 둔다. 디렉터리 인덱스 `README.md`와
`archive/`(상단 보관 배너만 붙인다), 그리고 자체 형식을 따르는 `apps/mobile/docs/`(영어 에이전트 문서 —
[apps/mobile/AGENTS.md](../apps/mobile/AGENTS.md))는 예외다. 라벨은 아래 다섯 개만 쓴다 — `관련`·`범위`·
`후속 작업의 원천`처럼 다른 이름을 새로 만들지 않는다.

| 라벨 | 필수 | 내용 |
|---|---|---|
| `**작성일**` | 필수 | 최초 작성일 `YYYY-MM-DD`. 결정일·이동일이 다르면 괄호로 한 번 덧붙인다 — `2026-09-05 (2026-09-09 결정)` |
| `**상태**` | 필수 | 아래 상태어로 시작하는 **한 줄**(길어도 두 줄) |
| `**원천**` | 선택 | 이 문서가 무엇의 원천인지. 비슷해 보이지만 원천이 아닌 것이 있으면 그 원천을 함께 링크한다 |
| `**출처**` | 선택 | 이 문서를 낳은 회의·백로그 항목(결정·회의 문서) |
| `**관련 문서**` | 필수 | 링크를 ` · `로 구분 |

| 위치 | 상태어 |
|---|---|
| 루트·`docs/` 직하·`specs/` | `현행` (확정 전 원칙 문서는 `초안`) |
| `decisions/` | `결정` · `결정(잠정)` · `미결` · `과거 결정`(일부 또는 전부 대체) |
| `plans/` | `제안` |
| `meetings/` | `회의 기록` |

- **상태 줄에는 구현 진척·검증 내역을 쓰지 않는다** — 구현이 진행될 때마다 낡는다. 요구별 구현 상태의
  원천은 [specs/](specs/README.md)의 라벨이고, 결정별 구현 요약은 [decisions/README.md](decisions/README.md)의
  `구현` 열, 남은 일은 [backlog.md](backlog.md), 끝난 일은 [progress.md](progress.md)다.
- 작성 뒤에 생긴 정정·대체·후속 결정은 라벨을 늘리지 않고 헤더 바로 아래 인용 배너로 붙인다 —
  `> **정정**(2026-09-02): …` · `> **대체**(2026-09-09): … → [새 문서](…)` · `> **후속 결정**(2026-08-13): …`.
  인용 블록(`>`)은 이 배너에만 쓴다.

## 본문 — 에이전트가 찾고 고치기 쉽게

- **사실은 원천에 한 번만 쓰고 나머지는 링크한다**([constitution.md](constitution.md) 제2조). 어느 문서가
  원천인지는 [README.md](../README.md) §어디를 봐야 하는가.
- **미결 작업은 [backlog.md](backlog.md)에만 둔다.** 결정·계획·스펙·진행 문서에 미결 체크리스트나
  "남은 일" 목록을 만들지 않고 백로그 ID(`A-4`)로 가리킨다.
- **ID와 링크로 가리킨다** — 요구는 스펙 ID(`SNAP-12`), 미결 작업은 백로그 ID(`A-4`), 다른 문서의 내용은
  절 링크(`file.md#절-제목`). "위 표"·"앞서 말한 것" 같은 지시어로 다른 절을 가리키지 않는다.
- **날짜는 절대 날짜**(`2026-10-07`)로 쓴다. "어제"·"최근"·"다음 주"는 쓰지 않는다.
- **코드는 경로와 심볼로 가리킨다.** 경로는 저장소 루트 기준(모바일 문서는 `apps/mobile` 기준)으로 쓰고,
  **줄 번호(`editor.py:157`, `#L34-L38`)는 쓰지 않는다** — 코드가 바뀌면 조용히 엉뚱한 줄을 가리킨다.
  위치가 필요하면 함수·상수 이름을 함께 적는다.
- **명령은 실행할 수 있는 형태 그대로** 쓴다 — 저장소 루트 기준, 실제로 있는 `npm run <script>`만.
- [progress.md](progress.md)의 항목 제목은 `## YYYY-MM-DD — 제목`, 같은 날 이어지면
  `## YYYY-MM-DD (이어서) — 제목`이다. 날짜로 grep 해서 찾는다.
