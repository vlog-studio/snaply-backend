# Pull Request 작성 지침

이 문서는 Snaply 백엔드 저장소에서 동료 개발자가 변경 목적과 리뷰 포인트를 빠르게
파악할 수 있는 Pull Request를 작성하기 위한 기준이다. 에이전트가 PR을 생성할 때도
같은 기준을 사용한다.

## 1. 기본 원칙

- PR 하나에는 하나의 주된 변경 목적만 담는다.
- 첫 화면에서 변경 이유, 주요 동작, 검증 결과를 파악할 수 있게 작성한다.
- 커밋 목록을 반복하기보다 리뷰어가 알아야 할 동작과 판단을 설명한다.
- 실제 diff에 포함된 내용과 실행한 검증만 기록한다.
- 리뷰가 필요한 부분을 구체적인 질문이나 파일·동작 단위로 제시한다.
- 관련 없는 기능, 리팩터링, 운영 문서는 가능한 한 별도 PR로 분리한다.

## 2. 제목

제목은 [`commit-guidelines.md`](commit-guidelines.md)의 Conventional Commits 형식을
사용하고 PR 전체의 대표 변경을 설명한다.

```text
<type>(<scope>): <영문 요약>
```

예시:

```text
feat(api): add Supabase login to Swagger
fix(api): reject expired billing webhooks
docs: document local development setup
```

제목은 명령형 현재 시제의 간결한 영어로 작성하고 마침표를 붙이지 않는다.

## 3. 본문 순서

동료가 위에서 아래로 읽으면서 상세 수준을 선택할 수 있도록 다음 순서를 권장한다.

1. `요약`: 무엇을 왜 바꿨는지 2~4문장으로 설명한다.
2. `주요 변경`: 리뷰할 수 있는 동작 단위로 나열한다.
3. `동작 조건`: 환경, feature flag, fallback, 호환성 조건을 적는다.
4. `리뷰 포인트`: 보안 경계, 오류 처리, 설계 판단처럼 집중해서 볼 부분을 적는다.
5. `확인 방법`: 재현 가능한 최소 절차를 적는다.
6. `검증`: 자동화 명령과 수동 확인 결과를 구분한다.
7. `참고`: 미검증 항목, 후속 작업, 이슈 링크를 기록한다.

변경 성격상 필요하지 않은 섹션은 생략할 수 있다. 단순 문서 수정에 빈 `동작 조건`이나
`확인 방법` 섹션을 억지로 만들 필요는 없다.

## 4. 권장 템플릿

```markdown
## 요약

<!-- 무엇을 왜 바꿨는지 2~4문장 -->

## 주요 변경

- <!-- 리뷰 가능한 동작 단위 -->

## 동작 조건

- <!-- 환경, 설정, fallback, 호환성 조건 -->

## 리뷰 포인트

1. <!-- 리뷰어가 집중해서 확인할 판단 또는 위험 -->

## 확인 방법

1. <!-- 재현 가능한 최소 절차 -->

## 검증

- [x] `실제로 실행해 통과한 명령`
- [x] 실제로 완료한 수동 확인
- [ ] 실행하지 않았거나 추가 확인이 필요한 항목

## 참고

<!-- 미검증 항목, 후속 작업, 관련 이슈 -->
```

## 5. 검증 작성법

- 명령은 복사할 수 있도록 백틱으로 정확히 기록한다.
- 성공한 자동 검증은 `[x]`, 실행하지 않았거나 실패한 항목은 `[ ]`로 표시한다.
- 테스트가 없는 경우 이를 숨기지 말고 수동 확인 범위와 함께 명시한다.
- 환경 제약으로 실행하지 못한 경우 원인과 리뷰어가 대신 확인할 방법을 적는다.
- UI나 외부 서비스 연동은 자동 검증과 별도로 수동 확인 절차를 제공한다.

예시:

```markdown
## 검증

- [x] `npm run typecheck -w apps/api`
- [x] `npm run lint -w apps/api`
- [ ] Supabase 테스트 계정을 이용한 Swagger 로그인 수동 확인
```

## 6. 리뷰 포인트 작성법

`코드 전반을 확인해 주세요`처럼 넓은 요청은 피한다. 다음처럼 리뷰어가 판단해야 할
경계와 예상 동작을 구체적으로 적는다.

```markdown
## 리뷰 포인트

1. 개발 전용 로그인 경로가 운영 환경에서 충분히 차단되는지
2. 외부 인증 오류를 API 오류로 변환하는 정책이 적절한지
3. 신규 환경변수의 legacy fallback 정책이 안전한지
```

## 7. PR 생성 전 체크리스트

- [ ] 기준 브랜치와 현재 브랜치의 전체 diff를 확인했다.
- [ ] PR 제목이 전체 변경을 대표한다.
- [ ] 관련 없는 변경이 포함되지 않았거나 본문에서 명확히 설명했다.
- [ ] 비밀값, 개인 정보, 디버그 로그가 포함되지 않았다.
- [ ] 관련 타입 검사, 린트, 테스트 또는 빌드를 실행했다.
- [ ] 본문의 검증 체크박스가 실제 실행 결과와 일치한다.
- [ ] 리뷰 포인트가 구체적으로 작성되었다.
- [ ] 별도 요청이 없으면 Draft PR로 생성한다.

## 8. PR 생성 후 보고

PR을 생성한 에이전트는 사용자에게 다음 정보를 간결하게 전달한다.

- PR 링크와 Draft 여부
- 대상 브랜치와 작업 브랜치
- 추가된 마지막 커밋
- 통과한 검증과 실행하지 못한 검증
- 리뷰 전에 사용자가 확인해야 할 사항
