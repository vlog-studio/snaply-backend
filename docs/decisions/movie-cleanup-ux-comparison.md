# D-c 판단 자료 — 선택지별로 화면이 실제로 어떻게 달라지는가

**작성일**: 2026-09-09
**상태**: 판단 자료 — 결정 자체는 [movie-cleanup-after-export.md](movie-cleanup-after-export.md)에 기록한다.
**근거**: 현재 앱 구현([apps/mobile/docs/features/movie.md](../../apps/mobile/docs/features/movie.md) ·

> 결정이 UX 를 크게 바꾼다는 이유로 판단이 미뤄졌다. 이 문서는 **각 안에서 어떤 화면이
> 없어지고 무엇이 새로 필요한지**를 현재 구현 기준으로 적어, 종이 위가 아니라 실제 동선을
> 두고 고를 수 있게 한다.

---

## 0. 지금 화면이 어떻게 생겼나 (사실)

무비는 **화면 하나**(`/movie/[id]`)이고, 그 화면이 두 얼굴을 가진다.

```
스튜디오(초안 편집)              감상 모드(완성본)
├ 스테이지(미리보기)             ├ 스테이지(완성 영상 재생)
├ 트랜스포트 ↺ ↻                 ├ 완성 시각 · 길이 · 스타일
├ 타임라인 스트립(컷 편집)        ├ 공유
├ 스타일 · 세부 칩                └ ⋯ 무비 편집하기 · 이름 바꾸기
└ AI로 생성 시작                        · 공유하기 · 무비 삭제하기
        │                                        │
        └───────── 생성 ──────────▶ 완성 ─────────┘
                   ◀── 무비 편집하기 (같은 화면에서 얼굴만 전환) ──
```

핵심은 **"완성 → 다시 편집 → 다시 만들기"가 이미 구현된 주 동선**이라는 것이다.
문서가 그 설계 의도를 명시하고 있다:

- "Users run a movie, watch it, **fix what came back, and run it again.**"
- 완성본에서 컷을 고치면 "편집한 컷 구성이 있어요" 안내가 서고,
  `이 구성으로 다시 만들기`가 footer 에 붙는다.
- 나가려 할 때 `EditExitSheet` 가 세 갈래(지금 다시 만들기 / 나중에 만들기 / 편집 취소)를 묻는다.
- 이 형태에 도달하기 전 **두 가지 대안을 시도했다가 버렸다**: 생성 전 3단계 마법사, 그리고
  "생성 후에만 편집 허용". 후자는 *사용자가 확정하지 않은 구성에 돈을 내게 만든다*는 이유로 기각됐다.

## 1. 선택지별 화면 차이

### 안 A — 내보내기 완료 시 프로젝트 삭제, 결과물도 진행 후 삭제

**없어지는 것**

| 화면·동선 | 어떻게 되나 |
|---|---|
| ⋯ 시트의 `무비 편집하기` | **제거.** 돌아갈 초안이 없다 |
| 완성본의 `이 구성으로 다시 만들기` | **제거** |
| "편집한 컷 구성이 있어요" 안내 · `구성 확인하고 다시 만들기` | **제거** |
| `EditExitSheet`(나가기 3갈래) | **제거** — 완성 후 편집이 없으니 drift 자체가 없다 |
| 감상 모드 ↔ 스튜디오 얼굴 전환 | **제거.** 화면이 사실상 초안 전용 + 결과 전용으로 갈라진다 |
| 스튜디오(`/`)·무비 탭(`/movies`)의 무비 목록 | 내보낸 무비가 사라지므로 **목록에 남는 것이 무엇인지 다시 정의**해야 한다. 지금은 "만든 무비들"이 곧 목록이다 |

**새로 필요한 것**

- **"정말 내보낼까요?" 확인 단계** — 되돌릴 수 없는 동작이 된다. 지금은 실수해도 고쳐서 다시
  만들면 되지만, A 에서는 100크레딧이 확정 소모되고 초안이 사라진다.
- **다운로드/게시 성공 판정** — "진행하면 삭제"이므로 실패를 삭제로 오인하면 파일이 영구히
  사라진다. 게시 실패 후 재시도는 파일이 있어야 하는데(결정 문서 §영향), 그 창을 언제까지 열지
  정해야 한다.
- **삭제 안내** — 사용자는 "내보내면 없어진다"를 사전에 알아야 한다.

**사용자에게 남는 경험**: 내보내면 끝. 결과가 마음에 안 들면 **스냅부터 다시 골라 처음부터**
만들고 **100크레딧을 다시 낸다.**

---

### 안 B — 현행 유지 (레시피 영구 · 결과물 30일 · 무료 재생성)

**화면 변화 없음.** 이미 만들어진 그대로다.

**새로 필요한 것**: 30일 만료 안내(만료 임박·만료됨 표시), 만료된 무비의 `다시 만들기`(무료)
동선. 즉 화면이 **늘어난다.**

---

### 안 C — 서버는 B, 앱 로컬 초안·캐시만 정리

**화면 차이가 A 와 거의 없다.** 내보내고 다운로드·게시를 진행하면 그 무비는 앱의 작업 목록에서
빠진다 — 사용자 눈에는 "내보내면 끝"이다.

**다른 점 하나**: 서버에 남아 있으므로 **"내보낸 무비" 목록에서 다시 열 수 있다.**
(사진 앱의 "최근 삭제한 항목"과 같은 성격 — 평소 동선에는 없지만 필요하면 찾을 수 있다.)

**새로 필요한 것**

- 서버 무비 목록 조회 화면 또는 진입점 하나 — **서버 `Movie` 엔티티(A-1)가 선행**이다.
- "로컬에서는 정리됐지만 서버에는 있다"는 개념을 어디에 어떻게 보여줄지.

## 2. 한눈에

| | A (삭제) | B (현행) | C (혼합) |
|---|---|---|---|
| 완성 후 고쳐서 다시 만들기 | ❌ 없어짐 | ✅ 유지 | ✅ 유지(다시 열면) |
| 사용자가 느끼는 단순함 | 최상 | 낮음 | **A 와 거의 같음** |
| 실수했을 때 | 100크레딧 재지불 | 무료 재생성 | 무료 재생성 |
| 지금 구현을 걷어내는 양 | **큼** (주 동선 제거) | 없음 | 작음 |
| 새로 만들 화면 | 확인·삭제 안내·성공 판정 | 만료 안내·재생성 | 서버 무비 목록 진입점 |

| 결제·보관 정책 3편 | **다시 설계** | 그대로 | 그대로 |

## 3. 판단에 도움이 되는 사실 셋

1. **"완성 후 편집"은 이미 한 번 기각된 대안의 반대편이다.** 개발 과정에서 "생성 후에만 편집
   허용"을 시도했다가, 사용자가 확정하지 않은 구성에 돈을 내게 된다는 이유로 버렸다.
   A 는 그보다 한 걸음 더 나아가 **편집 기회를 아예 없앤다** — 같은 문제가 더 큰 형태로 돌아온다.

2. **크레딧 모델과의 궁합.** export 1회 = 100크레딧이다. A 에서는 결과가 마음에 안 들 때마다
   100크레딧이 나간다. 재생성이 무료인 B·C 와 사용자 체감 비용이 크게 다르고, CS 문의도
   여기서 나온다.

3. **A 의 진짜 이득은 화면이 아니라 계약이다.** A 를 택하면 A-7 의 "에셋 라이선스에 영구 조항을
   걸 것인가"가 사라진다(만료 후 재렌더가 없으므로). BGM·스티커 조달 협상이 단순해진다 —
   이건 UX 가 아니라 **사업 조건**의 이득이라, UX 만 보고 판단하면 놓치기 쉽다.

---

## 4. 정리

- **UX 단순함만 원한다면 C 로 충분하다.** 사용자 화면은 A 와 거의 같고, 되돌릴 수 있으며,
  기존 구현과 결정을 뒤집지 않는다.
- **A 를 택할 이유는 화면이 아니라 A-7 라이선스 부담을 없애는 것**이다. 그 값어치가
  "주 동선 제거 + 재생성 100크레딧 + 결제 정책 재설계"보다 크다고 판단되면 A 가 맞다.
- **B 는 아무것도 안 바꾸는 대신 회의가 원한 단순함을 주지 못한다.**

A 를 택한다면 [storage-and-subscription-policy.md](storage-and-subscription-policy.md) §3 을
기각으로 바꾸고 A-2 구독 상품 범위를 다시 정하는 것까지 같은 결정에 포함한다.
