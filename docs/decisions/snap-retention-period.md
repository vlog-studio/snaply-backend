## 한 줄 요약

회의에서 "영상은 15일만 유지한다"는 제안이 나왔다. 그런데 지금 확정된 정책은 "기간 제한 없이,
무료 사용자는 총 2GB까지"다. 둘은 서로 다른 방식이라 하나를 고르거나 둘을 합치는 규칙을 정해야 한다.

## 쉬운 설명 — 지금은 어떻게 되어 있나

- 사용자가 3~5초 스냅을 찍으면 **앱이 자동으로 서버에 복사본을 올린다**. 서버 복사본은 백업이다.
- 서버 복사본은 **지우지 않는다**. 대신 "무료 사용자는 원본 합계 2GB까지"라는 **용량 한도**가
  결정돼 있다(SNAP-9). 한도를 넘으면 새 업로드를 막고 로컬에만 두는 방식이다. 이 한도 집행 코드는
  아직 없다.
- 보관 용량을 늘리는 것은 **구독 상품**으로 팔기로 했다(A-2 보관 축). 즉 "오래·많이 보관"이 돈을
  받는 근거다.

회의 제안은 "15일이 지나면 영상이 사라진다"는 **기간 한도**다. 기간 한도는 용량 한도와 성격이 다르다:
사용자가 아무것도 안 해도 영상이 없어진다.

## 이 결정이 영향을 주는 곳

| 영역 | 무엇이 바뀌나 |
|---|---|
| 서버 DB (`Video`) | 만료 시각 컬럼이 필요해진다. 만료분을 지우는 배치 작업이 새로 생긴다 |
| 무비(프로젝트) | 무비가 참조하는 스냅이 만료로 사라지면 그 컷을 잃는다(SNAP-5 와 같은 연쇄). 15일 안에 내보내지 않은 프로젝트가 깨질 수 있다 |
| 결제·구독 | "보관 용량을 구독으로 판다"는 A-2 설계의 근거가 약해지거나 바뀐다 |
| 앱 | 남은 보관 기간 표시, 만료 임박 알림, 만료된 스냅의 로컬 처리 규칙이 필요하다 |
| 문서 | SNAP-9 spec, 스토리지 정책 결정 문서, 약관(보관 기간 고지) |

## 선택지와 그 결과

### 선택지 A — 회의안: 15일 후 서버에서 만료

| 좋은 점 | 나쁜 점 |
|---|---|
| 서버 저장 비용이 가장 낮고 예측 가능하다 | 15일 안에 무비를 만들지 않은 사용자는 재료를 잃는다. "찍어두고 나중에 묶는" 사용 방식이 불가능해진다 |
| 2GB 한도 집행(유예 → 읽기 전용 전이) 구현이 필요 없어져 단순하다 | 보관 축 구독 상품의 판매 근거가 사라진다. A-2 를 다시 설계해야 한다 |
| | 로컬 삭제([local-copy-after-upload.md](local-copy-after-upload.md))까지 같이 하면 **사용자 영상이 완전히 소멸**한다. 약관 고지와 만료 전 알림이 필수다 |

### 선택지 B — 현행 유지: 기간 무제한 + 2GB 용량 한도

| 좋은 점 | 나쁜 점 |
|---|---|
| 이미 결정·문서화돼 있어 추가 결정이 없다 | 2GB 한도 집행 로직(현재 미구현)을 만들어야 한다 |
| 구독 상품 설계와 맞는다 | 사용자당 저장 비용이 계속 쌓인다(원가 계산은 스토리지 정책 §2) |
| 사용자가 언제든 예전 스냅으로 무비를 만들 수 있다 | |

### 선택지 C — 병행: 기본 15일, 구독자는 무제한(또는 더 긴 기간)

| 좋은 점 | 나쁜 점 |
|---|---|
| 무료 비용을 누르면서 구독 판매 근거를 유지한다 | 규칙이 두 개라 사용자에게 설명이 어렵고 앱 UI 가 복잡해진다 |
| | 구독이 끝나면 영상을 어떻게 할지(§4.4 유예 규칙)까지 다시 정해야 한다 |

## 권장

**B 를 기본으로 두고, A 를 원한다면 "만료 대상은 무비에 쓰이지 않은 스냅만" 같은 예외를 붙일지부터
검토**한다. 이유: 결제·보관 정책 3편이 이미 B 를 전제로 확정돼 있어, A 로 가면 구독 상품 설계까지
되돌아간다. 비용 절감이 목적이라면 원본 대신 배포 렌디션만 남기는 안(스토리지 정책 §6 에서 기각됨)을
다시 열어 비교하는 것이 더 정확하다.
