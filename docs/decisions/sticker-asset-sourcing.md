## 한 줄 요약

스티커를 영상에 얹는 **코드 설계는 끝났지만 실제 그림 파일은 0개**다. 그림을 어디서 가져올지(조달)와,
가져온 그림을 서버에 어떻게 넣고 관리할지(등록 경로)를 정해야 한다. 회의는 "관리자 페이지"를 말했지만
지금 서버에는 관리자라는 개념(권한·로그인)이 없다.

## 쉬운 설명 — 지금 상태

- 스티커를 "어디에 붙이는지"를 말하는 어휘(앵커: 화면 상단·인물 옆 등)는 계약에 들어가 있다.
- 스티커 묶음(팩)을 설명하는 **매니페스트**(파일 URL·어울리는 분위기·크기 범위·기본 움직임)의 설계도
  끝났다(kickoff §1.2). 그런데 매니페스트를 채울 **그림이 없고**, 매니페스트를 서버에 넣는 방법도 없다.
- **관리자 인증이 없다.** 모든 API 는 일반 사용자 토큰으로만 동작한다. "관리자 페이지"를 만들려면
  누가 관리자인지 판별하는 방법부터 새로 만들어야 한다.

## 이 결정이 영향을 주는 곳

| 영역 | 무엇이 바뀌나 |
|---|---|
| 법률 | 스톡 이미지 라이선스 대다수가 "최종 사용자가 파생물을 만드는 앱에 포함"을 금지한다. 우리 제품이 정확히 그 경우다. 조달 경로에 따라 계약 검토 범위가 다르다 |
| 서버 스키마 | 팩·스티커 테이블(매니페스트 저장)과 상태(`experimental → active → deprecated`) |
| 워커 | 렌더 시 스티커 파일을 내려받아 합성. 파일 저장 위치(S3 버킷)와 접근 방식 |
| 인증·권한 | 관리자 페이지를 만들면 관리자 판별(예: Supabase 커스텀 클레임), `/admin/*` 라우트 가드, 감사 로그가 필요하다 |
| 만료 무비 재생성 | 결과물을 다시 만들 때 스티커가 더 이상 배포 불가면 재생성이 깨진다. [movie-cleanup-after-export.md](movie-cleanup-after-export.md)에서 재생성을 유지하면 영구 사용권 조항이 필요하다 |

## 결정 1 — 조달 경로

| 선택지 | 결과 |
|---|---|
| **A. 디자이너 커미션** (권장 40~60종 · 3~4스타일) | 라이선스를 우리가 정한다(영구·재배포 포함). 비용과 리드타임이 든다. 제품 고유의 느낌을 만들 수 있다 |
| **B. 스톡 구매** | 빠르고 싸다. 대부분의 약관이 이 사용 형태(사용자 파생물 생성 앱 내장)를 금지하거나 확장 라이선스를 요구한다 — 계약 검토 없이는 못 쓴다 |
| **C. 유니코드 이모지** | 비용 0, 라이선스 문제 없음(플랫폼 폰트). 그러나 틱톡·인스타 기본 스티커와 구분되지 않아 우리 제품이 스티커를 제공할 이유가 사라진다 |
| **D. AI 생성 이미지** | 빠르고 싸다. 생성물의 저작권·상업 이용 조건이 서비스마다 다르고 국가별로 저작권 불성립 가능성이 있다. [bgm-sourcing.md](bgm-sourcing.md)의 법적 검토 항목과 동일한 검토가 필요하다 |

권장: **A**, 검증용 임시 에셋은 **C** 로 채워 파이프라인만 먼저 돌린다.

## 결정 2 — 등록·관리 경로 (관리자 페이지를 언제 만드나)

| 선택지 | 결과 |
|---|---|
| **A. 저장소 + 시드 스크립트** — 매니페스트 JSON 을 저장소에 두고 배포 시 스크립트가 DB 에 반영, 파일은 S3 에 업로드 | 관리자 인증이 필요 없다. 변경이 PR 로 남아 리뷰·롤백이 된다. 디자이너가 직접 올릴 수는 없어 개발자가 손을 대야 한다 |
| **B. 관리자 웹 페이지** — 팩 업로드·상태 전이·미리보기 UI | 비개발자가 운영할 수 있다. 관리자 인증·권한 모델·새 프런트엔드·감사 로그가 전부 새로 필요하다. 첫 팩 20종을 위해서는 과하다 |
| **C. A 로 시작하고 팩이 늘어나면 B** | 지금 필요한 것만 만든다. B 로 옮길 때 A 의 매니페스트 형식을 그대로 읽게 설계하면 이행 비용이 작다 |

권장: **C.** 관리자 페이지는 팩 상태 전이가 잦아지거나 비개발자 운영이 필요해질 때
`decisions/admin-console.md` 로 범위·인증·호스팅을 따로 결정한다.
