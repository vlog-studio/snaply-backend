## 1. 무엇을 정했나

| 항목 | 결정 |
|---|---|
| 입력 | 사용자가 넘긴 **스냅 여러 개** — 앱에서 찍었거나 갤러리 영상에서 가져온 스냅이다. 긴 영상을 통째로 받아 스냅을 잘라내는 것은 범위 밖이다 |
| 결과물 | **고칠 수 있는 무비 초안**이다. 렌더된 영상이 아니다. 템플릿으로 시작한 초안(TPL-3)처럼 일반 무비 초안이 되고, 사용자는 보고 고친 뒤 `무비 만들기`(MOV-7)로 렌더한다 |
| 편집 범위 | AI 가 정한 것은 **전부** 사용자가 고칠 수 있다. 지금의 편집(순서·삭제·추가·트림·스타일, MOV-4)에 더해 **컷 사이 전환을 경계마다** 바꿀 수 있다 |
| 과금 | 초안을 받는 데는 **크레딧을 쓰지 않는다.** 크레딧은 지금처럼 `무비 만들기`에서만 쓴다(MOV-10) |

AI 가 초안에서 정하는 것은 넷이다: 쓸 스냅(못 쓰는 것·중복은 뺀다) · 순서 · 컷마다의 구간 · 컷 사이 전환.

지금의 두 시작 경로([studio 기능 문서](../../apps/mobile/docs/features/studio.md))와 나란히 놓으면 이렇다.

| | 스냅 골라 새 무비 | 템플릿 | AI 편집 초안 |
|---|---|---|---|
| 재료를 고르는 쪽 | 사용자 | 로컬 매칭(한 번의 외출) | 사용자가 넘긴 것 중에서 AI |
| 배치하는 쪽 | 사용자(고른 순서) | AI, 사용자가 옮기기 전까지 | AI(순서·구간·전환), 사용자가 고친 값은 사용자 |

## 2. 이 결정에서 따라 나오는 것

### 2.1 AI 의 선택은 무비 만들기 전에 있어야 한다

사용자가 보고 고치려면 AI 가 고른 컷·구간·전환이 초안에 들어 있어야 한다. 그래서 자동 편집의
**선택**(v3 초안의 edit-director 가 하는 일)은 초안을 만들 때 돌고, 결과가 무비에 저장된다.
**렌더**는 지금처럼 `무비 만들기`에서 그 무비를 읽는다.

v3 를 Movie export 에 붙인다는 계획([trend-editing-pipeline.md](../plans/trend-editing-pipeline.md) §2.4)은
렌더에 대해서는 그대로다. 달라지는 것은 **선택과 렌더가 다른 시점에 돈다**는 것이다.

### 2.2 AI 가 정한 값마다 주인을 둔다

사용자가 고친 값은 AI 가 초안을 다시 만들어도 덮지 않는다. 순서는 이미 이 규칙이다 — 기본은 AI 가
정하고, 사용자가 옮기면 그 뒤로 사용자 것이다([movie-export-policy.md](movie-export-policy.md) ①,
`Movie.arranger`). 이 규칙을 **컷마다의 구간과 경계마다의 전환**으로 넓힌다.

주인은 값마다 둔다. 무비에 하나만 두면 전환 하나를 고친 것 때문에 AI 가 나머지 전환을 다시 고를 수
없게 되거나, 반대로 사용자가 고친 전환이 다시 만들 때 사라진다.

v3 초안의 `userEdits`(사용자 수정을 스펙 안에 목록으로 모으는 방식, P2)도 같은 목적이다. 여기서
사용자가 고치는 대상은 서버의 무비이므로 **값 옆에 주인을 두는 쪽**이 자연스럽다. 어느 표현으로
할지는 v3 와 함께 A-7 에서 정한다.

### 2.3 경계마다 고를 수 있는 전환은 편집 화면에서 보여야 한다

지금 편집 화면은 원본 컷을 이어 보여줄 뿐이고, 스타일은 렌더에만 들어간다
([무비 기능 문서](../../apps/mobile/docs/features/movie.md) "A style shapes the render, not the studio preview").
스타일 셋 중 하나를 고를 때는 그래도 됐다. 경계마다 전환을 고르게 하면서 결과를 보여주지 못하면
사용자는 보지 않고 고르게 된다.

- 경계마다 고를 수 있는 전환 = 편집 화면이 미리 보여줄 수 있는 전환이다.
- 미리 보여줄 수 없는 효과(클립 간 색 맞춤·LUT 처럼 렌더에서만 되는 것)는 지금처럼 **스타일에 딸린
  속성**으로만 둔다.

AI 가 쓰는 툴이 하나 늘 때마다 그 값을 고치는 UI 와 미리보기도 하나씩 늘어난다(§1 "전부 고칠 수 있다").
초안의 툴을 작게 시작하는 이유다.

### 2.4 사용자가 자른 구간은 비트에 맞추지 않는다

v3 초안은 컷 길이를 비트 수(`beatLength`)로 정하고 끝 지점을 거기서 파생한다([edit-spec-v3.md](edit-spec-v3.md)
B-6). 사용자가 자른 구간을 비트에 맞춰 옮기면 사용자가 정한 값을 서버가 덮는다 — 계획이 "덮지 않음"을
기본으로 적어 둔 문제다([trend-editing-pipeline.md](../plans/trend-editing-pipeline.md) §2.2).

그래서 컷 타이밍의 기준이 컷마다 다르다. 사용자가 자른 컷은 ms 가 기준이고, AI 가 정한 컷은 음악이
있을 때 비트가 기준이다. 음원이 없는 동안(A-7)은 모든 컷이 ms 기준이다. B-6 을 이 경우에 맞게 고치는
일은 A-7 이다.

### 2.5 무효화 사전에 액션 두 개가 빠져 있다

[invalidation-vocabulary.json](../../packages/shared-types/src/invalidation-vocabulary.json) 에는 컷 순서·삭제·추가와
전환 스타일 일괄 교체는 있지만 **트림과 전환 하나의 변경이 없다.** 사전은 액션 × 레이어를 빠짐없이
적는 규칙이라([edit-spec-v3.md](edit-spec-v3.md) §6) 두 액션(`cut-trim`·`transition-edit`)은 레이어마다
판단해서 넣어야 한다(A-7). "수동 컷 편집은 어떤 `attempt` 도 올리지 않는다"는 같은 절의 원칙은 두
액션에도 그대로 적용된다.

### 2.6 초안이 무료이므로 비용은 상한으로 막는다

초안은 사용자가 채택할지 모르는 제안이다. 제안에 과금하면 만들기도 전에 돈부터 낸다 — 템플릿 추천을
무료로 둔 이유와 같고([template-snap-recommendation.md](template-snap-recommendation.md) §4, REC-3), 그래서
§1 에서 초안을 무료로 정했다. 대신 초안이 부르는 분석의 비용은 상한으로 막는다. 상한 값은 단가 실측(A-3)
뒤에 정한다(A-11).

### 2.7 분석이 꺼져 있어도 초안은 나온다

vision 분석은 사용자가 동의해야 돈다(REC-4·ANA-5). 초안이 분석을 조건으로 삼으면 동의하지 않은 사용자에게는
기능 전체가 없는 것과 같다. 그래서 초안은 촬영 순서와 로컬 신호(중복·밝기·흐림·발화 구간 —
[계획](../plans/edit-recipe-tools.md) §4)로 만들어지고, 분석이 켜지면 더 나아진다.

템플릿 추천이 이미 같은 구조다 — 로컬 매칭이 먼저 채우고, 서버 결과는 사용자가 손대지 않은 슬롯에만
얹는다(REC-1). §2.2 의 주인 규칙이 있으면 초안에도 같은 방식을 쓸 수 있다. 초안을 바로 보여줄지,
편집이 끝날 때까지 기다릴지는 A-11 에서 정한다.

### 2.8 넘기는 수와 컷 수

무비는 최대 10컷이다(MOV-5). AI 가 **고르려면** 넘기는 스냅이 그보다 많아야 하는데, 지금 고르기 화면은
`최대 10개`다. 넘길 수 있는 수의 상한은 분석 비용과 함께 정한다(A-11). 템플릿 추천의 후보 상한
(1회 12개, REC-3)은 템플릿용이며, 이 경로의 상한은 따로 정한다.

## 3. 그대로 두는 기존 결정

- **모델 출력은 사용자에게 보이지 않는다**(ANA-2·REC-2). 초안에 들어가는 것은 선택의 결과(컷·구간·전환)이지
  모델이 쓴 문장이 아니다. 빠진 스냅을 이유와 함께 알릴지는 이 원칙과 부딪힐 수 있어 A-11 에서 정한다.
- **분석은 요청할 때만 돈다**(ANA-1). 초안 요청이 곧 명시적 요청이다.
- **선택은 규칙과 시드로 한다.** 모델은 스냅 내용 인식에만 쓰고, 무엇을 고를지는 스타일 번들의 가중치와
  시드로 정한다([edit-spec-v3.md](edit-spec-v3.md) §5, [template-snap-recommendation.md](template-snap-recommendation.md) §7).
  무비 한 편당 모델 비용이 늘지 않고, 같은 입력이 같은 초안을 낸다.
- **분석은 동의한 사용자에게만 돈다**(REC-4·ANA-5, 2026-09-29 옵트인 결정) — 서버 스위치와 회사 키(C-7)도 필요하다.

## 4. 기각한 대안

| 대안 | 기각 이유 |
|---|---|
| 렌더된 예시 영상을 돌려준다 | 생성 1회가 100크레딧이라(MOV-10) 사용자가 AI 결과를 보기 전에 돈을 낸다. 마음에 들지 않으면 고친 뒤 다시 렌더해야 한다 |
| 초안과 함께 무료 저해상도 미리보기를 렌더한다 | 결과를 정확히 보여주지만 초안마다 서버 렌더 비용이 들고, 해상도·워터마크 정책(A-2)이 정해지지 않은 채 유료 생성과 겹친다 |
| 전환은 스타일 단위로만 바꾼다 | 가장 작게 구현된다. 그러나 결과물을 만들기 전의 초안이므로 AI 가 정한 것은 전부 고칠 수 있어야 한다는 결정(§1)과 맞지 않는다 |
| 갤러리의 긴 영상을 받아 스냅을 자동으로 잘라낸다 | 장면 분할·하이라이트 추출이 새로 필요하다. 사용자가 이미 가진 재료(스냅)를 다루는 것이 먼저다. 가져오기는 지금처럼 사용자가 구간을 고른다 |

## 5. 열어 둔 것을 정한 것(2026-10-01)

§2.6·§2.7·§2.8·§3 이 A-11 로 넘긴 넷을 오너가 정했다.

| 항목 | 결정 | 근거 |
|---|---|---|
| 넘길 수 있는 스냅 수 | **30** | 컷 상한(10)의 3배라 고를 여지가 있다. 로컬 신호는 업로드 때 계산해 두므로 수가 늘어도 초안 요청은 느려지지 않는다 |
| 초안 1회의 vision 분석 수 | **12** | 템플릿 추천 1회와 같다 — 초안 1회의 분석 비용이 추천 1회를 넘지 않는다. 로컬 신호로 거른 뒤에만 보낸다(계획 §4) |
| 최근 24시간 초안 수 | **10** | 초안은 무비를 하나 만드는 일이라 화면 재진입마다 부르는 추천(20)보다 드물다 |
| 표시 시점 | **바로** | 분석을 기다리면 동의하지 않은 사용자와 흐름이 갈린다(§2.7). vision 결과는 나중에 `ai` 주인 값에만 얹는다 — 템플릿의 REC-1 과 같은 구조 |
| "다시 편집" | **v1 에 두지 않는다** | 시드의 `attempt` 가 이미 자리를 갖고 있어 나중에 붙일 수 있다. 무엇이 바뀌었는지 보여줄 UI 가 더 필요하다 |
| 미업로드 스냅 | **검사 없이 넣는다** | 방금 찍은 사람이 가장 오래 기다리면 안 된다([template-snap-recommendation.md](template-snap-recommendation.md) §5). 빼지 않고, 촬영 순서 자리에, 구간은 고르지 않는다. 방금 찍은 스냅끼리의 중복은 걸러지지 않는다 |
| 빠진 스냅 | **개수 + 다시 넣기, 이유는 보이지 않는다** | 중복·어두움·흐림은 로컬 신호라 모델 출력은 아니지만, 이유 문구는 판정이 틀렸을 때 사용자와 다투게 된다. 다시 넣을 수 있으면 이유 없이도 잃는 것이 없다 |

모든 상한은 **서버가 집행한다**(템플릿 결정 §4 와 같은 이유 — 비용 정책이 앱 릴리스에 묶이지 않게).

**미업로드 스냅이 계약을 정한다.** 앱의 무비는 기기에서 먼저 만들어지고, 컷이 모두 `videoId` 를 가진 뒤에야
서버로 간다. 서버가 업로드 안 된 스냅으로 무비를 만들 수는 없으므로, 초안 API 는 무비를 만들지 않고
**업로드된 스냅에 대한 제안**(쓸 스냅·순서·구간과 넣지 않은 스냅)을 돌려준다. 앱이 그 제안에 미업로드 스냅을
촬영 시각 자리에 끼워 넣어 무비를 만들고, 무비는 지금과 같은 경로(`POST /movies`)로 서버에 간다. 전환은 그때
`transition-director` 가 고른다. 템플릿 추천이 이미 이 모양이다(제안 → 앱이 병합 → 일반 무비).
