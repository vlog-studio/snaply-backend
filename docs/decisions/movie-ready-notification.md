# 무비 완성 알림 — 누가 보내는가

**작성일**: 2026-09-11
**상태**: 결정 — 구현 완료
**관련**: [expiry-notice-schedule.md](./expiry-notice-schedule.md) · [backlog.md](../backlog.md) A-1

---

## 무엇을 정했나

**편집 워커(Python)가 알림 요청을 큐에 넣고, Node 쪽 전용 워커 프로세스가 꺼내 발송한다.**
큐 이름은 `NOTIFICATION_QUEUE_NAME`(기본 `notifications`), 발송 프로세스는
`apps/api/src/notification-worker.ts` 다.

## 왜 워커가 직접 보내지 않는가

완료를 아는 것은 Python 워커인데 FCM 은 Node 에 있다. 워커에 FCM 을 심는 것이 제일 짧은
길이지만 두 가지를 잃는다.

- **서비스 계정이 두 서비스로 갈라진다.** 시크릿을 나눠 주는 곳이 늘어난다.
- **조용한 시간대·알림 설정 판정이 두 언어로 중복된다.** 중복되면 한쪽만 고쳐져도 아무도
  모른다. 알림 정책은 앞으로도 바뀔 값이라 이 비용이 계속 든다.

## 왜 Redis pub/sub 이 아닌가

워커는 이미 진행률을 pub/sub 으로 흘린다(`edit-jobs:{id}` 채널). 거기 얹는 것이 자연스러워
보이지만 두 가지가 걸린다.

- pub/sub 은 **그 순간 구독자가 없으면 메시지를 버린다.** 발송 쪽을 재배포하는 사이에 끝난
  작업의 알림이 사라진다.
- API 를 여러 개 띄우면 **모두가 받아 같은 알림을 여러 번 보낸다.**

큐는 둘 다 해결한다. 덤으로 같은 결과물의 중복 적재는 `jobId: movie_ready:{videoId}` 가 막는다.

## 왜 API 프로세스 안이 아닌가

`buildApp()` 은 테스트도 부른다. 그 안에서 큐를 소비하기 시작하면 테스트 실행이 실제 알림
작업을 집어삼킨다. 다른 워커들과 같은 방식으로 별도 프로세스에 둔다(compose 서비스
`notification-worker`, API 와 같은 이미지·다른 커맨드).

## 만료 예고와 다른 점

**조용한 시간대에 걸리면 보내지 않고 버린다.** 만료 예고는 걸러서 못 보내면 사용자가 파일을
잃기 때문에 배치를 낮에 돌려 그 구간을 피했지만, 완성 알림은 **놓쳐도 잃는 것이 없다** —
앱을 열면 완성된 무비가 거기 있다. 새벽 3시에 "브이로그가 완성됐어요" 를 보내는 쪽이 더 나쁘다.

**무비를 못 찾으면 보내지 않는다.** 옛 `POST /edit-jobs` 로 직접 만든 결과물에는 무비가 없고,
"무엇이" 완성됐는지 말할 수 없는 알림은 보내지 않는 편이 낫다.
