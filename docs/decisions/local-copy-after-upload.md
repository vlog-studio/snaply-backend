# 결정 요청 — 서버 업로드가 끝난 스냅의 로컬 파일을 지울 것인가

**작성일**: 2026-09-05 (2026-09-09 결정)
**상태**: 결정 — 선택지 **B**. 로컬을 캐시로 내리는 것이 목표이되, 실제로 삭제를 켜는 시점은
**서버 원천 전환 2단계(렌디션)·3단계(앱 동기화)가 실기기에서 검증된 뒤**로 미룬다.
그때까지 앱의 로컬 파일이 계속 원천이다.

## 한 줄 요약

지금은 **폰에 있는 파일이 원본**이고 서버는 뒤따라 올라가는 복사본이다. 회의안은 이를 뒤집어
**서버가 원본, 폰은 비워도 된다**로 가자는 것이다. 방향 자체는 이미 결정돼 있지만(서버 원천 전환),
그 전환의 1~3단계가 끝나기 전에 로컬을 지우면 사용자 영상이 재생 불가·복구 불가가 된다.

## 쉬운 설명 — 지금은 어떻게 되어 있나

- 앱의 모든 화면은 **로컬 파일**을 읽어 재생한다. 서버 업로드는 백그라운드에서 한 개씩 순서대로
  진행되고, 실패하면 재시도한다. 업로드가 끝나든 안 끝나든 화면은 로컬 파일로 돈다.
- 서버 복사본은 아이폰에서 찍은 HEVC/HDR 원본 그대로다. 안드로이드나 웹에서 바로 재생되지 않을 수
  있다. 그래서 "어디서나 재생되는 H.264 배포용 사본(렌디션)을 서버가 만든다"가 서버 원천 전환의
  **2단계**로 잡혀 있고, 아직 구현되지 않았다.
- 앱이 서버 목록과 자기 목록을 맞추는 동기화(reconcile, **3단계**)도 없다. 앱을 지우고 다시 깔면
  서버에 영상이 있어도 앱은 그것을 모른다.

## 이 결정이 영향을 주는 곳

| 영역 | 무엇이 바뀌나 |
|---|---|
| 앱 재생 | 로컬이 없으면 서버 URL 로 재생해야 한다. 지금 재생 URL 은 시한부(만료되는 서명 URL)라 매번 새로 받아야 하고, 오프라인에서는 재생이 안 된다 |
| 앱 저장 구조 | "로컬 파일이 원천"이라는 전제가 코드 곳곳에 있다(스냅 목록·삭제 전파·무비 컷 미리보기). 원천이 서버로 바뀌면 이 전제를 전부 바꿔야 한다 |
| 서버 | 렌디션 생성 워커(2단계), 목록 동기화 API(3단계)가 선행 조건이 된다 |
| 무비 만들기 | 서버 생성은 이미 서버의 파일을 쓰므로 영향 없음. 앱의 **초안 미리보기**는 로컬 파일로 재생하므로 영향 있음 |
| 데이터 손실 위험 | 업로드 "성공" 판정이 잘못되면(예: 업로드는 됐는데 서버 확정 처리가 안 됨) 유일한 사본이 사라진다 |

## 선택지와 그 결과

### 선택지 A — 회의안 그대로: 업로드 성공 즉시 로컬 삭제

| 좋은 점 | 나쁜 점 |
|---|---|
| 폰 저장 공간을 거의 쓰지 않는다 | **지금 구현 상태에서는 위험하다.** 렌디션·동기화가 없어 크로스 플랫폼 재생과 재설치 복구가 안 된다 |
| 서버가 유일한 원천이라 동기화 충돌이 없다 | 오프라인·저속 네트워크에서 자기 영상을 못 본다. 스냅 촬영 직후 미리보기도 네트워크에 의존한다 |
| | 전송 비용(egress)이 크게 늘어난다. A-4 의 "egress 실측 후 재평가" 항목이 선행이다 |

### 선택지 B — 서버 원천 전환 1~3단계 완료 후, 로컬은 "캐시"로 전환

| 좋은 점 | 나쁜 점 |
|---|---|
| 이미 결정된 방향([snap-source-of-truth](snap-source-of-truth.md) §1 "서버가 원천, 로컬은 캐시")과 일치한다 | 시간이 걸린다. 스키마+업로드 확장 → 렌디션 워커 → 앱 동기화 세 단계가 먼저다 |
| 캐시라서 공간이 부족할 때만 지우고, 있으면 오프라인 재생이 된다 | 캐시 정책(무엇을 언제 지우는지)을 따로 정해야 한다 |
| 실패 시 복구 경로(서버 → 재다운로드)가 있다 | |

### 선택지 C — 현행 유지: 로컬 원천, 서버는 백업

| 좋은 점 | 나쁜 점 |
|---|---|
| 아무것도 바꾸지 않는다 | 폰 용량이 사용자 부담이다. 스냅이 많아지면 앱이 무거워진다 |
| | 결정된 서버 원천 전환과 어긋난 채로 남는다 |

## 권장

**B.** A 는 방향은 맞지만 순서가 틀렸다. "업로드 성공 시 로컬 삭제"를 최종 목표로 두되, 실제로 삭제를
켜는 시점은 **렌디션 + 앱 동기화가 실기기에서 검증된 뒤**로 조건부 연기한다. 그 전까지 앱의 로컬 파일은
계속 원천이다. 15일 만료([snap-retention-period.md](snap-retention-period.md))와 함께 A 를 택하면
사용자 영상이 폰에서도 서버에서도 사라지므로 두 결정은 반드시 같은 자리에서 본다.

## 결정 기록

| 항목 | 기록 |
|---|---|
| 결정 | **B — 조건부 연기.** "업로드가 끝나면 로컬은 캐시"가 목표 상태이고, 그 전환을 켜는 조건은 **2단계(H.264 배포 렌디션)와 3단계(앱 reconcile)가 실기기에서 검증됨**이다. 조건이 충족되기 전까지 로컬 파일이 원천이고 지우지 않는다 |
| 결정일 / 결정자 | 2026-09-09 / 제품 |
| 기각한 선택지와 이유 | **A(즉시 삭제)** — 방향은 맞지만 순서가 틀렸다. 렌디션이 없어 서버 사본이 아이폰 HEVC/HDR 원본 그대로라 다른 플랫폼에서 재생되지 않고, reconcile 이 없어 재설치 시 복구가 안 되며, 업로드 성공 판정이 틀리면 유일한 사본이 사라진다. **C(현행 유지)** — 이미 확정된 서버 원천 전환과 어긋난 채로 남는다 |
| 함께 고칠 문서 | SNAP-14(신설) · snap-source-of-truth §5 · apps/mobile/docs/features/snaps.md |

### 15일 만료와의 관계 (2026-09-09 함께 확인)

같은 날 스냅 서버 보관이 **업로드 후 15일**로 정해졌다([snap-retention-period.md](snap-retention-period.md)).
A(즉시 삭제)를 함께 택했다면 **폰에서도 서버에서도 15일 뒤 영상이 완전히 사라졌을 것**이다.
B 를 택해 로컬이 원천으로 남으므로 그 조합은 생기지 않는다.

**단, 전환을 켜는 시점에 이 문제가 다시 열린다.** 로컬을 캐시로 내리는 순간 서버 만료가 곧
영상의 소멸이 되므로, 그때는 15일 만료 정책(또는 구독 연장)과 반드시 같이 본다.
전환 조건에 이 항목을 포함한다.
