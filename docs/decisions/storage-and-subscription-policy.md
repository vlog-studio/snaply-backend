# 스토리지 한도 축소와 구독 상품 도입

**작성일**: 2026-08-14
**상태**: 결정 — Free 원본 스냅 한도를 2GB로 축소하고, 무비는 30일 보관 후 만료시키며,
크레딧(생성)과 별개의 구독(보관) 축을 도입한다.
**원천**: 스토리지 한도 값과 무비 보관 기간, 크레딧·구독의 경계 규칙의 원천이다.

초과 시 동작(업로드 차단 + 로컬 보관)은 그대로 유지**한다. 원 문서는 수정하지 않는다.

| 유료 상품 축 | **크레딧(생성) + 구독(보관) 2축 분리** | 크레딧 단일 |

크레딧 묶음의 수량·가격, 구독 상품의 용량 티어·가격은 이 문서에서 확정하지 않는다 —
[backlog.md](../backlog.md) A-2에서만 관리한다.

## 2. 배경 — 원가를 실제 사용 패턴으로 다시 계산했다

[snap-source-of-truth.md](./snap-source-of-truth.md) §6.3은 스냅 평균 8MB, S3 Standard
$0.025/GB·월을 전제로 했다. 2026-08-14에 **3초 스냅 · 월 50편**이라는 제품 가정이 확정되면서
전제가 바뀌었고, Intelligent-Tiering 적용을 반영해 다시 계산했다.

### 2.1 스냅 1편이 실제로 차지하는 바이트

| 객체 | 3초 기준 | 한도 산정 |
|---|---:|---|
| 원본 (iPhone HEVC, 1080p~4K 혼재) | ~6 MB | **대상** |
| 배포 렌디션 (H.264 1080p) | ~3 MB | 제외 |
| 썸네일 | ~0.1 MB | 제외 |
| 합계 | ~9.1 MB | |

유저 가시 1GB당 실저장 **약 1.5GB**다(§6.3의 파생물 계수 1.4에서 소폭 상승 — 3초 고정이라
썸네일 비중이 커졌다).

### 2.2 종전 5GB 한도의 문제

원본만 산정하므로 한도에 잡히는 증가량은 월 300MB(50편 × 6MB)다.

```
5 GB ÷ 300 MB/월 = 약 17개월
```

**평균 유저가 1년 반 동안 한도에 닿지 않는다.** 그동안 유료 상품의 가치 제안이 0이고,
파생물까지 포함한 실제 저장량은 상한 없이 계속 누적된다. §6.2가 2GB를 "헤비 유저가 1개월 내
도달"로 평가했던 것은 스냅 평균 8MB·개수 무제한을 전제한 추정이었고, 3초 50편 패턴에서는
성립하지 않는다.

### 2.3 2GB에서의 도달 시점과 원가

```
2 GB ÷ 300 MB/월 = 약 6.7개월
```

촬영 화질에 따라 1080p 위주 약 10개월 ~ 4K 위주 약 4.5개월이다. 첫 해 안에 도달하되
체험이 충분히 쌓인 뒤라 전환 대화를 시작하기에 적절한 시점이다.

한도에 걸린 무료 유저 1명의 정상상태 점유량과 원가:

| 구성 | 용량 |
|---|---:|
| 원본 (한도 대상) | 2.00 GB |
| 렌디션 | 1.00 GB |
| 썸네일 | 0.03 GB |
| 무비 (30일 롤링, §4) | 0.06 GB |
| **실 점유** | **3.09 GB** |

| 항목 | 월 원가 |
|---|---:|
| S3 (Intelligent-Tiering 블렌디드 $0.012/GB) | $0.037 ≈ ₩51 |
| CloudFront (유저당 1.0GB, $0.12/GB) | $0.120 ≈ ₩165 |
| **합계** | **약 ₩216 — 상한 고정** |

종전 정책에서는 이 값이 시간에 따라 무한히 증가했다(24개월차 약 ₩285, 36개월차 약 ₩400).
**2GB 한도의 가장 큰 효과는 무료 유저 원가에 상한이 생기는 것**이다.

원가의 약 **70%가 스토리지가 아니라 CDN 전송**이라는 점도 함께 기록한다. 보관 정책만으로는
원가가 크게 내려가지 않으며, 라이브러리 화면의 프리페치 억제 등 전송 최적화가 별도로 필요하다.

## 3. 무비 — 30일 보관 후 만료, 재생성은 무료

### 3.1 결정

무비 파일은 생성 후 **30일**간 서버에 보관하고 이후 만료시킨다. 만료된 무비는 유저가
**크레딧 소모 없이 언제든 재생성**할 수 있다.

### 3.2 근거 — 결과물은 지우고 레시피는 남긴다

`EditJob.editSpec` / `EditJob.renderSpec`이 이미 Json으로 DB에 영구 저장되고
([schema.prisma](../../apps/api/prisma/schema.prisma) `model EditJob`), 원본 스냅도 한도
안에서 영구 보존된다. 즉 **무비 파일을 지워도 동일한 결과물을 언제든 재현할 수 있다.**

| | 크기 | 보관 |
|---|---:|---|
| 무비 파일 (mp4) | ~40 MB | 30일 |
| 레시피 (`editSpec` + `renderSpec`) | 수 KB | 영구 |

재렌더 원가는 편당 약 $0.004(₩6)로, 40MB를 영구 보관하는 것보다 훨씬 싸다. 이미 크레딧으로
결제한 결과물이므로 재생성에 크레딧을 다시 받지 않는다.

### 3.3 30일을 택한 이유

14일과 30일의 원가 차이는 **월 ₩1 미만**이다(평균 점유 56MB vs 120MB). 짧게 잡을 원가상의
이유가 없고, 30일이면 SNS 게시 사이클과 실패 후 재시도 여유가 확보된다. 유료 전환 압박은
스토리지 한도(6.7개월)가 맡는다.

### 3.4 한도 산정에 넣지 않는 이유

30일 롤링이면 무비 점유량은 누적되지 않고 약 120MB에 고정된다 — 2GB의 6%다. 한도에 넣어도
유저 체감이 없는 반면, "크레딧으로 결제한 결과물이 무료 한도를 잡아먹어 스냅 업로드가 막힌다"는
충돌이 생긴다. 산정에서 제외하면 **한도 초과 시에도 크레딧만 있으면 무비를 생성할 수 있어**
정책이 한 단계 단순해진다. §6.2의 "산정 범위 = 원본만" 판단을 그대로 유지하는 결정이다.

### 3.5 부수 조건

- 생성 완료 FCM 알림에 **보관 기간(30일)을 명시**하고, 만료 D-3에 알림을 보낸다. 없으면 CS로 온다.
- SNS 게시는 안전하다 — 틱톡 `PULL_FROM_URL`, 인스타 릴스 컨테이너 모두 게시 시점에 URL을
  가져가고 이후 플랫폼이 자체 사본을 갖는다. 만료 후 재시도가 필요하면 재생성으로 커버한다.
- 무비 만료 처리는 `Movie` 엔티티 구현([backlog.md](../backlog.md) A-1)에 포함한다.
  S3 삭제 실패분은 기존 정리 배치(E-3) 경로를 쓴다.

## 4. 유료 상품 — 크레딧(생성)과 구독(보관)의 2축

### 4.1 왜 크레딧만으로는 부족한가

| | 원가 발생 형태 | 회수 수단 |
|---|---|---|
| 무비 렌더링 | 일회성 (편당 ₩6) | 크레딧 ✅ |
| 스냅 보관·전송 | 반복 + 누적 (유저당 월 ₩216) | **종전에는 없음** |

스냅 업로드에는 결제 행위가 없다. 크레딧을 한 번도 사지 않는 유저에게도 매월 원가가 발생하며,
**일회성 결제로 반복 원가를 덮을 수는 없다.** 반복 원가는 반복 수익으로만 대응된다.

### 4.2 구독 도입이 기존 결정과 충돌하지 않는 이유

[credit-payment-model.md](./credit-payment-model.md)가 구독을 제거한 근거는 *"무비 생성이라는
실제 비용 발생 행위와 월 구독의 대응이 명확하지 않다"* 였다. 그 판단은 **생성 축에서는 지금도
유효하다.** 보관 축은 정반대로 매월 발생하고 매월 커지므로 월 구독이 원가에 1:1로 대응한다.
같은 문서 "확정하지 않은 것"의 마지막 항목인 "유료 스토리지 상품 도입 여부"에 대한 답이다.

### 4.3 경계 규칙 — 구독은 크레딧을 지급하지 않는다

"구독하면 매월 크레딧 N개" 형태의 번들은 [credit-payment-model.md](./credit-payment-model.md)가
기각한 "매월 크레딧을 지급하는 구독" 그 자체이며, 채택하면 결제 주기·이월·미납·강등 정책이
되살아난다. 구독 혜택은 **소모되지 않는 것**으로만 구성한다.

| 구독에 넣는다 | 구독에 넣지 않는다 |
|---|---|
| 스토리지 용량 확대 | 월 크레딧 지급 |
| 무비 영구 보관 (§3의 30일 만료 면제) | 크레딧 할인·보너스 지급 |
| 워터마크 제거 · 고해상도 export | 무비 생성 무제한 |

### 4.4 구독 만료 후 데이터 처리

구독으로 용량을 늘려 쓰던 유저가 해지하면 무료 2GB로 떨어지며 초과 상태가 된다. 즉시 삭제는
불가능하고 영구 보존은 원가가 회수되지 않으므로, 단계적 축소를 적용한다.

```
해지 / 결제 실패
  → 30일 유예 : 전체 기능 유지
  → 읽기 전용 : 열람·다운로드 가능, 신규 업로드만 차단
  → 최소 90일 보존 후 사전 고지 → 초과분 정리
```

§3.2의 레시피 영구 보관이 여기서도 완충 역할을 한다 — 무비 파일을 정리해도 재구독 시 복원할 수 있다.

## 5. 플랫폼(IAP) 확인 사항

2026-08-14 확인. 양 스토어 모두 자동갱신 구독을 정식 상품 유형으로 제공하므로
[payment-channel-iap.md](./payment-channel-iap.md)의 채널 결정을 바꾸지 않는다. 다만 같은 문서
§1이 consumable만 규정하고 있으므로 **auto-renewable subscription을 상품 유형에 추가**한다.

| | Apple | Google Play |
|---|---|---|
| 상품 유형 | auto-renewable subscription (StoreKit 2) | subscription (base plan + offers) |
| 등급 전환 | Subscription Group 내 업/다운그레이드 | base plan 다중 등록 |
| 결제 실패 | Billing Grace Period | Grace period → Account hold |
| 수수료 (우리 규모) | Small Business Program **15%**, 구독도 첫날부터 동일 | 서비스 10% + 결제 5% = **15%**, 한국 적용 2026-12-31 |

Apple은 SBP 미가입 시 구독 1년차 30%·2년차 15%지만, 연 순수취 $100만 이하인 동안에는
구분이 없다. **연 $100만을 넘어 15% 티어를 벗어나면 구독이 소모성 크레딧(30%)보다 수수료가
유리해진다** — 장기적으로 매출 축을 구독으로 옮길 유인이 된다.

한국 대체결제 경로(-4%p)는 자체 PG 수수료 약 3%와 운영 부담을 더하면 실익이 없다는
[payment-channel-iap.md](./payment-channel-iap.md)의 판단이 그대로 유효하다.

### 5.1 구독 도입으로 늘어나는 구현 부담

- **웹훅 이벤트**: consumable은 사실상 구매 1종이지만 구독은 `INITIAL_PURCHASE` ·
  `RENEWAL` · `CANCELLATION` · `EXPIRATION` · `BILLING_ISSUE` · `GRACE_PERIOD` ·
  `PRODUCT_CHANGE` · `UNCANCELLATION` · `REFUND`를 처리해야 하고, 각각이 한도 집행 상태를
  바꾼다. RevenueCat이 스토어 차이는 흡수하지만 상태 전이 로직은 우리 몫이다.
- **환불 경로 분리**: 크레딧 환불은 소비분 회수(잔액 음수 가능), 구독 환불은 entitlement
  소급 만료 → §4.4 진입이다. 하나의 핸들러로 묶지 않는다.
- **스토어 심사**: 구독은 Apple App Review 3.1.2(a)에 따라 구매 화면에 가격·기간·자동갱신
  조건 명시, EULA·개인정보처리방침 링크, **"구매 복원(Restore Purchases)" 버튼**이 필수다.
  소모성 크레딧에는 없던 요구이며 누락은 리젝 사유다.
- **가격 경직성**: 구독은 인상 시 기존 구독자 동의 절차가 필요해 크레딧보다 가격 변경이 어렵다.
  §2.3에서 무료 유저 원가에 상한이 생겼으므로 초기 가격을 오래 유지할 조건은 갖춰졌다.
- **계정 귀속**: entitlement가 지속되므로 한 스토어 계정으로 여러 Snaply 계정에 복원을
  시도하는 악용이 가능하다. RevenueCat `app_user_id` 고정과 transfer 정책 설정이 필요하다.
  [payment-channel-iap.md](./payment-channel-iap.md) §5의 "원천은 항상 백엔드" 원칙을
  구독 entitlement에도 동일하게 적용한다.

## 6. 기각한 대안

### 무비를 한도에 산정 (2026-08-14 논의 중 검토)

원가 대응은 정확하지만 크레딧으로 결제한 결과물이 무료 한도를 잠식해 "돈을 쓸수록 기능이
막히는" 구조가 된다. 30일 만료를 도입하면 점유량이 2GB의 6%로 고정돼 산정 실익도 사라진다. §3.4.

### 무료 유저의 원본을 30일 후 삭제 (렌디션만 영구 보존)

무료 유저 원가를 낮추고 "원본 화질 보관"을 유료 가치 제안으로 만들 수 있으나,
§3.2의 무비 무료 재생성이 **원본이 서버에 남아 있어야** 성립하므로 양립하지 않는다.
원본을 지키고 총량을 2GB로 조이는 쪽이 제품 약속(서버가 원천)과도 일관된다.

### 무비 보관 14일

원가 차이가 월 ₩1 미만이라 짧게 잡을 이유가 없다. §3.3.

### 5GB 유지 + 절감으로 대응

Intelligent-Tiering·Fargate Spot·NAT 제거 등으로 원가를 30~40% 줄일 수 있으나, 무료 유저
원가가 **상한 없이 누적**되는 구조 자체는 그대로다. 회수 구조가 비어 있는 문제는 절감으로
닫히지 않는다. §4.1.

### 한도를 용량이 아니라 보관 기간으로 전환

"최근 N개월 스냅만 보관"은 원가 상한이 확실하지만, 유저가 통제할 수 없는 시점에 데이터가
사라져 서버 원천 약속과 정면으로 충돌한다. 용량 기준을 유지하고 값만 조인다.

## 7. UI 표기

2GB는 iCloud 무료 5GB, Google Photos 무료 15GB 옆에서 짜 보인다. GB 대신 제품 단위로 환산해
표시한다. [snap-source-of-truth.md](./snap-source-of-truth.md) §6.2가 "보류"로 열어둔
하이브리드 표기(집행은 용량, 표기는 환산)를 채택하는 것이다.

```
2 GB ≈ 스냅 약 330편  ·  약 6~7개월치
```
