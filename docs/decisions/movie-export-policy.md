# 결정 요청 — 무비(프로젝트) 내보내기의 세부 규칙 다섯 가지

**작성일**: 2026-09-05
**상태**: 미결 — 결정 대기. 다섯 질문은 모두 서버 `Movie` 엔티티 설계의 입력이라 한 문서에 둔다.
**출처**: [backlog.md](../backlog.md) A-1 "남은 판단 ①~⑤" · [meetings/2026-08-31-dev-sync.md](../meetings/2026-08-31-dev-sync.md) §3·§4
**관련 문서**: [movie-model.md](movie-model.md) · [specs/movie.md](../specs/movie.md) · [plans/2026-08-31-dev-sync-follow-up.md](../plans/2026-08-31-dev-sync-follow-up.md) T3

## 한 줄 요약

"무비는 평면 스냅을 참조하는 `Movie` 엔티티로 만든다"까지는 결정됐다. 실제 스키마와 API 를 짜려면
아래 다섯 가지 작은 규칙이 더 필요하다. 각각 독립적으로 고를 수 있다.

## 쉬운 설명 — 지금은 어떻게 되어 있나

- 무비는 **앱 안에만** 있다. 서버는 "이 클립들을 이 순서·구간·스타일로 합쳐라"는 요청(`POST /edit-jobs`)만
  받고 결과 파일을 돌려준다. 서버는 "무비 A 가 있다"는 사실을 모른다.
- 회의에서 원한 "프로젝트 → 영상 → 목록 → 내보내기" 동선과 "AI 추천 프로젝트"는 서버가 무비를 알아야
  가능하다. 그래서 `Movie` 를 서버로 옮기는데, 옮기면서 아래를 정해야 한다.

---

## ① 내보내기 시 클립 순서의 기본값

**영향**: 앱의 초안 화면(순서 고정 옵션 있음), 템플릿 추천이 채운 슬롯 순서, 서버 `MovieClip.order`.

| 선택지 | 결과 |
|---|---|
| **A. 사용자가 넣은 순서** | 가장 단순. 사용자가 정렬을 원하면 직접 옮긴다. 현행 앱 동작과 같다 |
| **B. 촬영 시각 순** | 브이로그 흐름이 자연스럽다. 단 `capturedAt` 서버 저장(SNAP-10, 미구현)이 선행이고, 사용자가 의도적으로 바꾼 순서를 덮어쓰지 않는 규칙이 필요하다 |
| **C. 기본은 촬영 순, 사용자가 옮기면 그 뒤로 고정** | 둘의 장점. "순서를 손댔는가" 플래그가 스키마에 필요하다 |

권장: **C** — 앱이 이미 `순서 고정` 옵션을 가지고 있어 개념이 있다.

## ② 다시 내보내기: 결과물을 누적할 것인가, 교체할 것인가

**영향**: `Movie` 와 결과물(EditJob)의 관계가 1:1 인지 1:N 인지. 30일 보관 대상 파일 수. SNS 업로드 이력.

| 선택지 | 결과 |
|---|---|
| **A. 교체** — 무비당 결과물 1개, 새로 만들면 이전 파일 삭제 | 저장 비용 최소. 이전 버전으로 돌아갈 수 없다. 이전 파일로 진행 중인 SNS 업로드가 있으면 충돌 처리가 필요하다 |
| **B. 누적** — 생성마다 버전이 남고 사용자가 고른다 | 비교·되돌리기 가능. 파일이 N배로 쌓여 30일 보관 비용이 늘고, 앱에 버전 목록 UI 가 필요하다 |
| **C. 최신 1개 + 직전 1개** | 실수 복구는 되고 비용은 제한된다. 규칙이 하나 더 늘어난다 |

권장: **A** — [movie-cleanup-after-export.md](movie-cleanup-after-export.md)에서 레시피를 영구 보관하기로
하면 이전 버전은 레시피로 무료 재생성이 가능하므로 파일을 여러 개 둘 이유가 약하다.

## ③ 무비를 삭제하면 참조하던 스냅은?

**영향**: 앱의 삭제 확인 문구, 서버 삭제 API 의 동작, 스토리지 한도 계산.

| 선택지 | 결과 |
|---|---|
| **A. 스냅은 그대로 둔다** | 무비 = 레시피, 스냅 = 재료라는 모델([movie-model.md](movie-model.md))과 일치. 가장 안전 |
| **B. 다른 무비가 안 쓰는 스냅은 함께 삭제할지 묻는다** | 정리가 편하지만 "묻는" UI 와 참조 카운트 계산이 필요하다 |
| **C. 함께 삭제** | 한 스냅을 여러 무비가 공유할 수 있다는 MOV-1 과 충돌한다. 다른 무비의 컷이 사라진다 |

권장: **A.** C 는 채택하면 안 된다.

## ④ 날짜 기반 자동 그룹핑을 어디까지 넣을 것인가

**영향**: 앱 라이브러리 화면(이미 날짜별로 묶어 보여줌, SNAP-4), "AI 추천 프로젝트"의 첫 형태, 서버 API 유무.

| 선택지 | 결과 |
|---|---|
| **A. 표시만** — 라이브러리를 날짜로 묶어 보여주고, 그 묶음에서 "이걸로 무비 만들기" 버튼 | 앱만 바꾸면 된다. 서버 스키마 변화 없음. 현행에 가깝다 |
| **B. 서버가 제안** — 서버가 날짜·위치로 묶음을 만들어 "이 날의 브이로그" 초안을 제안 | 회의의 "AI 추천 프로젝트"로 이어진다. `capturedAt` 서버 저장과 `Movie` 서버 엔티티가 선행. 위치까지 쓰려면 A-4 결정이 필요 |
| **C. 없음** | 사용자가 매번 직접 고른다 |

권장: **A 먼저, B 는 T8(AI 추천 프로젝트)에서 별도로.**

## ⑤ 기존 `POST /edit-jobs` 직접 편집 API 는 언제 없애나

**영향**: 앱의 생성 호출 경로, 계약 파일·Swagger, editSpec v3 를 어디에 붙일지(A-7 부착 지점).

| 선택지 | 결과 |
|---|---|
| **A. `Movie` 내보내기 API 가 생기면 즉시 폐기** | 코드가 하나로 정리된다. 앱이 서버 `Movie` 로 완전히 전환될 때까지 생성이 막히므로 앱·서버를 동시에 배포해야 한다 |
| **B. 한 버전 동안 공존 후 폐기** | 앱이 점진적으로 옮길 수 있다. 두 경로를 유지·테스트하는 비용이 한 릴리스 동안 든다 |
| **C. 영구 공존** — 무비 없이도 클립을 바로 합치는 "빠른 생성" 용도로 남긴다 | 두 진입점을 계속 유지해야 하고 editSpec v3 를 두 곳에 붙여야 한다 |

권장: **B.** 폐기 시점을 정하지 않고 두면 C 가 되어 버린다.
