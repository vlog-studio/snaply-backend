## 한 줄 요약

웹훅은 "외부 서비스가 우리 서버로 사건을 알려주는 HTTPS 호출"이다. 받으려면 외부에서 항상 접근 가능한
**고정 HTTPS 주소**가 필요하다 — 이것이 회의의 "도메인 필요" 이유다. 그런데 **어느 서비스의 어떤
사건**을 받으려는지에 따라 만들어야 할 코드가 전혀 다르다. 현재 SNS 업로드는 웹훅 없이도 동작한다.

## 쉬운 설명 — 지금 서버가 받는 웹훅

| 웹훅 | 라우트 | 상태 |
|---|---|---|
| 인스타그램 (Meta) | `GET/POST /sns/instagram/webhook` | **등록 확인 핸드셰이크만** 구현. 이벤트는 서명 확인 후 무시. 릴스 게시에는 웹훅이 필요 없다 |
| 틱톡 | 없음 | 게시 상태는 서버가 주기적으로 물어보는 **폴링**으로 확인한다 |
| RevenueCat (결제) | `POST /billing/webhook/revenuecat` | 구현·테스트 완료. 운영 URL 만 없다(C-1) |
| AdMob SSV (광고 보상) | `GET /billing/webhook/admob` | 구현 완료. 운영 URL 만 없다(C-6) |

즉 "SNS 업로드가 안 되니 웹훅이 필요하다"는 상황은 아니다. 인스타 릴스 실게시는 이미 검증됐고,
틱톡은 받은함 방식의 확인 문제(C-2)가 남아 있을 뿐이다.

## 이 결정이 영향을 주는 곳

| 영역 | 무엇이 바뀌나 |
|---|---|
| 인프라 | 어느 답이든 고정 도메인 + 인증서 + 뒤에 실제 서버(B-1 배포 타깃)가 필요하다 |
| 코드 | 틱톡 웹훅을 받기로 하면 새 라우트·서명 검증·`SnsUpload` 상태 갱신·계약·테스트가 생긴다. 다른 답은 코드 변화가 없다 |
| 콘솔 등록 | 도메인이 바뀌면 인스타·틱톡 콘솔의 리디렉션 URI 와 웹훅 URL, URL prefix 소유권 검증(D-3)을 다시 등록한다 |
| 운영 변수 | `API_BASE_URL` · `INSTAGRAM_REDIRECT_URI` · `TIKTOK_REDIRECT_URI` 값이 운영 도메인으로 바뀐다(새 키는 없음) |

## 선택지와 그 결과

### 선택지 A — 결제·광고 웹훅만: 도메인을 붙이고 기존 라우트를 운영에 연결

| 좋은 점 | 나쁜 점 |
|---|---|
| 새 코드 없음. C-1·C-6 실검증이 바로 열린다 | SNS 쪽은 지금과 같다(폴링). 회의에서 "웹훅"이 SNS 를 뜻했다면 기대와 다르다 |

### 선택지 B — A + 인스타 콘솔 요구 충족: 기존 핸드셰이크 라우트를 운영 도메인으로 등록

| 좋은 점 | 나쁜 점 |
|---|---|
| Meta 앱 검수(C-5) 진행에 콘솔이 웹훅 등록을 요구할 때 막히지 않는다 | 실제로 처리하는 이벤트는 없다. 등록용이다 |

### 선택지 C — B + 틱톡 게시 상태 웹훅 신설(폴링 대체)

| 좋은 점 | 나쁜 점 |
|---|---|
| 게시 완료를 즉시 알 수 있어 폴링 간격·타임아웃 문제가 사라진다 | 새 라우트·서명 검증·상태 갱신 코드와 테스트. 틱톡 심사(`video.publish`, C-3) 이후에야 의미가 있다 |
| | 폴링을 완전히 없애면 웹훅이 유실됐을 때 상태가 영원히 "업로드 중"이 된다 — 웹훅 + 폴링 보조 구조가 필요하다 |

### 선택지 D — Meta 이벤트 실제 구독(댓글·멘션 등)

| 좋은 점 | 나쁜 점 |
|---|---|
| 게시 후 반응을 앱에서 볼 수 있다 | 현재 제품 범위 밖. 추가 권한 심사가 필요하고 spec 이 없다 |

## 권장

**B 를 지금, C 는 C-3(틱톡 직접 게시 승인) 이후 재검토.** 도메인 작업(사내 AWS 현황 파악 → 서브도메인 →
인증서 → 배포 타깃)은 이 결정과 무관하게 바로 시작한다. D 는 기각.
