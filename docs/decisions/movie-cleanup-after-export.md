# 결정 요청 — 내보내기가 끝난 프로젝트(무비)와 결과물을 지울 것인가

**작성일**: 2026-09-05 (2026-09-09 결정)
**상태**: 결정 — **결과물(브이로그)만 지우고 프로젝트(무비)는 남긴다.** 사용자가 다운로드·게시로
"끝내면" 서버의 결과물 파일을 삭제하고, 다시 보기는 제공하지 않는다. 프로젝트는 영구 보존되어
편집 화면에서 다시 고쳐 다시 생성할 수 있다(새 생성이므로 크레딧 100 을 다시 낸다).
선택지 A 를 **결과물 축에만** 적용한 형태다 — 화면 비교는
[movie-cleanup-ux-comparison.md](movie-cleanup-ux-comparison.md).

## 한 줄 요약

회의안은 "내보내기가 끝나면 프로젝트를 지우고, 결과물도 다운로드나 SNS 게시를 하면 지운다"다.
현행 결정은 정반대로 "**레시피(구성)는 영구 보관, 결과물 파일은 30일 보관, 만료되면 크레딧 없이
다시 만들어 준다**"다. 둘 중 하나로 정해야 한다.

## 쉬운 설명 — 용어와 현재 상태

| 회의 용어 | 현행 용어 | 지금 상태 |
|---|---|---|
| project | **무비(Movie)** — 어떤 스냅을 어떤 순서·구간·스타일로 합칠지의 "레시피" | 앱이 로컬에 소유. 서버 엔티티는 결정만 됨(A-1) |
| 내보내기 | **생성(EditJob)** — 서버가 레시피대로 렌더링. 1회 100크레딧 | 구현됨. 생성에 쓴 레시피(`editSpec`/`renderSpec`)는 서버에 영구 보관(MOV-14) |
| vlog | **결과물 파일** | 구현됨. 30일 보관 후 만료 + 무료 재생성은 **결정됐지만 미구현**(MOV-16) |

현행 결정의 논리는 "**파일은 크고 레시피는 작다**"이다. 파일은 30일 뒤 지워 비용을 아끼고, 레시피가
남아 있으니 필요하면 같은 결과를 다시 만들 수 있다. 그래서 재생성은 무료다.

## 이 결정이 영향을 주는 곳

| 영역 | 무엇이 바뀌나 |
|---|---|
| 사용자 경험 | "완성된 무비를 고쳐서 다시 만들기"(MOV-4, 이미 구현·앱 화면의 핵심 동선)가 사라진다. 실수로 내보낸 뒤 되돌릴 수 없다 |
| 크레딧 | 다시 만들려면 처음부터 프로젝트를 새로 짜고 100크레딧을 다시 낸다. "만료 무비 무료 재생성" 약속이 없어진다 |
| 결제·구독 | 결과물이 서버에 남지 않으면 보관 축 구독의 대상이 스냅만으로 줄어든다 |
| 에셋 라이선스 | 재생성이 없으면 "라이선스 만료 후 재렌더가 가능한가"(A-7 영구 조항) 논의가 필요 없어진다 — 단순해진다 |
| SNS 업로드 | 게시 시점에 플랫폼이 파일을 가져가므로 게시 후 삭제는 안전하다(§3.5). 단 게시 실패 후 재시도는 파일이 있어야 한다 |
| 서버 스키마 | 삭제로 가면 만료 배치·재생성 API 가 필요 없다. 대신 "다운로드/게시 완료" 이벤트로 삭제하는 로직이 필요하다 |

## 선택지와 그 결과

### 선택지 A — 회의안: 내보내기 완료 시 프로젝트 삭제, 결과물은 진행 후 삭제

| 좋은 점 | 나쁜 점 |
|---|---|
| 서버 보관이 거의 없어 비용·정리 로직이 단순하다 | 이미 구현된 "고쳐서 다시 만들기" UX 를 제거해야 한다. 앱 화면 구조가 바뀐다 |
| 에셋 영구 라이선스 문제가 사라진다 | 결과물이 마음에 안 들면 처음부터 다시(100크레딧). CS 로 돌아올 가능성이 크다 |
| 사용자 입장에서 "내보내면 끝"이라 개념이 단순하다 | 다운로드 실패·SNS 게시 실패 시 파일이 이미 없으면 복구 불가. "진행하면 삭제"의 성공 판정을 정확히 해야 한다 |

### 선택지 B — 현행 유지: 레시피 영구, 결과물 30일, 무료 재생성

| 좋은 점 | 나쁜 점 |
|---|---|
| 결정·spec·앱 구현이 이미 이 방향이다 | 30일 만료 배치, 만료 안내 알림(FCM 전환 필요), 재생성 API 를 구현해야 한다(A-1) |
| 실수·재편집에 강하다 | 에셋(BGM·스티커) 라이선스가 만료돼도 재생성이 가능해야 하므로 조달 계약에 영구 조항이 필요하다 |

### 선택지 C — 혼합: 서버는 B, 앱 로컬만 회의안대로 정리

내보내기 화면에서 다운로드/게시를 진행하면 **앱 로컬의 프로젝트 초안과 캐시 파일**은 정리하되,
서버의 레시피·결과물은 B 대로 둔다. 사용자가 원하면 서버 목록에서 다시 열 수 있다.

| 좋은 점 | 나쁜 점 |
|---|---|
| 회의의 "내보내면 끝" 느낌을 주면서 되돌리기도 가능하다 | 앱에 "내보낸 무비" 목록(서버 조회)이 필요하다 — 서버 `Movie` 엔티티(A-1)가 선행 |
| 기존 결정을 뒤집지 않는다 | 로컬을 지웠는데 서버에 있다는 개념을 사용자에게 설명해야 한다 |

## 권장

**C.** A 는 결제·보관 정책 3편과 이미 구현된 재편집 UX 를 되돌려야 하고, B 는 회의가 원한 단순함을 주지
못한다. C 는 서버 `Movie` 엔티티가 생기는 시점(A-1)에 자연스럽게 얹을 수 있다. A 를 택한다면
[storage-and-subscription-policy.md](storage-and-subscription-policy.md) §3 을 기각으로 바꾸고
A-2 구독 상품 범위를 다시 정하는 것까지 같은 결정에 포함한다.

## 결정 기록

| 항목 | 기록 |

### 파생 결정 (같은 날 확정)

1. **다시 생성은 유료다.** 끝낸 뒤 편집해서 다시 만들면 크레딧 100 을 다시 낸다.
   사용자가 결과물을 이미 가져갔으므로 새 생성으로 본다 → **MOV-16 의 "크레딧 없는 무료 재생성"은 폐기**된다.
2. **끝내지 않고 방치한 결과물은 30일까지 보관한다.** "끝내기"는 사용자 행동이라 하지 않을 수도
   있으므로 상한이 필요하다. 기존 MOV-16 의 30일 값을 그대로 쓴다.
3. **프로젝트 자동 삭제는 킬스위치로 둔다.** 기능은 구현하되 기본 꺼짐. 나중에 A 원안으로 갈지
   판단할 여지를 남긴다.

### ⚠️ 구현 시 반드시 지킬 것 — "끝냈다"는 자동으로 알 수 없다

`shared/lib/sharing/share-file.ts` 가 직접 적어둔 대로, 시스템 공유 시트는 사용자가 실제로
저장했는지 알려주지 않는다 — **"A share is therefore 'offered', never 'confirmed'."**
시트를 열었다 그냥 닫아도 성공과 똑같이 끝난다.

따라서 **공유 시트를 연 것만으로 삭제하면 안 된다.** 취소한 사용자의 브이로그가 사라지고
되돌릴 방법이 없다.

- **다운로드(공유) 경로**: 끝내기를 **사용자의 명시적 행동**으로 둔다(공유 후 확인, 또는 별도 버튼).
- **SNS 게시 경로**: 서버가 게시 성공을 알고 있으므로(`sns_uploads`) 자동 판정해도 안전하다.

### A-7 에셋 영구 라이선스는 닫히지 않는다

A 원안이었다면 재렌더가 없어져 "라이선스 만료 후 재렌더" 논의가 사라졌을 것이다. 그러나 이
결정은 **프로젝트를 남기고 다시 생성을 허용**하므로, 에셋 라이선스에 영구 조항이 필요한지의
질문은 [backlog.md](../backlog.md) A-7 에 **그대로 남는다.**
