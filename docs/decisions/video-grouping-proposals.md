> **미결정 — 3안 비교와 권장안까지만 정리된 상태다.** 결정 대기 항목은 [backlog.md](../backlog.md) A-1.

> 현재 영상은 유저에게 평면으로 귀속되고, 편집은 목록에서 고른 영상들을 `POST /edit-jobs`로
> 직접 묶어 요청하는 구조다. 기획 목표인 "묶음 단위 관리 + 내보내기(브이로그 생성)"를
> 어떤 모델로 가져갈지 3가지 안을 비교한다.

---

## 0. 판단 기준: 이 앱에서 "묶음"이란

Snaply의 사용 흐름: **외출/여행 중 위치 알림을 받고 클립 촬영 → 쇼츠 한 편으로 자동 편집 → SNS 업로드.**

- 유저 머릿속의 자연스러운 단위는 "폴더"가 아니라 **"그날의 외출 = 만들 브이로그 한 편"**.
- 촬영은 현장에서 즉흥적으로 일어난다 → 촬영 **전에** 정리를 요구하는 UX는 마찰.
- 클립에는 시간·위치 맥락이 있다 (이 앱의 차별점) → 자동 그룹핑의 재료가 이미 있다.

---

## 안 1 — 명시적 프로젝트 (폴더형)

> 유저가 프로젝트를 먼저 만들고, 그 안에 영상을 업로드하고, 프로젝트를 내보낸다.
> (원 기획서의 "프로젝트1 > 영상 1,2,3,4" 구조 그대로)

```
Project (name, status) ─< Video (projectId 필수, position)
POST /projects → POST /projects/:id/videos/upload-url → POST /projects/:id/export
```

| 장점 | 단점 |
|---|---|
| 모델이 직관적, 설명이 쉬움 | **촬영 전에 "프로젝트 생성" 선행 단계** — 현장 촬영 흐름과 충돌 |
| 요금제(프로젝트 수/프로젝트당 영상 수) 연결이 자연스러움 | 유저에게 정리 노동 부과 — 쇼츠 유저 이탈 요인 |
| 권한/공유 확장(협업 프로젝트 등)에 유리 | 클립 하나를 두 브이로그에 쓰려면 구조가 깨짐(복사 필요) |
| | 기존 영상(프로젝트 없음) 이관 정책 필요 |

- 구현 비용: **중** (신규 테이블 + 업로드 플로우 변경 + 기존 데이터 이관)
- 어울리는 제품 방향: 유저가 의도를 갖고 기획 촬영하는 크리에이터 툴

---

## 안 2 — 자동 묶음 (세션형)

> 서버가 촬영 시각(+위치)으로 클립을 자동 그룹핑. 유저는 "9월 3일 성수동" 묶음을
> 열어서 브이로그 생성만 누른다. (애플 사진 "추억" 방식)

```
Video (capturedAt, lat/lng 메타데이터) — 저장은 평면 유지
GET /videos?groupBy=session → 서버가 날짜/위치 클러스터로 그룹핑해 반환
POST /edit-jobs — 그룹의 videoIds로 기존 API 그대로
```

| 장점 | 단점 |
|---|---|
| **정리 노동 0** — 찍기만 하면 알아서 브이로그 단위로 모임 | 자동 묶음이 틀리는 경우(1박2일 여행, 하루 두 장소)의 수동 조정 UX 필요 |
| 위치 기반이라는 **앱의 차별점과 정확히 맞물림** | 묶음이 휘발적(저장 안 됨) — "이어서 작업" 개념이 없음 |
| 스키마 변경 최소 (메타데이터 컬럼만) | **촬영 시각/위치를 지금 안 받고 있음** — 소급 불가 |
| | 요금제 제한을 걸 대상이 애매함 |

- 구현 비용: **하** (컬럼 추가 + 그룹핑 쿼리) — 단, FE의 메타데이터 전달 필요
- 어울리는 제품 방향: 완전 자동화, "생각 없이 찍고 결과만 받는" 경험

---

## 안 3 — 브이로그 초안 (결과물 중심, draft형)

> "폴더"가 아니라 **만들려는 결과물(브이로그)이 곧 묶음**. 유저가 클립을 골라 담으면
> 초안(draft)이 되고, 초안은 저장·수정 가능하며, 내보내기를 누르면 편집이 실행된다.
> 폴더보다는 장바구니/작곡 중인 곡에 가깝다.

```
VlogDraft (title, stylePreset, clips[videoId+구간+순서], status: draft|exporting|done)
Video — 평면 유지, 초안이 참조만 함
POST /drafts → PATCH /drafts/:id (클립 추가/순서/구간) → POST /drafts/:id/export
```

| 장점 | 단점 |
|---|---|
| 유저 멘탈모델과 일치 — "자료 정리"가 아니라 "만들 영상" | 클립이 수십 개면 고르는 UX가 힘듦 → 목록에 날짜 그룹핑(안 2 요소) 필요해짐 |
| 클립을 여러 초안에 재사용 가능 (참조 구조) | "보관함 정리" 요구가 나중에 생기면 별도 대응 필요 |
| **기존 구조와 가장 가까움** — edit_jobs가 이미 clips 스냅샷 보유. 초안 = "내보내기 전의 edit_jobs" | |
| 요금제를 **초안 수 / 월 내보내기 수**에 연결 — 과금 포인트(비용 발생 지점)와 정직하게 일치 | |
| B의 영상 분석(하이라이트 추천)과 자연 결합 — 초안에 담을 때 추천 구간이 미리 채워짐 | |

- 구현 비용: **중하** (신규 테이블 1개 + CRUD + export는 기존 createEditJob 재사용, 워커 무변경)
- 어울리는 제품 방향: 자동 편집이 핵심이되 유저가 살짝 개입(순서/구간)하는 경험

## 권장안: 안 3을 뼈대로 + 안 2를 표현 레이어로

**저장은 평면 유지 → "브이로그 초안"으로 묶음 → 클립 목록 화면은 날짜(추후 위치)로 자동 그룹핑.**

1. 묶음을 저장 구조(폴더)가 아니라 **참조(초안)와 표현(자동 그룹핑)** 으로 다루면,
   클립 재사용·묶음 수정·자동화 어느 방향으로도 유연하다.
2. 유저 눈에는 원 기획서 그림("묶음 안에 영상들")과 동일하게 보인다 — 다른 건 내부 취급뿐.
3. 요금제 제한은 "초안 수 / 월 내보내기 수"로 대체 가능 (프로젝트 수 제한보다 과금 근거가 명확).
4. 단계적 도입이 가능하다:
   - **1차**: VlogDraft + export (전체 구간 이어붙이기)
   - **2차**: 촬영 메타데이터 기반 자동 그룹핑 → "이 묶음으로 초안 만들기" 원탭
   - **3차**: 영상 분석 연동 — 초안 생성 시 추천 구간 자동 채움 (진짜 "자동 편집")

## 진행 방식

- 회의에서 위 3안(+권장안)을 기준으로 논의한다.
- **회의 후 기획안에 대한 추가 의견·새 안이 나오면, 이 문서에 같은 형식(장단점·구현 비용·어울리는 제품 방향)으로 정리해 기존 안들과 비교한 뒤 확정하고 진행한다.** 문서에 없는 구조로 바로 구현에 들어가지 않는다.
- 확정된 안과 결정 사항(질문 목록 1~5의 답)은 이 문서에 기록하고, 이후 스키마/API 설계의 근거로 삼는다.
