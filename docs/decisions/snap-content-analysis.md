## 2. 결과 소비자를 내부로 한정한 이유

분석의 목적은 **자동 스냅 선택의 입력 신호**다. 사용자에게 한 줄 요약·태그를 노출하면
같은 모델 출력이 곧 제품 표면이 되고, 오답 신고 경로·표기 신뢰도·문구 톤까지 함께 설계해야 한다.
선택 신호로만 쓰면 오답의 비용은 "덜 좋은 클립이 뽑힌다"에 머물고, 사용자가 결과를 수정하는
기존 흐름이 그대로 안전망이 된다.

**기각한 대안**: 스냅별 요약·태그를 앱에 노출하고 검색/필터에 쓰는 안. 분석 품질 기준선이
없는 상태에서 노출 표면을 먼저 늘리는 순서가 뒤집혀 있다. 품질 기준선 확보 후 별도로 판단한다.

따라서 기존 `Video` 응답에 `analysisStatus`·`summary`를 추가하지 않고(당시 계획안 그대로), 조회 API는
사용자 기능이 아니라 **디버깅·운영 확인용 최소 범위**다.

## 3. 분석 시점 — 업로드 즉시가 아니라 추천 요청 시점

당시 계획안은 `POST /videos` 성공 후 스냅 하나당 분석 1건을 자동 적재하는 구조였다.
**이 부분은 채택하지 않는다.**

이유는 비용의 성격이다. 스냅은 3초 단위로 대량 업로드되고, 그중 실제로 무비에 쓰이는 것은
일부다. 업로드 즉시 전량 분석은 **버려질 스냅까지 전부 과금**한다. 반면 추천 요청 시점 분석은
사용자가 편집 의사를 밝힌 후보에만 비용이 발생한다.

- 분석 결과는 `videoId` 단위로 **캐시하고 재사용한다.** 같은 스냅이 다음 추천에 다시 후보로
  들어와도 재분석하지 않는다. 모델·프롬프트 버전이 올라갈 때만 새 버전으로 재분석한다
  (버전은 `video_analyses.analysis_version`).
- 대가는 **첫 추천의 대기시간**이다. 이걸 동기 응답으로 감당하지 않는다 — §4.
- 당시 계획안의 `VIDEO_ANALYSIS_AUTO_ENQUEUE` 는 "업로드 시 자동 적재" 플래그였으므로
  이 결정에서는 의미가 없다. 본구현 시 플래그는 **추천 경로에서 분석을 켜는지**로 다시 정의한다.

**기각한 대안**
- *업로드 즉시 전량 자동*: 추천 지연이 0이라는 장점은 크지만, 사용률과 무관하게 비용이
  업로드량에 비례한다. 스냅당 단가 실측이 없는 지금 이 비례를 켤 근거가 없다.
- *업로드 시 큐 적재 + 저부하 시간대 배치*: 총 비용은 전량 분석과 같다. 스파이크·rate limit
  대응은 동시성 설정으로 해결되므로 배치가 주는 이득이 비용 문제를 덮지 못한다.

## 4. 추천 실행은 비동기 job

후보가 수십 장이면 분석 합계가 초 단위를 넘는다. 추천 API가 그걸 동기로 기다리면 후보 수에
따라 타임아웃이 오락가락하고, 상한을 걸면 상한을 넘긴 요청을 실패로 처리할 수밖에 없다.

기존 편집 job과 같은 패턴을 쓴다 — 요청은 즉시 접수 응답, 진행 상황은 진행률 채널로 발행,
결과는 조회. 분석 동시성은 워커 설정에서 조절한다. 새 큐와 상태 모델이 필요하지만,
`edit_jobs` + Redis Pub/Sub 진행률이라는 검증된 구조를 복제하는 일이다.

**기각한 대안**: 동기 상한 대기(구현은 단순하나 후보 수에 취약) ·
사용자가 스냅을 고르는 단계에서 상위 후보를 미리 분석하는 유휴 워밍(대기는 가장 짧지만
헛분석 비용이 생겨 §3의 결정과 방향이 어긋난다).

## 5. 스파이크의 범위 (실행되지 않음)

별도 스파이크 없이 본구현으로 갔다(§9). 스파이크로 하려던 기준선 실측 — 평가셋(§1. 직접 촬영이라 엣지
케이스를 맞춤으로 확보할 수 있어 시드·공개 샘플보다 낫다), 모델 2개 비교와 프레임 4장·`low` 고정(변수를
하나로 두어야 "운영 모델을 무엇으로 고정할지"에 답할 수 있다), 사람이 채점할 항목 — 은 [plans/snap-analysis-recommendation-rollout.md](../plans/snap-analysis-recommendation-rollout.md)
§4.1 이 이어받고, 처리시간·토큰·실패율은 DB 에서 잰다(§9.3). 그 실측에서도 **원본 영상·추출 프레임·모델
원문 응답은 저장소에 커밋하지 않는다.**

## 6. 프라이버시 — 생산 활성화의 선행 조건

사용자가 촬영한 스냅의 프레임을 외부 모델 제공자에게 보내는 처리다. 팀 촬영분 실측은 이 문제를
건드리지 않지만, **생산 스냅에 켜기 전에 약관·개인정보처리방침의 분석 고지·제3자 제공 고지와
법무 검토가 선행돼야 한다.** [snap-source-of-truth.md](./snap-source-of-truth.md)의 위치 정보 검토와 같은 취급이다.

전송 범위는 당시 계획안 그대로다 — 원본 영상 전체가 아니라 임시 추출 프레임만,
오디오는 전송하지 않으며, 영상 삭제 시 분석 결과도 삭제한다.

**기각한 대안**: 사용자 옵트인 설정. 법적으로는 가장 안전하지만 설정 UI·설정별 분기·미동의
사용자를 위한 추천 폴백이 전부 필요해지고, 미동의 비율이 높으면 기능 자체가 반쪽이 된다.
약관 검토 결론이 "개별 동의 필요"로 나오면 이 기각을 재검토한다.

> 약관·개인정보처리방침 **초안**(`apps/api/src/routes/legal.ts`)에 분석 고지·수탁자·국외 이전 절이 있다.
> 법무 검토 전이므로 이 선행 조건은 열려 있고, 남은 항목은 [backlog.md](../backlog.md) D-2 에만 둔다.
> 출시 전이라 "개정" 절차(사전 공지·재동의)가 아니라 출시 문서화에 포함한다.

### 6.1 2026-09-29 — 법무 검토 전에는 사용자 동의(옵트인)로 켠다

오너가 법무 검토를 기다리지 않고 분석을 켜기로 했고, 그 방식으로 위에서 기각한 옵트인을 골랐다.
**§6 의 "생산 스냅에 켜기 전 법무 검토 선행"은 이 절로 대체된다.** 법무 검토 자체는 여전히 필요하다 —
동의 문구도 검토 대상이다([backlog.md](../backlog.md) D-2).

| 항목 | 결정 |
|---|---|
| 켜는 조건 | 서버 스위치(`MOVIE_RECOMMENDATION_ENABLED`)가 켜져 있고, 사용자가 **현재 문구 버전**에 동의했다. 둘 중 하나라도 없으면 분석하지 않는다 |
| 묻는 때 | 분석을 쓰는 기능을 처음 쓸 때. 서버 스위치가 꺼져 있으면 묻지 않는다 |
| 기록 | 종류·문구 버전·동의 시각·철회 시각을 남긴다. 문구가 바뀌면 버전을 올리고 다시 묻는다 |
| 철회 | 나 탭에서 언제든. 그 뒤로 분석하지 않고, 이미 만든 분석 결과와 추천 기록을 파기한다. 큐에서 기다리던 작업은 행이 지워졌으므로 워커가 건너뛴다(보내지 않는다). 철회 순간 이미 처리 중이던 작업은 전송이 끝날 수 있지만 결과는 저장되지 않는다 — 워커의 조건부 UPDATE 가 지운 행을 되살리지 않는다 |
| 집행 | 서버가 한다. 분석 요청(`POST /videos/{videoId}/analysis`)과 추천 요청 모두 — 지금까지 분석 요청에는 스위치 검사도 없어서, 키만 있으면 누구나 분석을 돌릴 수 있었다 |

**기각을 뒤집은 이유**

- §6 이 옵트인을 기각한 비용은 "미동의 사용자를 위한 폴백"이었는데, 그 폴백이 그 사이 생겼다. 템플릿은 로컬
  매칭으로 동작하고(REC-1), AI 편집 초안은 분석 없이도 만들어진다([auto-edit-draft.md](auto-edit-draft.md) §2.7).
  새로 필요한 것은 동의 화면·기록·서버 집행이다.
- 법무의 미결 질문 "별도 동의가 필요한가"(D-2)에 가장 보수적인 답을 먼저 해 두는 셈이다. 결론이 "고지로
  충분하다"로 나오면 그때 기본값을 다시 정한다.
- 남는 약점은 §6 이 적은 그대로다 — 동의하지 않는 비율이 높으면 분석의 효과가 그만큼 줄어든다.

**기각한 대안**

- *모든 사용자에게 켜고 개인정보처리방침으로만 고지*: 얼굴이 담길 수 있는 프레임이 국외(OpenAI, 미국)로
  가는데 고지 문구·DPA·보관 조건이 확정 전이다. 법무 결론 전에 고르기엔 위험이 크다.
- *옵트아웃(기본 켜짐, 원하면 끔)*: 끄기 전까지는 동의 없이 보내는 것이라 위와 같은 문제가 남는다.

## 9. 2026-08-19 — 본구현으로 직행하면서 정해진 것

스파이크를 별도로 돌리지 않고 본구현을 진행했다. §1~§4 의 방향(내부 소비, 요청 시점 분석,
외부 vision, 비동기)은 그대로이며, 아래는 계획 문서(현재 보관)와 **다르게** 구현한 지점이다.

### 9.1 계획과 다른 지점

| 항목 | 계획 제안 | 실제 구현 | 이유 |
|---|---|---|---|
| 분석 트리거 | `POST /videos` 성공 후 자동 적재 | **명시적 요청** `POST /videos/:id/analysis` | §3. 버려질 스냅에 과금하지 않는다. 추천 경로도 같은 서비스 함수를 호출한다 |
| 재시도 | `POST .../analysis/retry` 별도 엔드포인트 | **요청 API 하나로 통합**(멱등) | 같은 행을 재사용하므로 별도 경로가 필요 없다. 엔드포인트가 둘이면 "무엇이 새 분석이고 무엇이 재시도인가"를 앱이 판단해야 한다 |
| 되돌릴 수 없는 실패 | 재시도 API 가 상태만 검사 | **409 + `error.retryable: false`** | 손상된 영상·정책 거절을 다시 큐에 넣으면 같은 비용으로 같은 실패를 반복한다 |
| feature flag | `VIDEO_ANALYSIS_AUTO_ENQUEUE` | **두지 않았다** | 자동 적재가 없으므로 끌 대상이 없다. 분석은 호출하지 않으면 돌지 않는다 |
| 영상 길이 | `Video.durationMs` 컬럼 추가 | `video_analyses.duration_ms`(스냅샷) + `videos.duration_seconds` **실측 교정** | 기존 `Video` 응답 계약을 건드리지 않는다. 실측은 완료 시점에만 반영한다 |
| 프레임 수 | 최대 4장 | 최대 4장 + **유사 프레임 제거 후 남은 장수** | 거의 같은 화면 4장은 토큰만 늘린다. 실제 사용 장수는 `frame_timestamps_ms` 로 남는다 |
| 진행률 | 언급 없음 | **없음**(폴링) | 결과가 사용자 노출용이 아니라 진행률 UI 가 필요 없다. WS 채널을 늘리지 않는다 |

`visualIssues` 는 자유 텍스트가 아니라 **코드 enum**으로 고정했다(`shaky`·`blurry`·`too_dark` 등).
자유 텍스트를 받으면 "어떤 이유로 못 쓰는 스냅이 많은가"를 집계할 수 없다.

### 9.2 스파이크를 건너뛴 대가

품질·단가 기준선 없이 배포 가능한 상태가 됐다. 그래서 **켜는 것은 여전히 조건부**다 — 남은 조건
(운영 모델 고정 · 단가·후보 수 상한 확정 · 법무 검토, §6)은 [backlog.md](../backlog.md) A-3·A-6·D-2 에만 둔다.

### 9.3 기준선은 이제 DB 에서 측정한다

`video_analyses` 가 `input_tokens`·`output_tokens`·`model_version`·`prompt_version`·
`attempts`·`started_at`·`completed_at`·`error_code` 를 모두 남긴다. 별도 스파이크 CLI 없이
같은 테이블을 집계해 처리시간·토큰·실패율·모델별 비교를 낼 수 있다. 그래서 스파이크 디렉터리
(`apps/ai-worker/scripts/analysis-spike/`)는 남기지 않고 제거했다 — 프레임 추출·검증 로직이
두 곳에 복제되면 한쪽만 고쳐진다.

품질(요약 사실성·환각 비율·`usableForEdit` 정확도)만은 여전히 사람이 채점해야 한다.
채점 대상은 이제 실행 결과 테이블에서 뽑는다.
