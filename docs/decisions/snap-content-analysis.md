## 2. 결과 소비자를 내부로 한정한 이유

분석의 목적은 **자동 스냅 선택의 입력 신호**다. 사용자에게 한 줄 요약·태그를 노출하면
같은 모델 출력이 곧 제품 표면이 되고, 오답 신고 경로·표기 신뢰도·문구 톤까지 함께 설계해야 한다.
선택 신호로만 쓰면 오답의 비용은 "덜 좋은 클립이 뽑힌다"에 머물고, 사용자가 결과를 수정하는
기존 흐름이 그대로 안전망이 된다.

**기각한 대안**: 스냅별 요약·태그를 앱에 노출하고 검색/필터에 쓰는 안. 분석 품질 기준선이
없는 상태에서 노출 표면을 먼저 늘리는 순서가 뒤집혀 있다. 품질 기준선 확보 후 별도로 판단한다.

따라서 계획안 §11.1의 "기존 `Video` 응답에 `analysisStatus`·`summary`를 추가하지 않는다"는
그대로 유지되고, 조회 API는 사용자 기능이 아니라 **디버깅·운영 확인용 최소 범위**다.

## 3. 분석 시점 — 업로드 즉시가 아니라 추천 요청 시점

계획안은 `POST /videos` 성공 후 스냅 하나당 분석 1건을 자동 적재하는 구조였다.
**이 부분은 채택하지 않는다.**

이유는 비용의 성격이다. 스냅은 3초 단위로 대량 업로드되고, 그중 실제로 무비에 쓰이는 것은
일부다. 업로드 즉시 전량 분석은 **버려질 스냅까지 전부 과금**한다. 반면 추천 요청 시점 분석은
사용자가 편집 의사를 밝힌 후보에만 비용이 발생한다.

- 분석 결과는 `videoId` 단위로 **캐시하고 재사용한다.** 같은 스냅이 다음 추천에 다시 후보로
  들어와도 재분석하지 않는다. 모델·프롬프트 버전이 올라갈 때만 새 버전으로 재분석한다
  (계획안 §5의 `analysisVersion` 설계는 유지).
- 대가는 **첫 추천의 대기시간**이다. 이걸 동기 응답으로 감당하지 않는다 — §4.
- `VIDEO_ANALYSIS_AUTO_ENQUEUE`(계획안 §10)는 "업로드 시 자동 적재" 플래그였으므로
  이 결정에서는 의미가 없다. 본구현 시 플래그는 **추천 경로에서 분석을 켜는지**로 다시 정의한다.

**기각한 대안**
- *업로드 즉시 전량 자동*: 추천 지연이 0이라는 장점은 크지만, 사용률과 무관하게 비용이
  업로드량에 비례한다. 스냅당 단가 실측이 없는 지금 이 비례를 켤 근거가 없다.
- *업로드 시 큐 적재 + 저부하 시간대 배치*: 총 비용은 전량 분석과 같다. 스파이크·rate limit
  대응은 동시성 설정으로 해결되므로 배치가 주는 이득이 비용 문제를 덮지 못한다.

## 4. 추천 실행은 비동기 job

후보가 수십 장이면 분석 합계가 초 단위를 넘는다. 추천 API가 그걸 동기로 기다리면 후보 수에
따라 타임아웃이 오락가락하고, 상한을 걸면 상한을 넘긴 요청을 실패로 처리할 수밖에 없다.

기존 편집 job과 같은 패턴을 쓴다 — 요청은 즉시 접수 응답, 진행 상황은 진행률 채널로 발행,
결과는 조회. 분석 동시성은 워커 설정에서 조절한다. 새 큐와 상태 모델이 필요하지만,
`edit_jobs` + Redis Pub/Sub 진행률이라는 검증된 구조를 복제하는 일이다.

**기각한 대안**: 동기 상한 대기(구현은 단순하나 후보 수에 취약) ·
사용자가 스냅을 고르는 단계에서 상위 후보를 미리 분석하는 유휴 워밍(대기는 가장 짧지만
헛분석 비용이 생겨 §3의 결정과 방향이 어긋난다).

## 5. 스파이크의 범위 (실행 전 §9로 대체됨)

> **2026-08-19: 이 절의 "스파이크만 한다"는 범위는 실행되지 않았다.** 같은 날 본구현으로
> 바로 진행하기로 결정했다 — §9. 아래 내용은 당시 판단 기록이며, 기준선 측정 방법은
> §9.3 으로 바뀌었다.

목적은 **품질·처리시간·스냅당 단가의 기준선 확보**다. A-3의 "OpenAI 호출 비용 한도"는
실측 없이는 정할 수 없으므로, 이 스파이크가 그 값의 입력이다.

### 5.1 하는 것

- 팀원 폰으로 직접 촬영한 **30~100편**. 계획안 §14.4의 카테고리(여초·음식·셀카·반려동물·
  빠른 움직임·야간·역광·흔들림·초점 불량·유사 프레임·중간에 화면이 바뀜)를 의도적으로 커버한다.
  직접 촬영이라 엣지 케이스를 맞춤 확보할 수 있다는 점이 시드·공개 샘플보다 유리하다.
- **모델 2개 비교**(상위 모델 vs 저비용 모델). 프레임은 4장·detail `low`로 **고정**한다.
  변수를 1개로 제한하는 이유는 "운영 모델을 무엇으로 고정할지"라는 단일 질문에 답하기 위해서다.
- 측정 항목: 한 줄 요약의 사실성 · 핵심 사물/행동 포함률 · 환각 비율 ·
  `usableForEdit` 판단 정확도 · 스냅당 처리시간 · 입출력 토큰 · **스냅당 단가** · 호출 실패율.
- 프레임 추출은 FFprobe 실측 길이 기준 상대 위치(계획안 §7)를 그대로 검증한다.

### 5.2 하지 않는 것

- `VideoAnalysis` Prisma 모델·마이그레이션, 분석/추천 라우트, shared types, BullMQ 큐,
  프로덕션 워커 엔트리 — **전부 본구현 단계로 미룬다.** 스파이크는 로컬 스크립트와
  로컬 결과 파일로 끝낸다.
- `env-spec.ts`·`.env.example`에 `OPENAI_*`·`VIDEO_ANALYSIS_*`를 선언하지 않는다.
  스파이크 스크립트는 셸 환경에서 키를 받는다. 선언은 본구현 착수와 같은 변경에서 한다
  (선언만 먼저 하면 아무도 읽지 않는 변수가 원천 문서에 남는다).
- 프레임 수(1/2/4)·detail(low/high) 격자 탐색. 4장·low에서 품질이 부족할 때만 다음 라운드로 연다.
- 원본 영상·추출 프레임·모델 원문 응답은 저장소에 커밋하지 않는다.

## 6. 프라이버시 — 생산 활성화의 선행 조건

사용자가 촬영한 스냅의 프레임을 외부 모델 제공자에게 보내는 처리다. 스파이크는 팀 촬영분만
쓰므로 이 문제를 건드리지 않지만, **생산 스냅에 켜는 시점에는 약관 개정과 제3자 제공 고지가
선행돼야 한다.** [snap-source-of-truth.md](./snap-source-of-truth.md)의 위치 정보 검토와 같은 취급이다.

전송 범위는 계획안 §15를 유지한다 — 원본 영상 전체가 아니라 임시 추출 프레임만,
오디오는 전송하지 않으며, 영상 삭제 시 분석 결과도 삭제한다.

**기각한 대안**: 사용자 옵트인 설정. 법적으로는 가장 안전하지만 설정 UI·설정별 분기·미동의
사용자를 위한 추천 폴백이 전부 필요해지고, 미동의 비율이 높으면 기능 자체가 반쪽이 된다.
약관 검토 결론이 "개별 동의 필요"로 나오면 이 기각을 재검토한다.

> **2026-08-19**: 약관·개인정보처리방침 **초안**에 분석 고지·수탁자·국외 이전 절을 넣었다
> (`apps/api/src/routes/legal.ts`). 아직 법무 검토 전이므로 이 절의 선행 조건은 그대로 열려
> 있다. 남은 항목은 [backlog.md](../backlog.md) A-3. 서비스가 출시 전이라 "개정" 절차가 아니라
> 출시 문서화에 포함하면 된다는 점만 달라졌다.

## 9. 2026-08-19 — 본구현으로 직행하면서 정해진 것

스파이크를 별도로 돌리지 않고 본구현을 진행했다. §1~§4 의 방향(내부 소비, 요청 시점 분석,
외부 vision, 비동기)은 그대로이며, 아래는 계획 문서(현재 보관)와 **다르게** 구현한 지점이다.

### 9.1 계획과 다른 지점

| 항목 | 계획 제안 | 실제 구현 | 이유 |
|---|---|---|---|
| 분석 트리거 | `POST /videos` 성공 후 자동 적재 | **명시적 요청** `POST /videos/:id/analysis` | §3. 버려질 스냅에 과금하지 않는다. 추천 경로(A-1 이후)는 같은 서비스 함수를 호출한다 |
| 재시도 | `POST .../analysis/retry` 별도 엔드포인트 | **요청 API 하나로 통합**(멱등) | 같은 행을 재사용하므로 별도 경로가 필요 없다. 엔드포인트가 둘이면 "무엇이 새 분석이고 무엇이 재시도인가"를 앱이 판단해야 한다 |
| 되돌릴 수 없는 실패 | 재시도 API 가 상태만 검사 | **409 + `error.retryable: false`** | 손상된 영상·정책 거절을 다시 큐에 넣으면 같은 비용으로 같은 실패를 반복한다 |
| feature flag | `VIDEO_ANALYSIS_AUTO_ENQUEUE` | **두지 않았다** | 자동 적재가 없으므로 끌 대상이 없다. 분석은 호출하지 않으면 돌지 않는다 |
| 영상 길이 | `Video.durationMs` 컬럼 추가 | `video_analyses.duration_ms`(스냅샷) + `videos.duration_seconds` **실측 교정** | 기존 `Video` 응답 계약을 건드리지 않는다. 실측은 완료 시점에만 반영한다 |
| 프레임 수 | 최대 4장 | 최대 4장 + **유사 프레임 제거 후 남은 장수** | 거의 같은 화면 4장은 토큰만 늘린다. 실제 사용 장수는 `frame_timestamps_ms` 로 남는다 |
| 진행률 | 언급 없음 | **없음**(폴링) | 결과가 사용자 노출용이 아니라 진행률 UI 가 필요 없다. WS 채널을 늘리지 않는다 |

`visualIssues` 는 자유 텍스트가 아니라 **코드 enum**으로 고정했다(`shaky`·`blurry`·`too_dark` 등).
자유 텍스트를 받으면 "어떤 이유로 못 쓰는 스냅이 많은가"를 집계할 수 없다.

### 9.2 스파이크를 건너뛴 대가

품질·단가 기준선 없이 배포 가능한 상태가 됐다. 그래서 **켜는 것은 여전히 조건부**다.

- 운영 모델은 아직 고정되지 않았다(`OPENAI_VISION_MODEL` 기본값은 잠정).
- 스냅당 단가 상한과 추천 1회당 후보 수 상한이 정해지지 않았다.
- 생산 스냅에 켜기 전 **약관 개정·제3자 제공 고지**가 여전히 선행 조건이다(§6).

### 9.3 기준선은 이제 DB 에서 측정한다

`video_analyses` 가 `input_tokens`·`output_tokens`·`model_version`·`prompt_version`·
`attempts`·`started_at`·`completed_at`·`error_code` 를 모두 남긴다. 별도 스파이크 CLI 없이
같은 테이블을 집계해 처리시간·토큰·실패율·모델별 비교를 낼 수 있다. 그래서 스파이크 디렉터리
