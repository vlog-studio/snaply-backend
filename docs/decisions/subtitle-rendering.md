## 한 줄 요약

지금 자막은 파일 안에 **별도 트랙**으로 들어간다(소프트 자막). 플레이어에서 켜야 보이고, 틱톡·인스타에
올리면 사라진다. 대안은 자막을 **영상 화면에 직접 그려 넣는** 것(번인)이다. 그러면 어디서나 보이지만
끌 수 없고, 화려한 애니메이션 자막은 번인으로만 가능하다.

## 쉬운 설명 — 두 방식의 차이

| | 소프트 자막 (현행, `mov_text`) | 번인 자막 (ASS/libass) |
|---|---|---|
| 자막이 어디에 있나 | 영상 파일 안의 별도 텍스트 트랙 | 영상 픽셀 자체에 그려짐 |
| 플레이어에서 끄기 | 가능(기본 꺼짐인 플레이어가 많음) | 불가능 |
| SNS 업로드 시 | **유실됨** — 플랫폼이 재인코딩하며 트랙을 버린다 | 유지됨 |
| 단어 단위 팝업·색 변화 같은 숏폼 스타일 | 불가능 | 가능 |
| 렌더 비용 | 추가 인코딩 없음 | 자막 합성 단계가 들어가 재인코딩 1회 추가(생성 시간·서버 비용 증가) |
| 오타 수정 | 트랙만 바꾸면 됨(이론상) | 다시 렌더링해야 함 |

현재 자막은 **opt-in**(기본 없음)이고, 켜면 한국어 음성 인식(whisper)으로 만든다. 음성 인식 정확도
문제는 두 방식 모두 같다 — 이 결정은 "보여주는 방식"만 정한다.

## 이 결정이 영향을 주는 곳

| 영역 | 무엇이 바뀌나 |
|---|---|
| FE 계약 | [api-spec.md](../api-spec.md)가 "플레이어에서 켜야 보인다, SNS 업로드 시 유실될 수 있다"고 안내한다. 번인이면 이 문구가 반대로 바뀐다 |
| 앱 | 자막 토글의 설명 문구, 미리보기에서 자막이 보이는지 여부 |
| 워커 | 번인은 libass 합성 단계 추가. 폰트 파일(TTF/OTF)을 워커 이미지에 넣어야 한다 |
| editSpec v3 | 번인이어야 "자막 스타일" 층(위치·폰트·애니메이션)이 의미가 있다. 소프트면 그 층이 필요 없다 |
| 크레딧 | 재인코딩이 늘어 생성 시간이 길어진다. 차감량(100)은 그대로여도 원가는 오른다 |

## 선택지와 그 결과

### 선택지 A — 현행 유지: 소프트 자막

| 좋은 점 | 나쁜 점 |
|---|---|
| 구현 변화 없음 | SNS 업로드가 이 제품의 핵심인데, 올리면 자막이 사라진다. 사용자는 "자막 켰는데 왜 없냐"고 묻는다 |
| 사용자가 끌 수 있다 | 숏폼형 자막 스타일을 만들 수 없어 A-7 의 트렌드 편집 목표와 어긋난다 |

### 선택지 B — 번인으로 전환

| 좋은 점 | 나쁜 점 |
|---|---|
| SNS 에서 그대로 보인다. 제품 목적과 맞는다 | 재인코딩 1회 추가 → 생성 시간·비용 증가 |
| 단어 단위 애니메이션 등 숏폼 스타일 가능 | 자막 오류를 플레이어에서 숨길 수 없다. 음성 인식 품질이 그대로 노출된다 |
| | 앱 안내 문구·spec·워커·폰트 자산을 함께 바꿔야 한다 |

### 선택지 C — 둘 다: 소프트 트랙도 넣고 번인도 한다

| 좋은 점 | 나쁜 점 |
|---|---|
| 접근성(스크린리더·검색)에 소프트 트랙이 유용하다 | 화면에 자막이 두 번 보일 수 있다(플레이어가 소프트 트랙을 켜면). 이득이 작고 혼란은 크다 |

### 선택지 D — 사용자가 고른다: 자막 켤 때 "화면에 새김 / 파일에만" 선택

| 좋은 점 | 나쁜 점 |
|---|---|
| 용도별로 맞출 수 있다 | 옵션이 하나 더 생기고, 두 경로를 다 유지해야 한다. 대부분 사용자는 차이를 모른다 |

## 권장

**B.** 이 제품의 결과물은 SNS 로 나가는 것이 목적이고, 소프트 자막은 그 경로에서 사라진다. 음성 인식
품질 노출이 걱정이면 "자막은 기본 꺼짐(opt-in)"을 유지하면서 번인으로 가는 것이 절충이다.
D 는 v3 파이프라인이 안정된 뒤 필요하면 추가한다.
