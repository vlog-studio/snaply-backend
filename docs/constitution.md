# Constitution — 저장소 최상위 원칙

**작성일**: 2026-09-02
**상태**: 초안 — 확정되면 저장소의 모든 spec·plan·구현·문서에 우선하는 현행 규칙
**원천**: 저장소 전체에 적용되는 최상위 원칙의 단일 원천
**관련 문서**: [AGENTS.md](../AGENTS.md) · [README.md](../README.md) · [docs/team.md](team.md)

## 이 문서의 지위

- 이 문서는 **원칙**만 담는다. 원칙을 집행하는 **세칙**(명령, 파일 위치, 형식)은
  [AGENTS.md](../AGENTS.md)와 각 원천 문서가 담고, 이 문서는 세칙을 중복 서술하지 않는다.
- spec·plan·구현·리뷰가 이 문서와 충돌하면 **이 문서가 우선한다.** 원칙이 현실과 맞지 않게
  되었으면 원칙을 어기는 것이 아니라 **개정**한다(§개정 절차).
- 각 조항은 "지켰는지 확인할 수 있는" 문장으로 쓴다. 확인할 수 없는 선언은 여기에 넣지 않는다.

## 제1조 — 스펙이 구현보다 먼저다

동작 계약(사용자가 관찰하는 동작, API 계약, 정책 값)을 새로 만들거나 바꾸는 작업은
**무엇을·왜 만드는지 합의된 문서(spec)가 코드보다 먼저** 존재해야 한다.
구현 계획(어떻게)은 spec과 구분하며, spec 없이 plan을 쓰지 않는다.

- 예외: 버그 수정, 리팩터링, 의존성 갱신처럼 **동작 계약이 변하지 않는** 변경.
- 근거: 계약 합의 없이 구현부터 하면 리뷰가 "코드가 맞는가"가 아니라 "이게 맞는 방향인가"로
  되돌아가고, 문서는 사후 추인 기록으로 전락한다.

## 제2조 — 각 사실의 원천은 한 곳이다

모든 사실(스키마, API 계약, 환경변수, 정책 값, 현재 상태)은 **정확히 한 문서·한 파일**을
원천으로 가지며, 다른 문서는 그 원천을 **링크**한다. 같은 사실을 두 곳에 서술하지 않는다.

- 원천 지도는 [README.md](../README.md) §어디를 봐야 하는가.
- 근거: 사본이 둘이면 하나를 고칠 때 나머지가 반드시 낡는다. 이 저장소의 문서 규칙 전체가
  이 원칙의 파생이다.

## 제3조 — 계약과 구현은 같은 커밋에서 움직인다

동작 계약을 바꾸는 커밋은 그 계약을 서술하는 원천 문서·선언을 **같은 커밋**에서 갱신한다.
"코드 먼저, 문서는 나중에"를 허용하지 않는다.

- 적용례(세칙은 각 원천 참조): 라우트/스키마 변경 ↔ `docs/api-spec.md`,
  새 환경변수 ↔ `apps/api/src/env-spec.ts` + `.env.example`,
  DB 스키마 ↔ 마이그레이션, 코드 ↔ 해당 테스트.
- 근거: 커밋이 분리되는 순간 제2조의 원천이 낡은 상태로 존재하는 구간이 생긴다.

## 제4조 — 시크릿은 경계를 넘지 않는다

시크릿은 로컬 `.env` 파일과 배포 플랫폼의 시크릿 주입에만 존재한다.
**커밋·앱 번들·문서에 시크릿을 넣지 않으며**, 클라이언트로 가는 변수는 공개 가능한 값만 허용한다.

- 세칙: [AGENTS.md](../AGENTS.md) §작업 환경 · [decisions/env-management.md](decisions/env-management.md).
- 근거: 번들·이력에 들어간 시크릿은 회수가 불가능하다.

## 제5조 — 검증은 파괴적이지 않아야 한다

테스트·검증은 **격리된 환경(전용 DB, 지정된 실행 명령)에서만** 실행한다. 개발·운영 데이터를
건드릴 수 있는 경로로 검증을 실행하지 않으며, 그런 경로는 발견 즉시 가드를 세운다.

- 세칙: [AGENTS.md](../AGENTS.md) §테스트.
- 근거: 실제로 잘못된 경로의 `npx vitest` 실행이 개발 DB 시드를 삭제한 사고가 있었다.

## 제6조 — 계약의 형태는 하나다

외부로 노출되는 계약(API 응답 구조, 에러 전파, 네이밍)은 저장소 전체에서 **하나의 형태**를
따른다. 새 코드가 기존 형태와 다른 형태를 도입하려면 먼저 이 문서 또는 세칙을 개정한다.

- 세칙: [AGENTS.md](../AGENTS.md) §코드 컨벤션 · §공유 파일.
- 근거: 형태가 둘이면 소비자(모바일, FE)가 분기를 갖게 되고 그 분기는 계약이 아니라 우연이 된다.

## 제7조 — 기록은 수명에 따라 배치한다

문서는 **계속 갱신되는가, 한 시점에 굳는가**로 위치가 결정되며, 수명이 끝난 문서는 archive로
옮기고 판단 근거로 쓰지 않는다. 미결 작업 목록은 저장소 전체에서 **하나**만 존재한다.

- 세칙: [doc-conventions.md](doc-conventions.md) · [AGENTS.md](../AGENTS.md) §문서 갱신 의무.
- 근거: 미결 목록이 여럿이면 하나를 닫아도 나머지가 낡는다(제2조의 특수형).

## 제8조 — 변경은 원자적이다

한 커밋에는 **하나의 독립적인 변경 목적**만 담되, 함께 있어야 완전한 것(코드와 테스트,
스키마와 마이그레이션, 계약과 문서)은 쪼개지 않는다. 되돌리는 이유가 다른 변경은 분리한다.

- 세칙: [AGENTS.md](../AGENTS.md) §커밋 · [commit-guidelines.md](commit-guidelines.md).
- 근거: 커밋이 원자적이어야 revert·bisect·리뷰가 커밋 단위로 성립한다.

## 개정 절차

- 이 문서의 개정은 **별도 커밋**으로 하고, 조항의 신설·폐지·의미 변경에는 배경과 기각한
  대안을 [docs/decisions/](decisions/)에 남긴다. 자구 수정은 결정 문서 없이 가능하다.
- 조항을 폐지할 때는 삭제하지 않고 폐지 표시와 폐지 사유 링크를 남긴다.
- 이 문서와 세칙(AGENTS.md 등)이 충돌하면 이 문서가 우선하되, 충돌을 발견한 사람은
  같은 커밋 또는 즉시 후속 커밋에서 세칙을 정합시킨다.
