## 무엇을 정했나

1. **백엔드를 사내 물리 서버 한 대에 docker compose 로 올린다.** 목적은 **팀 공용 통합 서버**다.
   각자 노트북에서 백엔드를 띄우고 각자의 데이터를 보던 것을 한 곳으로 모은다.
   - 앱 개발자가 백엔드를 자기 노트북에 띄우지 않아도 된다
   - 모두가 **같은 데이터**를 본다 — "제 로컬에선 되는데요" 가 사라진다
   - main 에 머지되면 자동 배포돼 통합 문제가 빨리 드러난다

   상주하는 것은 `docker-compose.yml` 의 api, 워커 넷(편집·렌디션·분석·알림), postgres, redis, minio 이고,
   마이그레이션은 배포 때 한 번 도는 `migrate` 서비스가 맡는다.
2. **데이터베이스는 서버의 컨테이너로 돌린다.** Supabase 는 로그인(Auth) 전용으로 둔다.
3. **배포는 서버에 설치한 GitHub self-hosted runner 가 받아 실행한다.** GitHub 쪽에서 이미지를 빌드·
   스모크 검사해 GHCR 에 올리고, 서버의 runner 가 그 이미지를 받아 마이그레이션 → 컨테이너 교체 → 헬스체크를 한다.

## 전제 — 사내망 서버의 제약

| | |
|---|---|
| 메모리 / 디스크 | 97GB / 791GB — 넉넉하다. 성능은 제약이 아니다 |
| 외부 → 서버 | **불가**(사내망 전용) |
| 서버 → 외부 | 가능 |

서버에서 바깥으로 나갈 수 있다는 점이 이 구성을 성립시킨다. 이미지 내려받기·Supabase 로그인·
FCM·OpenAI 가 전부 **나가는** 방향이다.

반대로 **이 서버는 실사용자를 받을 수 없다.** 사내망 전용이라 LTE 로 접속하는 사용자의 폰이 닿지
않는다. 바깥에서 **우리를 불러야** 하는 SNS 게시·결제 웹훅·광고 보상 검증은 mock 으로 둔다
([deployment.md](./deployment-on-prem.md) §0). 실사용 서버는 외부 접속이 되는 곳에 따로 필요하며, **그때
이미지와 파이프라인은 그대로 재사용된다** — 지금 하는 일이 그때 버려지지 않는다([deployment.md](./deployment-on-prem.md) §6).

## 왜 DB 를 서버 컨테이너로 두는가

클라우드 배포를 전제로 Supabase Postgres 를 검토했으나, 사내 서버로 정해지면서 전제가 달라졌다.

- 메모리가 충분하다
- 인터넷이 끊겨도 돈다
- 무료 플랜 자동 일시정지 위험이 없다

관리형 DB 가 아니므로 백업은 매일 덤프로 해결한다(절차와 한계는 [deployment.md](./deployment-on-prem.md) §4).

## 왜 self-hosted runner 인가

GitHub Actions 는 평소 **GitHub 이 빌려주는 컴퓨터**에서 돈다. 그 컴퓨터는 사내망 안으로 들어올
수 없으므로 "서버에 접속해서 새 버전으로 바꿔라" 를 시킬 수 없다.

**self-hosted runner 는 그 작업자 프로그램을 우리 서버에 설치한 것이다.** 설치하면 서버가
GitHub 쪽으로 **먼저 연결을 걸어** "나한테 시킬 일 있나요?" 하고 계속 묻는다. 일이 생기면
받아와서 **서버 안에서** 실행한다. 바깥에서 들어오는 문을 열 필요가 없다.

> 택배 기사가 회사 안으로 못 들어오니, 우리 직원이 정문까지 나가서 받아오는 것과 같다.

## 기각한 대안

- **DB 를 Supabase Postgres 에 둔다** — 클라우드 배포를 전제로 한 안이었다. 사내 서버에서는 위 세
  가지 이유로 컨테이너 쪽이 낫다.
- **GitHub 이 빌려주는 컴퓨터에서 서버로 접속해 배포한다** — 사내망이 바깥의 접속을 받지 않아
  성립하지 않는다. 성립시키려면 방화벽에 들어오는 구멍을 내야 한다.
