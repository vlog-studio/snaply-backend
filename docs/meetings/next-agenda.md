## 0. 사용 방법

각 안건은 다음 순서로 진행한다.

1. **이미 확정된 사실**을 읽는다. 이 내용은 이번 회의에서 다시 뒤집지 않는다.
2. **결정 질문**마다 선택지 하나에만 `[x]`를 표시한다.
3. 추천안을 따르지 않아도 된다. 다른 안을 택하면 이유를 한 줄 남긴다.
4. 결정을 미루면 반드시 **막힌 이유·결정 담당자·재논의 날짜**를 적는다.
5. 안건 마지막의 **확정 기록**을 채운다.

- `Video`는 사용자에게 평면으로 귀속한다.

## 2. 크레딧 결제 정책 — P1

### 이미 확정된 사실

- **Free/Standard/Premium 정기 구독은 제품 모델에서 제거한다.**
- 무비 생성 비용은 사용자가 보유한 크레딧에서 차감한다.

## 3. 영상 분석·하이라이트 추천 — P1

- 원본 영상 전체나 오디오는 외부로 보내지 않고, 최대 4개 저해상도 프레임을 한 요청으로 분석한다.

## 7. 공동 소유 정책 3건 — P0

### 7-1. FCM 멀티 디바이스

#### 현재 동작

- `User`에는 `fcmToken` 문자열이 하나만 있다.
- `POST /auth/fcm-token`을 호출하면 이전 값을 새 토큰으로 항상 덮어쓴다.
- 알림 발송도 그 토큰 하나만 조회해 `send()`으로 전송한다.
- FCM이 토큰을 무효라고 응답하면 사용자 행의 `fcmToken` 전체를 `null`로 만든다.

즉 현재 구조에서는 같은 계정으로 휴대폰 A에 로그인한 뒤 태블릿 B에서 로그인하면, B의 토큰이
A의 토큰을 덮어쓴다. 이후 geofence 알림은 B에만 오고 A에는 오지 않는다. 마지막으로 등록한
기기의 앱을 삭제하거나 토큰이 만료되면 그 토큰이 정리되면서, 다른 기기가 이미 로그인된
상태여도 다시 토큰을 등록하기 전까지 사용자에게 보낼 알림이 하나도 남지 않는다.

#### 왜 추가 설정이 필요한가

FCM 토큰은 사용자 계정 자체가 아니라 **앱이 설치된 기기·설치 인스턴스**를 가리킨다.
따라서 다음 사용 경험을 지원하려면 사용자와 토큰을 1:N으로 분리해야 한다.

- 한 사용자가 휴대폰과 태블릿을 함께 사용
- 기존 휴대폰을 유지한 채 새 휴대폰에서 로그인
- 같은 계정을 여러 기기에서 사용하면서 모든 기기에 알림 수신
- 한 기기의 로그아웃·앱 삭제·토큰 만료가 다른 기기의 알림을 끊지 않게 처리

`user_devices`를 도입하면 사용자 알림 1건을 활성 기기 토큰 전체로 fan-out하고, 일부 토큰만
실패했을 때 실패한 기기 레코드만 제거할 수 있다. geofence 쿨다운과
`notification_logs`는 **사용자 알림 이벤트 기준으로 한 번만** 기록하고, 기기 수만큼
쿨다운을 소비하지 않는 것이 권장 동작이다.

#### 꼭 필요한가

멀티 디바이스가 무조건 필요한 것은 아니다. 제품이 **계정당 활성 기기 1대만 공식 지원**하고,
새 기기 로그인 시 이전 기기의 알림이 끊기는 동작을 사용자에게 명시한다면 현재 단일 컬럼을
유지할 수 있다. 반대로 여러 기기 로그인을 허용하면서 알림도 정상 동작해야 한다면

### 구현 순서

확정 후 권장 순서는 다음과 같다.

1. **공통 기반**: 스키마 변경 PR → 리뷰 → merge → 양쪽 `npm run db:generate`
2. **Movie**: CRUD → export → 기존 편집 엔진 연결 → API 문서 → e2e
3. **크레딧 결제**: 상품·일회성 Checkout → 원장·예약/차감/환급 → 구독 코드 제거 → e2e
4. **배포**: 이미지 smoke → 스테이징 → migration → 도메인·콜백 → canary
5. **FE-BE 병행 연동**: Movie, `capturedAt`, 스토리지 상태, FCM, SNS 실검증
6. **영상 분석**: 승인된 시점과 비용 가드에 따라 feature flag 상태로 배포
7. **잔여 검증**: Stripe·TikTok·Meta·FCM과 미디어 스트레스 케이스
