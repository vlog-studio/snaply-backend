# 광고 보상형 크레딧 모델 검토안

> **작성일**: 2026-08-12
> **상태**: 예정 회의 안건·의견 기록용 제안 — 아직 승인·구현되지 않았으며 현행 정책이 아니다.
> **미결 작업 원천**: [backlog.md](../backlog.md) A-2, C-1
> **관련 결정**: [credit-payment-model.md](../decisions/credit-payment-model.md)
> **관련 과거 제안**: [2026-08-12 의사결정 워크시트](../archive/2026-08-12-backend-decision-workshop.md) §2

## 1. 한 줄 제안

**Movie 기본 export에 100크레딧을 사용하고, 보상형 광고 한 편이 완료될 때마다
15~20크레딧을 즉시 지급한다.**

`광고 5회 시청 = Movie 1회`처럼 묶음 과제를 노출하지 않는다. 사용자는 광고 한 편만 보고
멈춰도 보상을 보유하며, 구매·가입·이벤트로 얻은 크레딧과 합쳐 사용할 수 있다.

### 초기 운영 가설

| 항목 | 제안값 | 상태 |
|---|---:|---|
| Movie 기본 export | 100크레딧 | 팀 검토 필요 |
| 광고 완료 1회 | 20크레딧 | 원가·eCPM 실측 전 가설 |
| 일일 보상 광고 | 최대 3회 | 부정수급·광고 피로 방어용 상한 |
| 광고 간 쿨다운 | 5~15분 | 클라이언트 UX 검토 필요 |
| 초기 파일럿 | 한국 사용자 10~20%, 4주 | 트래픽 규모에 따라 조정 |

`20크레딧`은 확정 상품값이 아니다. Movie 실제 변동원가와 광고 순매출을 측정한 뒤
`15~20크레딧` 범위에서 확정한다.

---

## 2. 왜 100크레딧 단위인가

경제적으로 `광고 5회 = Movie 1회`와 `광고 1회 = 20크레딧, Movie = 100크레딧`은
같아 보이지만 사용자 경험은 다르다.

| 묶음 보상 | 누적 크레딧 보상 |
|---|---|
| 5편을 모두 봐야 보상 획득 | 한 편마다 즉시 보상 획득 |
| 4편에서 중단하면 보상이 없음 | 언제 멈춰도 잔액이 유지됨 |
| “5편을 봐야 한다”는 완주 압박 | 부족한 만큼만 채우는 선택지 |
| 광고 외 보상과 결합하기 어려움 | 구매·가입·이벤트 크레딧과 결합 가능 |
| 보상 비율 변경이 크게 느껴짐 | `+15`, `+20`처럼 운영 단위 조정 가능 |

100이라는 단위는 광고만을 위한 것이 아니다. 가입 보상, 프로모션, 장애 보상, 구매 보너스 등
서로 다른 지급 사유를 하나의 경제 안에서 조절하기 위한 단위다.

## 3. 사용자 경험 제안

### 3.1 잔액이 부족한 경우

```text
현재 60크레딧
Movie 제작까지 40크레딧이 필요해요.

[광고 보고 +20크레딧]  [크레딧 구매]
```

광고 완료 후:

```text
+20크레딧이 지급됐어요.
현재 잔액 80크레딧
```

### 3.2 표현 원칙

- `광고 2/5회`처럼 묶음 과제나 완주율을 표시하지 않는다.
- 광고를 누르기 전에 이번 광고의 보상량을 명확히 표시한다.
- 광고 한 편이 완료될 때마다 보상을 확정한다.
- 일일 한도는 비용·부정수급 방어용이며 달성해야 하는 목표처럼 노출하지 않는다.
- 광고가 없거나 검증이 지연되면 `지급 확인 중` 또는 이용 불가 상태를 정확히 안내한다.
- 사용자는 광고를 보지 않고도 구매 크레딧으로 동일한 기본 export를 이용할 수 있다.

### 3.3 조합 사용 예시

| 현재 상태 | Movie 제작 방법 |
|---|---|
| 가입 보상 50 | 광고 2회로 40 획득 + 구매 잔액 10 사용 |
| 이전 잔액 65 | 광고 2회로 40 획득 후 100 차감, 5 잔액 유지 |
| 구매 잔액 500 | 광고 없이 Movie 5회 제작 |
| 광고 잔액 20 | 며칠에 걸쳐 한 편씩 보고 누적 가능 |

## 4. 크레딧 원장 정책 제안

사용자 화면에는 합산 잔액을 보여주되 서버 원장에서는 출처를 분리한다.

| 원장 사유 | 의미 | 만료 제안 |
|---|---|---|
| `PURCHASED` | 스토어 결제로 구매 | 만료 없음 |
| `AD_REWARD` | 서버 검증을 통과한 광고 보상 | 30일 또는 만료 없음 검토 |
| `SIGNUP_PROMO` | 신규 가입 보상 | 프로모션 정책에 따름 |
| `EVENT_PROMO` | 이벤트·운영 보상 | 프로모션 정책에 따름 |
| `EXPORT_RESERVE` | Movie export 요청 시 예약 | 작업 완료까지 |
| `EXPORT_SPEND` | export 성공 후 확정 차감 | 해당 없음 |
| `EXPORT_REFUND` | export 실패 후 예약분 환급 | 원래 출처·만료일 복원 |

### 차감 순서

1. 만료가 가장 가까운 프로모션 크레딧
2. 광고 보상 크레딧
3. 구매 크레딧

### export 상태 전이

```text
잔액 확인 → 100크레딧 예약 → Movie export 실행
                         ├─ 성공: 확정 차감
                         └─ 실패: 같은 출처로 전액 환급
```

재시도·중복 요청은 동일한 export에 대해 추가 차감되지 않도록 멱등 키가 필요하다.

## 5. 경제성 검토

### 5.1 기준 공식

```text
광고 1회 손익분기 보상 크레딧
= 광고 완료 1회 순매출 ÷ Movie export 1회 변동원가 × 100
```

예를 들어 광고 1회 순매출이 23원이고 Movie 변동원가가 100원이라면 손익분기는
약 23크레딧이다. 광고 보상을 20크레딧으로 지급하면 사용된 광고 크레딧의 Movie 원가는
약 20원이며 광고 순매출 23원보다 낮다.

### 5.2 조사 기준

한국 보상형 광고 벤치마크를 원화로 환산하면 완료 광고 한 편의 매출은 대략
**13~33원** 범위로 추정된다. 다만 해당 자료에는 게임 앱 데이터가 많이 포함되므로
Snaply의 실제 값은 더 낮을 수 있다.

| 광고 순매출/회 | Movie 원가 50원 | Movie 원가 100원 | Movie 원가 150원 |
|---:|---:|---:|---:|
| 13원 | 손익분기 26C | 손익분기 13C | 손익분기 약 9C |
| 23원 | 손익분기 46C | 손익분기 23C | 손익분기 약 15C |
| 33원 | 손익분기 66C | 손익분기 33C | 손익분기 22C |

따라서 `+20크레딧`은 다음 조건에서만 유지할 수 있다.

- 한국 사용자 대상 광고 순매출이 기준 시나리오에 근접한다.
- 1080×1920 Movie export의 실측 변동원가가 충분히 낮다.
- 무효 트래픽과 중복 지급이 통제된다.
- 광고 크레딧 사용 후에도 공헌이익이 양수다.
- 광고 제공군의 구매 전환율이 대조군보다 유의하게 악화되지 않는다.

### 5.3 Movie 원가에 포함할 항목

- FFmpeg worker CPU·메모리 사용 시간
- 원본 영상 다운로드와 결과 업로드
- 결과 영상·썸네일 저장
- 결과 영상 다운로드 egress
- 선택적 자막 생성 비용
- 실패·재시도로 발생한 중복 처리 비용

참고 자료:

- [Tenjin 광고 수익화 벤치마크](https://tenjin.com/blog/ad-monetization-benchmark-report-2025-ecpm-ad-revenue/)

## 6. 광고 보상 지급 흐름

클라이언트의 `광고를 봤다`는 콜백만으로 크레딧을 지급하지 않는다.

```text
클라이언트                  Snaply API                   광고 네트워크
    │                           │                              │
    ├─ 보상 세션 요청 ─────────▶│                              │
    │◀─ rewardSessionId ────────┤                              │
    │                           │                              │
    ├─ 보상형 광고 시청 ──────────────────────────────────────▶│
    │                           │◀─ 서명된 SSV callback ───────┤
    │                           ├─ 서명·세션·한도 검증          │
    │                           ├─ transactionId 중복 확인      │
    │                           └─ AD_REWARD +20 원장 기록      │
    │                           │                              │
    └─ 잔액 조회 ──────────────▶│                              │
```

### 서버 검증 항목

- SSV 서명과 공개 키
- 허용된 광고 단위와 보상량
- 일회성 `rewardSessionId`
- 광고 네트워크 `transactionId` unique 제약
- 사용자별 일일 한도와 쿨다운
- 비정상 계정·디바이스·IP 패턴
- 이미 취소·정지된 사용자 여부

참고: [Google AdMob 서버 측 검증](https://developers.google.com/admob/android/ssv)

## 7. 스토어·광고 정책 경계

- 보상형 광고는 사용자가 명시적으로 선택해야 한다.
- 광고를 보기 전에 행동과 보상량을 정확하게 고지한다.
- 광고 크레딧은 같은 사용자만 사용할 수 있고 현금화·양도할 수 없다.
- 앱의 주 목적이 광고 시청이 되거나 인위적으로 노출·클릭을 늘리는 구조를 만들지 않는다.
- 구매 크레딧과 광고·프로모션 크레딧은 원장에서 구분한다.
- Apple IAP로 구매한 크레딧에는 만료를 두지 않는다.
- 모바일 앱의 디지털 기능 구매는 Apple IAP·Google Play Billing 또는 각 스토어가 허용하는
  대체 결제 조건을 별도로 검토한다. Stripe Checkout만 연결하는 것으로 결정하지 않는다.

참고 자료:

- [Google AdMob 보상형 광고 정책](https://support.google.com/admob/answer/7313578)
- [Apple App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/)
- [Google Play 결제 정책](https://support.google.com/googleplay/android-developer/answer/9858738)

## 8. 파일럿 제안

### 8.1 사전 조건

- Movie export 1회 변동원가를 작업별로 기록할 수 있다.
- 광고 지급과 export 차감을 출처별 원장으로 추적할 수 있다.
- 광고 미노출 대조군을 유지할 수 있다.
- SSV 검증과 중복 지급 방지가 완료돼 있다.

### 8.2 초기 조건

| 항목 | 제안 |
|---|---|
| 기간 | 4주 |
| 대상 | 한국 사용자 10~20% |
| 보상 | 광고 완료 1회당 20크레딧 |
| 한도 | 사용자당 하루 최대 3회 |
| 노출 위치 | 크레딧 화면과 잔액 부족 화면 |
| 대조군 | 동일 조건 광고 미노출 사용자 |

### 8.3 측정 지표

| 분류 | 지표 | 확인할 질문 |
|---|---|---|
| 광고 | eCPM, fill rate, 완료율, 순매출 | `+20`을 유지할 실제 매출이 발생하는가? |
| 크레딧 | 지급량, 사용률, 미사용 잔액 | 발행한 보상이 실제 원가로 얼마나 전환되는가? |
| Movie | 평균·p95 변동원가, 실패·재시도율 | 광고 보상 사용 후 공헌이익이 양수인가? |
| 결제 | 구매 전환율, 구매 ARPU | 광고가 결제를 잠식하는가? |
| 제품 | 잔액 부족 이탈률, export 전환율, 리텐션 | 광고가 첫 Movie 경험을 늘리는가? |
| 보안 | 무효 트래픽, 중복·차단 지급률 | 운영 가능한 수준으로 방어되는가? |

파일럿 종료 후 `+20 유지`, `+15로 축소`, `대상·한도 변경`, `도입 중단` 중 하나를 결정한다.

## 10. 합의 후 반영 순서

1. [backlog.md](../backlog.md) A-2에 확정값과 구현 범위를 반영한다.
2. [credit-payment-model.md](../decisions/credit-payment-model.md)에 확정된 광고 보상 정책과
   기각한 대안을 기록한다.
3. Movie export 원가 계측과 크레딧 원장을 먼저 구현한다.
4. 광고 SSV 지급 흐름과 일일 한도를 구현한다.
5. 클라이언트의 잔액·광고 선택·지급 대기 UX를 연결한다.
6. 파일럿과 대조군 측정을 수행한다.
7. 실측 결과에 따라 광고 보상량과 노출 범위를 확정한다.

이 문서는 합의 전 제안서다. 확정된 정책의 원천은 결정 문서, 남은 작업의 원천은
[backlog.md](../backlog.md)로 유지한다.
