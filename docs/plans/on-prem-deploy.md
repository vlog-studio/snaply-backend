## 1. 무엇을 만드는가

**팀 공용 통합 서버.** 지금은 각자 노트북에서 백엔드를 띄우고 각자의 데이터를 보는데, 그걸
서버 한 대로 모은다.

- 앱 개발자가 백엔드를 자기 노트북에 띄우지 않아도 된다
- 모두가 **같은 데이터**를 본다 — "제 로컬에선 되는데요" 가 사라진다
- main 에 머지되면 자동 배포돼 통합 문제가 빨리 드러난다

**이 서버는 실사용자를 받을 수 없다.** 사내망 전용이라 LTE 로 접속하는 사용자의 폰이 닿지
않는다. 실사용 서버는 외부 접속이 되는 곳에 따로 필요하며, **그때 이미지와 파이프라인은 그대로
재사용된다** — 지금 하는 일이 그때 버려지지 않는다.

## 2. 서버 사양과 제약

| | |
|---|---|
| 메모리 / 디스크 | 97GB / 791GB — 넉넉하다. 성능은 제약이 아니다 |
| 외부 → 서버 | **불가**(사내망 전용) |
| 서버 → 외부 | 가능 |

서버에서 바깥으로 나갈 수 있다는 점이 이 계획을 성립시킨다. 이미지 내려받기·Supabase 로그인·
FCM·OpenAI 가 전부 **나가는** 방향이다.

## 3. 서버에 올라가는 것

컨테이너 여덟 개다. 전부 이미 `docker-compose.yml` 에 정의돼 있다.

| 컨테이너 | 하는 일 |
|---|---|
| api | 앱이 붙는 서버 |
| edit worker | 영상 편집(무비 생성) |
| rendition worker | 업로드된 스냅을 어디서나 재생되는 형식으로 변환 |
| analysis worker | 스냅 내용 분석(OpenAI) |
| notification worker | 완성 알림 발송 |
| postgres | 데이터베이스 |
| redis | 작업 큐 |
| minio | 영상 파일 저장소 |

**데이터베이스는 서버 컨테이너로 돌린다**(2026-09-15 결정 변경). 클라우드 배포를 전제로
Supabase Postgres 를 검토했으나, 사내 서버로 정해지면서 전제가 달라졌다 — 메모리가 충분하고,
인터넷이 끊겨도 돌며, 무료 플랜 자동 일시정지 위험이 없다. 백업은 매일 덤프로 해결한다.
**Supabase 는 로그인(Auth) 전용으로 지금처럼 둔다.**

## 4. 배포가 도는 방식

### self-hosted runner 가 필요한 이유

GitHub Actions 는 평소 **GitHub 이 빌려주는 컴퓨터**에서 돈다. 그 컴퓨터는 사내망 안으로 들어올
수 없으므로 "서버에 접속해서 새 버전으로 바꿔라" 를 시킬 수 없다.

**self-hosted runner 는 그 작업자 프로그램을 우리 서버에 설치한 것이다.** 설치하면 서버가
GitHub 쪽으로 **먼저 연결을 걸어** "나한테 시킬 일 있나요?" 하고 계속 묻는다. 일이 생기면
받아와서 **서버 안에서** 실행한다. 바깥에서 들어오는 문을 열 필요가 없다.

> 택배 기사가 회사 안으로 못 들어오니, 우리 직원이 정문까지 나가서 받아오는 것과 같다.

### 머지하면 일어나는 일

```
main 에 머지
   ↓
[GitHub 컴퓨터]  이미지 빌드 → 스모크 검사 → GHCR 에 올림      ← 이미 구현돼 있다
   ↓
[사내 서버 runner]  이미지 받기 → DB 마이그레이션 → 컨테이너 교체 → 상태 확인
```

윗줄은 이미 동작한다(`.github/workflows/deploy.yml`). **아랫줄이 이번에 만드는 부분**이다.

교체 순서가 중요하다. 마이그레이션이 실패하면 거기서 멈추고 **이전 버전이 계속 돈다** —
반쯤 적용된 상태로 새 코드가 뜨는 것이 제일 나쁘다.

## 5. 한 번만 하는 준비 작업

순서대로 한다. 앞이 끝나야 뒤가 의미 있다.

1. **Docker 설치**, 배포용 계정 생성
2. **self-hosted runner 설치** — GitHub 저장소 설정에서 명령어를 복사해 서버에서 실행한다.
   서비스로 등록해 재부팅해도 살아 있게 한다
3. **시크릿 준비** — 운영은 `.env` 파일을 쓰지 않는 것이 원칙이지만
   ([env-management.md](../decisions/env-management.md)), 사내 서버에는 시크릿 저장소가 없다.
   **root 만 읽을 수 있는 파일 하나**를 서버에 두고 compose 가 읽게 한다. 저장소에는 넣지 않는다.
   넣을 값의 목록은 `apps/api/src/env-spec.ts` 에서 `origin !== 'local'` 인 항목 전부다
4. **`NODE_ENV=production` 주입** — 빠뜨려도 배포는 성공한다. 빠뜨리면 Swagger 가 열린다
5. **운영용 compose 설정 추가** — GHCR 이미지를 받아 쓰도록(지금은 서버에서 빌드하게 돼 있다)
6. **배치 cron 등록** — 아래 §6
7. **첫 배포 수동 실행 → 헬스체크 확인**

## 6. 매일 도는 배치

빠뜨려도 **배포는 성공하고 에러도 나지 않는다.** 대신 알림이 안 가거나 파일이 무한히 쌓인다.

| 시각(KST) | 무엇 |
|---|---|
| 10:00 | 만료 예고 알림 |
| 새벽 | 만료 정리 · 계정 실삭제 · pending 영상 회수 |

**예고와 정리를 같은 시각에 묶지 않는다** — 조용한 시간대(22–08시)에 보낸 예고는 발송되지 않고
버려진다. 그러면 사용자가 예고 없이 영상을 잃는다
([expiry-notice-schedule.md](../decisions/expiry-notice-schedule.md)).

## 7. 사내망이라 안 되는 것

바깥에서 **우리를 불러야** 하는 것들이다. 전부 mock 스위치가 있어 켜두면 나머지는 정상으로 돈다.

| 안 되는 것 | 대응 |
|---|---|
| SNS 게시 — 플랫폼이 우리 MinIO 로 영상을 가지러 와야 한다 | `SNS_MOCK=true` |
| 결제 웹훅(RevenueCat) | `BILLING_MOCK=true` |
| 광고 보상 검증(AdMob) | `AD_REWARD_ENABLED=false`(기본값) |

푸시 알림·스냅 분석은 **나가는 방향**이라 정상 동작한다.

## 8. 실사용 서버가 필요해질 때

이 서버로는 사용자를 받을 수 없으므로 언젠가 외부 접속이 되는 곳이 필요하다. 그때 추가로
필요한 것은 **고정 HTTPS 도메인**(backlog D-1)과 위 §7 의 세 가지를 실제로 켜는 일뿐이다.
이미지·마이그레이션·배치 구성은 그대로 간다.
