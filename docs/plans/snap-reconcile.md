## 1. 지금 상태 — 서버에는 있는데 앱이 묻지 않는다

기기 A에서 찍은 스냅은 서버에 올라가지만, 기기 B나 재설치한 앱은 그 사실을 모른다. 앱이 `GET /videos`
(목록)를 한 번도 부르지 않기 때문이다.

| 구성 | 있는 것 | 없는 것 |
|---|---|---|
| 업로드 | `upload-url` → PUT → `POST /videos`(`durationSeconds`·`capturedAt`) | 치수, 로컬 스냅 id |
| 렌디션 | H.264/SDR 배포본·썸네일·`durationMs`(2단계, 2026-09-09) | 치수 기록 |
| `GET /videos` | `kind` 필터, 커서 페이지(최대 50), 업로드 최신순 | 테스트(0개), 정렬 동점 처리(`id`), 치수, 만료 시각 |
| 삭제·만료 | 행을 툼스톤으로 남긴다(`removalReason`: `user`·`expired`) | **API로 드러나지 않는다** — 목록에서 빠지고 단건은 404 |
| 앱 | 로컬 스냅 id → `videoId` 연결은 동기화 스토어의 `uploaded` 항목뿐 | 목록 조회, 서버에서 온 스냅을 담을 자리(`Snap.uri`는 로컬 파일 전제) |

**그래서 생기는 일**

- 재설치하면 무비는 돌아오지만(`GET /movies`) 컷의 스냅이 없어, 모든 컷이 "스냅 삭제됨"으로 보이고 재생되지
  않는다. 다른 기기에서 만든 무비도 같다.
- 다른 기기에서 지운 스냅이 이 기기에는 남는다. 만료된 스냅도 라이브러리에서는 알 수 없다 — SNAP-12·13의
  앱 쪽이 이 작업에 걸려 있다(A-1).

**선행 결함 둘(E-8)** — reconcile은 서버 사본을 복구 원천으로 믿기 시작하므로 먼저 닫는다.

1. 무비 생성을 취소하면 결과물 행이 soft-delete되는데, 이 행이 **원본 스냅의 S3 키를 들고 있다.** 그래서
   남은 객체 정리 배치(`media:purge-expired` ③)가 원본 스냅 파일을 지운다. 원본 행은 `ready` 그대로 남는다.
2. 사용자 삭제·만료·정리 배치 어느 것도 렌디션(`renditionS3Key`)을 지우지 않는다. 지운 스냅의 재생 가능한
   사본이 계정 purge 전까지 남는다.

## 2. 목표 — 끝나면 사용자가 보는 것

2026-09-27 스펙에 올렸다([specs/snap-library.md](../specs/snap-library.md) §기기 간 동기화, `결정·미구현`).

- **SNAP-15** — 같은 계정의 스냅은 기기와 재설치를 넘어 보인다. 처음 재생할 때 받아 온다. 이미 만료된
  스냅은 나타나지 않는다.
- **SNAP-16** — 한 기기에서 지운 스냅은 모든 기기에서 사라진다(원본 파일 포함). 서버에 연결하지 못한
  동안에는 어떤 기기의 스냅도 지워지지 않는다.
- **SNAP-12**는 목록의 "만료됨"이 만료 전에 그 스냅을 갖고 있던 기기에만 남도록 범위를 좁혔고, 촬영한
  기기의 만료 스냅은 무비에 담을 수 없다고 적었다.

함께 풀리는 것: 재설치·다른 기기의 무비 재생(movie.md 제한 사항), 라이브러리의 "만료됨"과 남은 기간
(SNAP-12·13 앱 쪽).

## 3. 먼저 정할 것

### 3.1 제품 결정 — 2026-09-27 권장안대로 결정

결정의 기록과 기각한 안은 [decisions/snap-sync-across-devices.md](../decisions/snap-sync-across-devices.md)에 있다.
아래 표는 결정 전의 제안 그대로다.

| # | 질문 | 권장 | 이유 |
|---|---|---|---|
| P1 | 다른 기기에서 지운 스냅을, 이 기기의 **로컬 원본까지** 지우는가 | **지운다**("어디서나 삭제"). 삭제 확인 문구에 모든 기기에서 지워진다고 적는다 | 결정 문서 §3.2의 전 기기 전파다. 지우지 않으면 서버에 없는 "이 기기에만 있는" 스냅이 생기고, 로컬이 원천인 지금은 그것을 다시 올릴지까지 정해야 한다. 실수 삭제가 모든 기기에서 되돌릴 수 없게 되는 위험은 휴지통(§6)이 맡는다 |
| P2 | 서버에서 만료된 스냅은 **촬영한 기기**에서 어떻게 보이는가 | 파일은 두고(SNAP-14) "만료됨"으로 표시한다. 이 기기에서 재생은 되지만 **무비에는 담을 수 없다** | 무비는 서버 사본으로 만든다. 담게 두면 그 컷은 영원히 업로드 대기로 남고, 무비 아웃박스는 컷의 스냅이 모두 업로드된 뒤에만 보내므로 무비가 서버로 가지 못한다 |
| P3 | 새 기기·재설치에서 **이미 만료된** 스냅을 목록에 되살리는가 | **되살리지 않는다.** 살아 있는 스냅만 가져온다. "만료됨"은 그 스냅을 알던 기기의 라이브러리와 무비 컷(이미 구현)에서만 보인다 | 만료분은 시간이 갈수록 쌓이기만 하고 새 기기에서 할 수 있는 일이 없다. 정하면 SNAP-12의 "목록·무비에서는 만료됨으로 남아"의 적용 범위를 스펙에서 먼저 좁힌다 |

### 3.2 기술 선택 — 이 계획에서 정한다

| # | 선택 | 기각한 안 |
|---|---|---|
| T1 | **다른 기기에서 온 스냅의 로컬 id는 서버 `videoId`다.** 동기화 항목도 처음부터 `uploaded`로 쓴다 | 새 UUID 발급 — id↔`videoId` 매핑이 하나 더 생긴다. 결정 문서 §4의 "`snap.id` UUID 전환"도 필요 없어진다. 파일명 id는 기기 밖으로 나가지 않고, 기기 밖에서 온 스냅은 이미 UUID다 |
| T2 | **제거 사유는 조회 API로 묻는다.** 목록에서 사라진 id만 `POST /videos/lookup`에 보낸다 | 목록에 `removedSince`로 툼스톤 포함 — 기기 시계와 서버 시계를 비교해야 하고, 첫 동기화 때 계정의 툼스톤을 전부 받는다 |
| T3 | **치수는 렌디션 워커가 ffprobe로 잰다**(회전 반영). 워커는 이미 같은 파일에 ffprobe를 돌린다 | 앱이 `POST /videos`에 싣기 — 새 앱의 새 업로드만 채워지고, 측정 못 한 스탠드인을 거르는 규칙을 클라이언트마다 지켜야 한다 |
| T4 | **다른 기기 스냅의 파일은 `Paths.cache`에 렌디션으로 받는다.** 썸네일은 reconcile 때, 영상은 처음 재생·편집할 때 받는다 | 원본 다운로드 — iPhone HEVC/HDR이 Android에서 안 돌 수 있고 전송량이 약 2.5배다(결정 문서 §6.3). `Paths.document` — 캐시인데 공간을 영구히 쓴다 |
| T5 | **`POST /videos`에 `clientId`(= 로컬 스냅 id)를 싣고 목록에 돌려준다.** 촬영한 기기가 자기 행을 알아본다 | 없이 가기 — 등록 성공 직후 스토어에 기록하기 전에 앱이 죽거나 동기화 스토어 파일을 잃으면(쓰기가 best-effort다) 자기 스냅이 "다른 기기 스냅"으로 한 번 더 보인다 |

## 4. 설계

### 4.1 병합 규칙

한 번의 reconcile은 두 번에 걸쳐 입력을 모은다. ① `GET /videos?kind=source`를 끝 페이지까지 읽는다.
② 목록에 없는 이 기기의 `uploaded` id를 `lookup`에 보낸다. 이미 만료로 적어 둔 id는 다시 묻지 않는다.
그다음 **순수 함수**가 행동 목록을 낸다. 무비의 `entities/movie/lib/movie-sync.ts`와 같은 모양이다.
`pending` 행(등록 전)은 무시한다.

| 서버 | 이 기기 | 행동 |
|---|---|---|
| 살아 있음 | 같은 스냅이 있음(`uploaded` 항목, 또는 id = `videoId`) | 서버 파생값만 갱신한다 — 만료 시각, 다른 기기 스냅이면 길이·치수도 |
| 살아 있음, `clientId` = 로컬 스냅 id | 항목이 `uploaded`가 아님 | 항목을 `uploaded`로 복원한다. 다시 올리지 않는다 |
| 살아 있음 | 없음, 삭제 대기(`deleteTombstones`)에도 없음 | **추가한다** — 다른 기기 스냅으로. 썸네일을 받아 둔다 |
| 살아 있음 | 삭제 대기 중 | 건너뛴다 — 방금 지운 스냅이 되살아나지 않게 |
| 제거됨 `user` | 있음 | 연쇄 삭제(SNAP-5)한다. `DELETE`는 보내지 않는다(P1) |
| 제거됨 `expired` | 촬영한 기기의 스냅 | 파일을 두고 "만료됨"으로 표시한다(P2) |
| 제거됨 `expired` | 다른 기기 스냅 | 캐시 파일을 지우고 "만료됨"으로 남긴다 |
| 모름(행 없음) | 촬영한 기기의 스냅 | 항목을 지워 다시 올린다 — 로컬이 원천이다 |
| 모름 | 다른 기기 스냅 | 지운다 — 어디에도 원천이 없다 |

**안전 규칙** — 둘 다 테스트로 고정한다.

- **목록에 없다는 이유만으로 지우지 않는다.** 지우는 것은 `lookup`이 사유를 말한 경우뿐이다.
- **한 단계라도 실패하면 아무것도 적용하지 않는다.** 네트워크 오류, 페이지 중간의 실패, 삭제 대기
  계정의 403(`ACCOUNT_PENDING_DELETION`), 목(mock) 모드가 모두 여기에 해당한다. 다음 기회에 처음부터
  다시 한다.

**언제 도는가**: `useMovieSync`와 같다. 계정이 바인드된 뒤 한 번, 그리고 포그라운드로 돌아올 때마다 돈다.
로그인 상태에서, 스냅·동기화 스토어가 복원된 뒤에만 돈다.

### 4.2 기존 코드와 만나는 곳

| 곳 | 바뀌는 것 |
|---|---|
| `entities/snap`의 `Snap` | `origin?: 'server'` 추가(없으면 이 기기). 선택 필드라 스토어 마이그레이션이 없다. `uri`는 필수 필드이고 계정 purge가 이것으로 파일을 찾으므로, 받을 캐시 경로 `<Paths.cache>/server-snaps/<videoId>.mp4`로 미리 채운다 |
| 다른 기기 스냅의 값 | 길이는 `durationMs`, 없으면 `durationSeconds`(정수). 촬영 시각은 `capturedAt`, 없으면 `createdAt`(SNAP-10). 치수는 서버 값, 없으면 스탠드인(측정 표시 없이). 위치는 없다 |
| 동기화 스토어 | `uploaded` 항목에 만료 시각을 두고, 새 상태 `expired`를 추가한다 |
| 썸네일 | 캐시 `video-thumbnails/<파일 이름>.jpg`를 먼저 본다. 서버 썸네일을 `<videoId>.jpg`로 받아 두면 `VideoFrame`은 바꿀 것이 없다 |
| 재생·편집 | 파일이 없으면 받은 뒤 플레이어에 넘긴다. `CutPlayer`는 상태·오류 이벤트를 듣지 않는다 |
| 업로드 워커 | `origin: 'server'`는 고르지 않는다. 항목이 `uploaded`라 지금도 고르지 않지만, 방어로 둔다 |
| 메타데이터 백필 | 받지 않은 다른 기기 스냅은 건너뛴다. 서버 `durationMs`·치수가 있으면 측정한 것으로 친다 |
| 삭제(`use-delete-snaps`)·계정 purge(`purge-local-library`) | 캐시 파일 삭제 경로를 추가한다. `deleteLocalRecording`은 `recordings/` 밖을 거부한다 |
| 무비 — 컷 연결 | **바꿀 것이 없다.** 읽어 온 컷은 짝이 없으면 `snapId`에 `videoId`를 쓰므로(`mapRemoteMovie`), T1로 추가된 스냅에 그대로 이어진다 |
| 무비 — 만료 컷 표시 | 로컬 스냅이 없어도 `unavailable`이면 "만료"로 그린다. 지금은 스냅이 없으면 "스냅이 삭제됐어요"가 먼저다(`timeline-cut.tsx`의 `expired = !missing && cut.unavailable`, `cut-inspector.tsx`). P3로 새 기기에는 만료 스냅이 오지 않으므로, 고치지 않으면 만료된 컷이 삭제로 보인다 |
| 무비에 담기 | 만료된 스냅은 고를 수 없다(P2) |

### 4.3 구현하며 바뀐 것 (2026-09-27)

- **다른 기기에서 지운 스냅은 무비를 건드리지 않는다.** 표의 "연쇄 삭제(SNAP-5)"는 스냅·파일·동기화 항목만
  지운다. 지운 기기가 이미 컷을 뺀 무비를 서버에 보냈으므로, 여기서 무비까지 고쳐 보내면 그 기기의 더 새
  편집을 덮을 수 있다. 무비는 무비 동기화가 서버 것을 받아 온다.
- **새 기기의 만료 컷**: P3로 만료 스냅이 오지 않으므로, 원본이 없는 컷도 `unavailable` 이면 "만료"로 읽게
  타임라인·인스펙터·빈 상태 문구를 고쳤다(§4.2 표의 "무비 — 만료 컷 표시").
- **파일을 못 지운 제거는 항목을 남긴다** — 다음 패스가 다시 묻는다.
- **렌디션 워커의 치수는 배포본에서 잰다.** 다른 기기가 받는 파일이 배포본이라 그 치수가 맞다.

## 5. 단계

### 5.1 0단계 — 선행 결함(E-8)

- 결과물 행의 삭제가 원본 스냅의 키를 건드리지 않게 한다. 모든 삭제·만료 경로가 렌디션을 지우게 한다.
  행마다 자기가 가진 객체만 지운다.
- **넘어가는 기준**: 두 가지를 통합 테스트로 확인한다. 취소 후 정리 배치를 돌려도 원본 스냅 키가 남는다.
  삭제·만료 뒤에는 렌디션 키가 지워진다.

### 5.2 1단계 — 서버 계약

- `GET /videos` 항목에 `width`·`height`·`expiresAt`·`clientId`를 추가한다(모두 nullable).
  - `expiresAt`은 `retention-policy`에서 유도한다. 행에 저장하지 않고, 앱에도 15일을 복사하지 않는다 —
    구독이 기간을 바꾸면 사용자마다 달라진다.
  - 정렬에 `id` 동점 처리를 넣는다.
- `POST /videos/lookup` — 받는 것은 `{ ids: uuid[] (≤100) }`, 돌려주는 것은 id별 `live` 또는 `removed`
  (`removalReason`·`removedAt`)다. 남의 id와 없는 id는 똑같이 응답에서 빠진다 — 존재 여부조차 알 수 없어야
  한다(SNAP-8).
- `POST /videos` 본문에 `clientId?`를 받는다. 유일 제약은 걸지 않는다(§6).
- 렌디션 워커가 치수를 기록한다(`width`·`height` 마이그레이션).
- **테스트**: 목록 페이지네이션(지금 0개), `lookup`의 소유권 격리, `expiresAt` 유도, 워커 치수(Python).
- **문서**: Zod 계약 → `npm run openapi:write -w apps/api` → [api-spec.md](../api-spec.md).
- **넘어가는 기준**: 위 테스트가 통과하고, 세로로 찍은 실제 아이폰 스냅 한 편에 회전을 반영한 세로 치수가
  기록된다.

### 5.3 2단계 — 앱: 더하기만 하는 reconcile

- 목록을 읽어 다른 기기 스냅을 **추가만** 한다. §4.1 표의 "제거됨"·"모름" 행은 아직 적용하지 않는다.
  아무것도 지우지 않으므로 먼저 내도 안전하다.
- 함께 넣는 것: `clientId` 복원, 썸네일 미리 받기, 재생·편집 때 파일 받기, 백필·업로드 워커·삭제 경로 보정(§4.2).
- **테스트**: 병합 함수 단위 테스트(표의 각 행), 추가된 스냅이 업로드되지 않는지, 삭제 대기 스냅이
  되살아나지 않는지.
- **넘어가는 기준**: Android dev build에서 재설치 → 로그인 → 스냅과 무비가 돌아오고 무비가 재생된다.

### 5.4 3단계 — 앱: 제거 전파와 만료 표시

- `lookup`을 붙여 §4.1 표의 나머지 행을 적용한다.
- 같은 변경에서 라이브러리의 "만료됨"(SNAP-12)과 남은 기간(SNAP-13)을 그리고, 만료된 스냅을 무비에
  담지 못하게 한다. 로컬 스냅이 없는 만료 컷도 "만료"로 그린다(§4.2). 삭제 확인 문구에 모든 기기에서
  지워진다고 적는다(SNAP-16).
- 2단계와 따로 내는 이유: 이 단계는 지운다. 규칙이 틀리면 사용자의 유일한 원본이 사라진다.
- **테스트**: 안전 규칙 둘(목록에 없다는 것만으로 지우지 않음, 실패하면 아무것도 적용하지 않음), 403에서
  아무것도 지우지 않음.

### 5.5 4단계 — 실기기 검증

같은 계정으로 두 기기(Android dev build와 iPhone)를 쓴다.

1. A에서 촬영 → B에 썸네일로 나타나고, 재생하면 받아 온다. iPhone HEVC 스냅이 Android에서 재생된다(렌디션)
2. A를 재설치 → 로그인 → 라이브러리와 무비가 돌아오고 무비가 재생된다
3. B에서 삭제 → A에서도 사라진다
4. 만료(개발 DB에서 `createdAt`을 당긴 뒤 `media:purge-expired --yes`) → A는 "만료됨"이고 무비에 담을 수 없다.
   B는 "만료됨"이다. 새로 설치한 C의 라이브러리에는 보이지 않고, 그 스냅을 쓴 무비의 컷은 C에서도 "만료"로 보인다
5. 계정을 전환하면 다른 계정의 스냅이 보이지 않는다
6. 비행기 모드나 서버를 멈춘 상태에서 포그라운드로 돌아와도 아무것도 지워지지 않는다

통과하면 SNAP-15·16을 `구현됨`으로 바꾸고, 스냅 기능 문서의 제한 사항과 movie.md의 "reconcile 전" 문장을
고친다. **이로써 SNAP-14 전환의 조건 하나가 채워진다.** 켜는 판단은 A-4에서 한다.

## 6. 열어 두는 것

| 항목 | 지금 하지 않는 이유 |
|---|---|
| 휴지통(삭제 유예) | 결정은 있다(soft delete + 유예, 결정 문서 §1). 다만 서버가 삭제 즉시 파일을 지우는 지금 구조를 바꾸고 복구 화면을 만들어야 하는 별도 기능이다. P1로 삭제가 모든 기기로 전파되면 필요성이 커진다 |
| "이 기기에서만 제거" | 로컬이 원천인 동안, 촬영한 기기에서 제거하는 것은 원본을 지우는 것과 같다. SNAP-14 전환 때 연다 |
| 업로드 멱등(`clientId` 유일 제약·`upload-url` 행 재사용) | 파일명 id는 기기 사이에 겹칠 수 있어서 유일 제약을 걸려면 UUID가 필요하다. T5의 `clientId`는 식별용이라 겹쳐도 해가 없다 |
| 이미 있는 중복 행 | 지난 크래시 창에서 생긴 중복 행에는 `clientId`가 없어, "다른 기기 스냅"으로 한 번 더 보일 수 있다. 개발 단계라 정리하지 않는다 |
| 전송량 | 렌디션 기준 스냅당 약 3MB다. A-4의 "egress 실측 후 재평가"가 4단계 뒤에 실측값을 얻는다 |
