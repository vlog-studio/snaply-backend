**작성일**: 2026-09-09

**미결 작업의 원천은 [backlog.md](./backlog.md) A-1 이다** — 이 문서는 그 항목들을 앱 관점에서

## 0. 무엇이 바뀌었나 (한 문단)

무비(프로젝트)가 **서버 엔티티가 됐다.** 지금까지 무비는 앱의 로컬 저장소에만 있어서 기기를
바꾸거나 앱을 지우면 사라졌고, 생성할 때마다 컷 목록을 `POST /edit-jobs` 로 펼쳐 보냈다.
이제 서버가 무비를 알고, 생성은 `POST /movies/{id}/export` 로 한다. 그리고 스냅과 결과물에
**보관 기간**이 생겨서, 앱이 "만료됨"을 그릴 수 있어야 한다.

## 1. 서버가 준비를 마친 것

| 기능 | 엔드포인트 | 비고 |
|---|---|---|
| 무비 CRUD | `POST/GET /movies` · `GET/PATCH/DELETE /movies/{id}` | |
| 생성(내보내기) | `POST /movies/{id}/export` → 202 `{ jobId }` | 진행률은 기존 편집 작업 API·WS 그대로 |
| 끝내기 | `POST /movies/{id}/finish` | 결과물 파일 삭제, 무비는 남음 |
| **SNS 게시 시 자동 끝내기** | `POST /sns/{platform}/upload` | 게시가 성공하면 서버가 알아서 끝낸다(2026-09-09) |
| 촬영 시각 저장 | `POST /videos` 의 `capturedAt` | **이미 앱이 보내고 있다**(2026-09-09) |
| 만료 정리 배치 | `npm run media:purge-expired -w apps/api` | 스냅 15일 · 결과물 30일 |
| **만료 예고 알림** | `npm run media:notify-expiring -w apps/api` | 삭제 D-3 · D-1 푸시(2026-09-09) |
| **배포 렌디션** | `Video.playbackUrl` · `durationMs` | 업로드 확정 시 자동 생성(2026-09-09) |

### 재생은 `playbackUrl` 을 먼저 쓴다

원본은 아이폰이 기록한 그대로(HEVC, 종종 HDR)라 **다른 플랫폼에서 재생되지 않을 수 있다.**
그래서 업로드가 확정되면 서버가 H.264/SDR 사본을 만들고 `playbackUrl` 로 준다.

- 아직 변환 전이거나 변환에 실패하면 `null` 이다 → 그때는 `originalUrls` 로 폴백한다
- 등록 직후에는 대개 `null` 이다(변환이 몇 초 걸린다). 목록·상세를 다시 읽으면 채워져 있다
- `durationMs` 는 서버가 실측한 길이다 — 클라이언트가 보고한 `durationSeconds` 보다 정확하다

**만료 예고 푸시는 서버가 보낸다.** 삭제 3일 전과 1일 전 두 번이며, 알림 데이터에
`kind: "snap_expiry"` 가 실려 오므로 앱은 그것으로 라이브러리를 열면 된다.
**다만 알림을 끈 사용자는 아무 안내도 받지 못한다** — 화면의 남은 기간 표시(SNAP-13)가
그 경우의 유일한 안내라 앱 작업이 아직 필요하다.

**아직 없는 것**: 서버 목록 동기화(3단계)와 무비 완료 알림의 FCM 전환(여전히 앱의 로컬 알림). 로컬 파일은 여전히 원천이고 업로드가 끝나도
지우지 않는다(SNAP-14) — 전환 조건 중 렌디션은 충족됐고 **reconcile 이 남았다.**

## 2. 앱이 붙여야 할 것

### 2-1. 무비를 서버에서 읽고 쓰기 ★ 가장 큼

`entities/movie` 의 zustand `persist` 를 서버 쿼리/뮤테이션으로 바꾼다. 그 파일의 주석이 이미
이 전환을 예고해 두었다("서버 전환 시 이 파일은 서버 쿼리/뮤테이션으로 바뀌고 로컬 영속은 사라진다").

**기존 로컬 무비는 이관하지 않는다** — 아직 개발 단계이므로 각자 기기의 이전 저장소를 비운다.
마이그레이션 코드를 만들지 않기로 결정했다.

생성 호출도 `POST /edit-jobs` 에서 `POST /movies/{id}/export` 로 옮긴다. 옛 경로는 **한 릴리스
동안 함께 살아 있다가 다음 릴리스에서 제거**된다.

### 2-2. 만료 표시

- 스냅 라이브러리: 만료된 스냅을 **"만료됨"으로 보여준다.** 목록에서 빼면 안 된다 — 사용자가
  무엇을 잃었는지 알아야 한다.
- **사용자가 지운 것과 기간 만료로 사라진 것은 문구가 달라야 한다.** 만료는 우리 정책 때문에
  사라진 것이라 안내 톤도 다르다.
- 남은 보관 기간을 볼 수 있어야 한다(SNAP-13). 알림에만 의존하지 않기 위해서다.
- 무비 화면: 컷의 `unavailable: true` 를 그린다. **무비 자체는 열려야 한다.**

### 2-3. 끝내기 버튼 ⚠️ 여기가 제일 조심스럽다

`POST /movies/{id}/finish` 는 되돌릴 수 없다 — 결과물 파일이 사라지고 다시 보기는 없다.

**공유 시트를 연 것만으로 호출하면 안 된다.** 앱의 `shared/lib/sharing/share-file.ts` 가 직접
적어둔 대로 시스템 공유 시트는 저장 여부를 알려주지 않는다:

> A share is therefore "offered", never "confirmed".

시트를 닫기만 해도 성공과 똑같이 끝나므로, 그대로 끝내기를 부르면 **취소한 사용자의 브이로그가
사라진다.** 다운로드 경로에서는 **사용자의 명시적 행동**을 받아야 한다 — 공유 후 확인 시트든
별도 버튼이든. **SNS 게시 경로에서는 앱이 끝내기를 부르지 않는다.** 서버가 플랫폼의 성공 응답을 직접 봤으므로
게시 성공 시 서버가 그 결과물을 쓰던 무비를 자동으로 끝낸다 — 앱이 또 부르면 이미 끝난 무비라
404 가 난다. 게시 응답을 받은 뒤에는 **무비를 다시 읽어** `finishedAt` 이 찬 것을 반영하면 된다.
(틱톡이 `pending` 으로 접수만 된 경우는 예외다 — 플랫폼이 나중에 영상을 가져가므로 파일을
남겨둔다. 그때는 무비가 끝나지 않은 채로 남는다.)

### 2-4. 화면 수명이 달라진 곳

감상 모드(완성본 재생)는 **완성 시점 ~ 끝내기 전까지만** 존재한다. 끝낸 무비를 열면 결과물이
없으므로 편집 화면으로 연다. 무비 자체는 계속 편집·재생성할 수 있고, 다시 만들기는 **새 생성이라
크레딧 100 을 다시 낸다**(무료 재생성은 폐기됐다).

## 3. 계약에서 오해하기 쉬운 것 넷

1. **컷 순서는 배열 순서다.** `order` 필드가 응답에 없다 — 두 표현이 어긋나지 않게 하려고
   일부러 뺐다. `PATCH` 로 보낼 때도 배열 순서가 그대로 저장된다.
2. **`arranger` 가 순서의 주인이다.** `user`(기본)면 서버가 **절대** 다시 정렬하지 않고,
   `ai` 면 촬영 시각 순으로 정렬한다. 템플릿 추천처럼 서버가 고른 조합은 `ai` 로 만들고,
   **사용자가 순서를 손대는 순간 `user` 로 바꿔 보내야** 그 뒤로 고정된다.
3. **`PATCH` 의 `clips` 는 통째로 교체**다. 부분 수정이 아니다.
4. **생성 중(`generating`)에는 수정·재생성·끝내기가 전부 409** 다.

## 4. 확인이 필요한 것 (앱 쪽 판단)

- **만료된 스냅을 쓰던 무비를 어떻게 보여줄지.** 프로젝트는 영구 보존인데 스냅은 15일이라,
  몇 달 뒤 무비를 열면 컷이 대부분 비어 있을 수 있다. 서버는 그 컷을 `unavailable` 로 표시하고
  그 상태의 `export` 를 400 으로 막는다 — 화면이 그다음에 무엇을 제안할지는 앱의 판단이다
  (컷을 빼고 다시 만들기? 무비를 지우기?). "무비에 쓰인 스냅은 만료 예외" 로 할지의 정책
  판단도 아직 열려 있다([backlog.md](./backlog.md) A-1).
- **끝내기를 어느 화면에서, 어떤 문구로 받을지.** 되돌릴 수 없다는 것이 사용자에게 분명해야 한다.
